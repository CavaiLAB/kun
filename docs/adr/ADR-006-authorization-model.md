## 1 背景与问题（Context）

Kun 对鉴权**全无**：`src/` 中没有任何 `IAuthorizationHandler`、策略或权限抽象；Mediator 没有授权行为；只有 `roles` claim 透传；`IPermissionChecker` 被 Kun 的 ADR 两次推迟（基线 K §2.3）。这是 S1 最大的单项工作量之一，且要同时服务 UI、API、MCP 三入口并与 RLS 协同（基线 P §10.1 第 4 条）。

参考平台的教训：框架层只保证「已登录」，细粒度权限散在业务服务里且可被客户端传参（`menuId / flowIds`）绕过，移动端控制器无校验，数据权限只对自生成查询生效、不是数据库级，权限无缓存每次查库，基数超限静默截断（基线 P 附录 A-14；基线 S §6.2、§9.3；基线 F §3.10）。可借鉴的是「数据权限方案化（菜单 → 条件 JSON 方案 → 角色授权）」与「按钮 / 列 / 字段双重门」（基线 F §3.10）。

基线 S 把权限分为 L0 租户隔离 → L1 角色 → L2 功能权限 → L3 资源实例 → L4 数据权限 → L5 字段 → L6 ABAC 七层（基线 S §9.3）。数据权限多方案合并语义经源码裁决为「同角色内 AND、跨角色 OR、任一方案为全部数据则整体放开」（基线 F 附录 C-1）。

## 2 决策（Decision）

- 【经 S1-DEC-038 D31 修订：`IDataPermissionFilter` 只提供进程内过滤表达式 `GetExpressionAsync<T>`，输出谓词 AST 的 `GetPredicateAsync` 与 `DataPermissionPredicate` 已移除，序列化的数据范围规则用数据契约的 Filter AST（`contracts/data/v1`、`contracts/authz/v1`）；HTTP、gRPC、命令与配置四类执行入口以 `AuthorizationSubject` 判定，并显式传身份修订与委托状态；gRPC 以内核标记接口 `Kun.Authorization.IPermissionEnforcementInterceptor` 识别权限拦截器】**D6.1 Kun 侧只新增 `Kun.Authorization` 端口**：`IPermissionChecker`（`Check / BatchCheck / ListAllowedActions / ListPermissions / Explain`）、`IDataPermissionFilter`（输出 EF 表达式或 SQL 谓词 AST）、`IFieldPolicy`，以及 ASP.NET Core 策略、Mediator Pipeline 行为、gRPC 拦截器集成；不放实现。
- **D6.2 `qian.authz` 为内置实现**（`tier: system, alwaysEnabled`）：权限点与默认角色模板由插件清单 `provides.permissions` 声明并登记；资源类型（应用、菜单、按钮、API、流程、打印…）由插件注册。权限点编码统一为 `<plugin-id>:<resource>:<action>`（如 `qian.workflow:flow:launch`、`qian.crm:customer:read`）：清单只声明 `resource` 与 `actions`，插件 ID 前缀由 `qian.authz` 登记时拼接。
- **D6.3 租户域 RBAC**：内置角色（平台超管；租户 Owner / Admin / 开发者 / 使用者）+ 自定义角色；主体可为用户、组织、岗位、用户组；有效角色 = 直接授予 ∪ 经组织 / 岗位 / 组获得；`Check` 缺省拒绝；平台超管旁路在策略中显式声明并审计。
- **D6.4 数据权限（L4）**：条件树 + 系统变量（`@userId @userAndSub @organizeAndProgeny @positionAndSub` 等，每个带自然语言描述写进契约），**编译成 SQL / EF 谓词在本地执行**，RLS 永远兜底；合并语义固定为「同角色 AND / 跨角色 OR / 任一全部数据则放开」，不做可配置（Q19）；开了数据权限但主体无任何方案 = 查不到数据；行级策略覆盖所有读写路径，不只列表。
- **D6.5 字段权限（L5）**：读投影或脱敏，写白名单；［前端框架］按元数据渲染，以服务端为准。
- 【经 S1-DEC-045 D5 标注：给不在平台宿主里的系统用的远程接口上，「每次决策」读作执行前的那一次判定；界面为显示而问的预判不逐条入审计，只计数；高风险的权限点放行每条都记。见 §10】**D6.6 每次决策可解释**（`{allow|deny, reason, matchedPolicies}`）并入 `qian.audit` 哈希链。
- 【经 S1-DEC-045 D4 标注：远程接口上，执行前的判定每次都问、不缓存；界面用的结果按时长缓存，最长多久是一项配置，缺省 3 秒；数据范围最多缓存 3 秒；都没有推送。见 §10】**D6.7 权限不进令牌**：令牌只含身份与会话类 claim（规范集 `sub`、`tenant_id`、`membership_id`、`scope`、`identity_revision`、`sid`、`amr`、`acr`，预留 `profile`、`act`），不含权限集合（S2S 令牌的 `roles[]` 例外见 ADR-010 D10.4 / R24）；有效权限按主体缓存，以 `identity_revision` 递增 + 推送刷新即时失效；网关 `ForwardedClaimTypes` 白名单只转发 `identity_revision`，不转发权限集合。（2026-10-22 S1-DEC-027：授予的增、改、撤提交后，授权组件在同一调用内经身份端口 `BumpIdentityRevisionAsync` 递增受影响 user 主体在该租户的修订，并把服务端修订下限同步抬到新值。这一做法只在同进程宿主里生效，身份组件不在本进程即跳过。瞬时故障退避重试，总时长不超过 3 秒；仍失败记警告与计数，不回滚授权变更。`authz.role.changed.v1` 不扇出。非 user 主体与无成员身份的主体跳过。陈旧令牌回 401（gRPC Unauthenticated），客户端据此换令牌。拆分部署（platform / identity 两个 Pod）由身份侧订阅 `authz.grant.changed.v1`，随 S1-EVT-002 闭环，见 S1-IDP-012。）
- **D6.8 鉴权唯一入口**：UI、API、MCP 三入口同一个判定服务；网关 + 服务端双层强制；「端点 → 权限点」写进 OpenAPI 扩展并与能力清单共用；低代码数据引擎在唯一入口做「资源 + 动作 + 行级」三段式校验，不依赖设计器布尔开关与客户端传参；内部调用走服务身份。
- **D6.9 S3 可选 OpenFGA 插件**（`qian.authz.openfga`）处理资源实例共享与市场授权（L3 ReBAC）；行级过滤不交给远程引擎（ListObjects 默认截断 1000 条 / 3 秒）；网关粗粒度 ABAC（OPA）S3 可选。
- **D6.10 高级权限模式**（身份切换、组织角色、逐级递减、互斥 / 基数 / 先决约束）为 S3 可选；S1 在令牌预留 `profile` claim，权限模型按 L0–L6 分层留扩展位（Q10 补充裁决）。基数超限直接拒绝并返回结构化错误。
- **D6.11 配额与可见性口径**：平台超管不计入租户用户配额，租户管理员计入；平台超管对租户不可见，但审计可见（Q12 补充裁决）。
- 【经 S1-DEC-038 D25 修订：启用时点由 S4 提前到路线里程碑 M1「能问能查」（平台级裁定 P31）；看板的四个阶段怎么对应到路线的里程碑，产品负责人 2026-11-24 说这一问先移除。现状：服务间令牌按冻结契约只接受 `user` 与 `service` 两类主体，带委托的主体拒绝】**D6.12 统一主体模型** `user / service / agent` + 委托链字段（RFC 8693 `act`）S1 设计到位；S4 启用时 Agent 有效权限 = 委托人权限 ∩ 授予 scope；权限点带风险级别与 step-up 标记；危险操作 Agent 只能发起申请。
- **D6.13 MFA**：TOTP S1 必做（见 ADR-005 D5.3）；商密要求不做假设。

## 3 理由（Rationale）

- 端口在 Kun、实现在 Qian，兑现 Kun ADR 留下的重议条件，又不违背其「不做权限模型」的定位（基线 K §2.3）。
- 权限不进令牌避免令牌膨胀与权限变更后的「旧令牌仍有效」窗口；代价（查询压力）由按主体缓存 + `identity_revision` 解决（基线 S §6.2 第 4 条）。
- 本地编译谓词叠加 RLS，是动态表场景下唯一既有性能又有兜底的方案；远程 ReBAC 引擎有截止时间与条数限制，不能当行过滤器（基线 S §6.2 第 5 条）。
- 合并语义不做可配置：源码裁决的语义已可覆盖参考平台全部用例，可配置会让策略引擎与 Agent 的可解释性复杂化。

## 4 备选方案与放弃原因（Alternatives）

- **权限进令牌**：令牌膨胀、变更不即时、权限集合经网关透传到下游不可控。放弃。
- **OpenFGA / OPA 作为主引擎**：行级过滤性能与截断限制不可接受，且与 RLS 叠加困难；仅作 S3 适配插件。放弃作主引擎。
- **Casbin 类库内嵌**：模型表达力与可解释性不足以覆盖数据权限编译，且需要再造管理面。放弃。
- **鉴权分散在控制器**（参考平台）：可被客户端参数绕过，三入口不一致。明确反例。

## 5 后果与代价（Consequences）

- 正面：三入口一致；每次决策可解释、可审计，S4 的 `Explain` 直接作为 Agent 工具；数据权限对动态表与手写表一视同仁。
- 负面：权限模型从零自建，S1 与身份核心互为前置；按主体缓存的跨服务一致性是工程难点；数据权限编译器依赖 S2 元数据，S1 只能落契约。
- 配套：权限管理界面（S2）、授权界面含字段 / 数据（S2）、创建者自动 Owner、［前端框架］权限渲染协议、决策审计查询。

## 6 对各阶段的影响

- **S1**：端口 + 租户 RBAC + 权限点清单登记 + API 强制校验 + 决策审计 + `identity_revision` 失效 + 数据权限契约与系统变量目录。
- **S2**：数据权限编译器、字段权限、授权界面、数据权限方案随发布自动生成。
- **S3**：OpenFGA 插件、OPA、高级权限模式、应用中心 / 后台权限区分。
- **S4**：Agent 有效权限 = 用户权限 ∩ scope；`Check / ListAllowedActions / Explain` 作为 MCP 工具。

## 7 待确认事项

- 等保 2.0 / 商密要求（Q18：不做假设，需确认）。
- 按主体缓存有效权限的存储与失效推送方案（Redis 背板）需技术验证。
- `ListAllowedActions` 在大租户、多角色下的性能基线需测。

## 9 平台上不论做什么系统，权限都走这一套（2026-11-26）

产品负责人 2026-11-26 说（[S1-DEC-043](../../pm/tasks/S1-DEC-043.md) D7；平台级裁定 P86，原文在 `CavaiLAB/jiangxin` 的 [2026-11-26 平台级裁定](https://github.com/CavaiLAB/jiangxin/blob/c7b32a4dea2d1455fd2b9835e1cc0848c9d036c2/docs/decisions/2026-11-26-platform.md)）：「另外，这个企业级平台后续不论做什么系统，权限都是要走这一套的，所以要在  Kun 框架上做好这部分。」

- 读法（整理者的读法，产品负责人没有逐句确认）：平台上做的任何系统，判权限只问 Kun，不各做一套。管理端、应用、插件、Agent、DSH 一侧的服务都算。
- 与本文的关系：没有出入，同向。D6.8 定的是界面、接口、MCP 三个入口用同一个判定服务；这次把范围说到平台上做的所有系统，其中有不在本仓库里的。它与他 2026-11-24 的一句也同向：「所有涉及到权限的这些，后面我都会接入到 PaaS 服务上。统一使用 C# 进行提供。」（见 [ADR-017](ADR-017-deployment.md) §12）
- 现状：判定的端口、权限点的注册表、租户域的角色权限、三处强制执行点与决策审计已有（S1-AZ-001 至 S1-AZ-004），给 .NET 进程里的代码用。给别的进程、别的语言用的远程授权接口是规划，还没有实现；[S1-AZ-005](../../pm/tasks/S1-AZ-005.md) 没有开始。D6.4 的数据权限、D6.5 的字段权限排在 S2，D6.12 的 `agent` 主体在路线里程碑 M1 启用，都还没有做。
- 没有定的：远程接口的形状；先做哪几种接法。
- 看板上的任务没有动，没有新建任务，没有改代码。

## 10 远程授权接口的十个问题定了（2026-11-26）

产品负责人 2026-11-26 说（[S1-DEC-045](../../pm/tasks/S1-DEC-045.md) D1 至 D10）：「远程的授权接口 也按照建议执行」。答的是远程授权接口[契约草案](../prd/specs/authz-remote-interface.md)第 14 节的十个问题。「建议」是整理时列给他的十条，都是各问的选项（一），其中六条另加了条件；十条照录在 S1-DEC-045 里。

- 读法（整理者的读法，产品负责人没有逐条确认）：他只说了这一句，没有逐条回；十条建议连同加的条件一起算已定。「执行」读作登记、把草案改成裁定后的版本、建任务，实现照任务的先后来。
- 与本文的关系：没有一条推翻本文。§9 末尾写「没有定的：远程接口的形状；先做哪几种接法」。先做哪几种接法现在定了。远程接口的形状只定了下面几件；端点与字段、名字、数字仍是提议，等契约定稿（[S1-AZ-011](../../pm/tasks/S1-AZ-011.md)）。

定了什么。括号里是契约草案里写它的那一节：

| 条目 | 定成什么 | 加的条件 | 与本文的关系 |
|---|---|---|---|
| D1 先做哪几种接法 | 先做人问自己与登记过的系统替人问；智能体带着委托链问的那一种随路线里程碑 M1（第 3 节） | 没有 | §9 里没有定的一件；D6.12 的启用时点不变 |
| D2 代问带不带本人的令牌 | 别的系统替某个人问，缺省带这个人的登录令牌，由平台自己核对；拿不到的场合逐个登记成例外（第 4.3 节） | 没有 | 加上的内容：一个系统替某个人问，平台要自己核对这个人的令牌，是认证上新加的一条路，记在 [ADR-010](ADR-010-gateway-layers.md) §10 与 [ADR-005](ADR-005-identity-sso.md) §10。被判定的主体写在请求体里是草案的设计，仍是提议 |
| D3 几个租户共用的系统用几个身份 | 一个身份，只能带着本人的令牌问，租户以令牌为准；例外只开在判定接口上（第 4.3 节） | 后台作业那一部分仍要按租户各登记，建议随租户开通自动登记，不靠人手。「建议随租户开通自动登记」读作要做，是整理者的读法 | 冻结契约的说明里「租户域的端点见到平台级的主体一律拒绝」之外的一处例外。冻结的契约这次没有动 |
| D4 权限改了多久生效 | 守 3 秒：执行前的那一次每次都问、不缓存；界面显示用的结果与数据范围最多缓存 3 秒（第 8 节） | 执行前每次都问是硬的一条；界面上按钮多久消失做成配置，缺省 3 秒，量出来撑不住再放宽，放宽不用再裁定 | D6.7 在远程接口上怎么读 |
| D5 哪些判定留审计记录 | 执行前的那一次留，拒绝必记、放行按现有的采样配置；界面为显示而问的只计数（第 11.1 节） | 高风险的权限点，放行也每条都记，不参加采样 | D6.6 在远程接口上怎么读 |
| D9 客户端包的语言 | TypeScript 与 .NET（第 7 节） | 谁在前看第一个使用方；接第一个历史系统时再看要不要出 Java | 加上的内容 |
| D10 协议 | 先只做 HTTP（第 6 节） | 没有 | 加上的内容 |

D6、D7、D8 说的是要人确认的能力，记在 [ADR-016](ADR-016-agent-boundary.md) §11；D8 另记在 ADR-010 §10 与 [ADR-012](ADR-012-workflow-engine.md) §10。

D6.6 与 D6.7 照这次的裁定怎么读：

- D6.6「每次决策可解释并入审计的哈希链」。在远程接口上，「决策」读作执行前的那一次判定，即别的系统真要执行受保护的操作之前问的那一次。界面为了决定显示什么而问的预判不逐条入审计，只按调用方、按结果计数。平台宿主里现行的分法也是这样：经执行端口的判定记，「列出持有的权限点」不逐条记。条件加了一层：高风险的权限点放行不参加采样，每条都记。「高风险」读作风险等级是 `high` 或 `critical`，是整理者的读法。现在的采样不看风险等级，要改。
- D6.7「以 `identity_revision` 递增 + 推送刷新即时失效」。在远程接口上，执行前的判定每次都问，下一次判定就生效，与进程内一样。界面用的结果与数据范围按时长缓存，没有推送。界面用的结果最长缓存多久是一项配置，缺省 3 秒；放宽以后别的系统界面上的按钮可能慢过 3 秒才变，执行不受影响。数据范围最多缓存 3 秒，不在这项配置里。把「做成配置」读成这一项配置、把数据范围放在它之外，是整理者的读法。
