# ADR-024 模型服务：平台不装 Higress，额度用积分

> 方括号里是代称，替换了产品负责人原话里点名的开源项目与仓库地址；本仓库不写这些名字。

> 状态：Accepted（2026-11-27）。各条的来路不同，标在各条上：「已定」是产品负责人定的；「带条件」是他说了条件、条件由整理者的评估判定的；「读法」是整理者对他的话的理解，他没有逐句确认；「提议」是整理者的建议，没有裁定。读法与提议不随本文接受，哪一条不对，照他的话改。答复的原话与九个问题各到哪一步，登记在 [S1-DEC-044](../../pm/tasks/S1-DEC-044.md)。ADR-015 已标部分取代与换主语，ADR-010 已标修订，ADR-016 的两条加了标注（经 Higress 的路没有了对象，新路是提议七）。都还没有实现。

本文说的「模型入口」，指平台一侧接调用方的模型请求、转给上游的那一处；「现成的模型网关」，指 Higress 这一类另外安装的网关；「推理服务」指自己管 GPU 与模型的推理服务，现行的选型是 GPUStack（ADR-015 D15.2、D15.3 里与 Higress 无关的部分，仍然有效）。

## 1 背景与问题（Context）

ADR-015（2026-10-06）定模型服务并入团队现有的 Higress / MaaS 设施：模型请求由 Higress 转发，本仓库一侧只做上游登记、适配与模型目录，不自写模型代理（D15.1、D15.3、D15.5）。当时的理由是 Higress 已是团队唯一的模型流量咽喉点，另起一套会分裂计量、限流与账单（ADR-015 §3）。

2026-11-26 产品负责人定了企业级框架分两种、多租户与单租户两个版本，模型服务留标准的接口、只提供一套（[S1-DEC-043](../../pm/tasks/S1-DEC-043.md) D5；两种形态按带不带模型推理分，是那里登记的读法）。随后有了一份[契约草案](../prd/specs/model-service-interface.md)（提议，[S1-MGW-004](../../pm/tasks/S1-MGW-004.md)），九个待裁定的问题由 S1-DEC-044 跟踪。草案与问题当时都照「模型请求由现成的模型网关转发」写。

同一天他接着讨论模型服务接口，说了下面四句。原话照录；第一句里点了四个开源项目的名字，本仓库不写项目的名字，换成了方括号。

1. 「模型服务接口需要讨论一下，首先接入可以参考［三个开源项目］等可以接入更多的模型，也可以参考［一个开源项目与它的仓库地址］，可以给每个用户固定的额度。」
2. 「额度的单位用积分，可以选择是否启用积分系统，周期也可以选择。在考虑是否还要 Higress」
3. 「评估一下，不需要就不安装了吧。你觉得有这个必要吗？因为它安装起来还是挺复杂的。」
4. 「但是你要考虑 GPU Stack 使用他作为模型推理服务的时候，如何交互。」这一段后面几句要两套部署（带推理服务与不带）的架构设计与数据流，并问到 Web 端多用户怎么实现。两套部署里模型请求怎么走写在 §2.4 提议六，其余不在本文里。

第 2 句回的是整理时列给他的五条，原样录在 S1-DEC-044。第 3 句回的是整理时给他的另一份看法。那份看法建议 Higress 不再当必装件，所有形态只走调用方、模型入口、上游这一条路，现场已有的网关登记成一个上游；它把这叫作可选，内容与现在的 D24.4 加提议一、二相同，不是 §4 里不选的两条路并存。第 3 句之后，整理者做了评估与本机实测，结论是不需要，见 §3。点名的四个项目怎么接模型、怎么管额度，整理时读了，归纳在契约草案第 4.5 节。

要定的是：Higress 还装不装；不装的话模型请求由谁转发；额度怎么算；ADR-015 哪几条随之改。

## 2 决策（Decision）

### 2.1 产品负责人定的

- **D24.1（已定）额度的单位用积分。**
- 【2026-11-27：开关按租户设，关着时用量照记，已定，见 §10.2 第 15 条】**D24.2（已定）积分系统可以选择启用或不启用。** 开关设在哪一级，他没有说，见 §2.3 读法二。
- 【2026-11-27：周期可选日、周、月，缺省每周一重置，照原表建议已定，见 §10.2 第 15 条】**D24.3（已定）额度的周期可以选择。** 有哪几种周期、缺省是哪一种，没有定。整理时列给他的是「周期可配，缺省每周」，他答的是周期可以选择，没有说缺省。

### 2.2 带条件的

- 【2026-11-27：原表第 5 条照建议定了模型请求都过平台自己的模型入口，整理时读作条件得到确认，见 §10.3】**D24.4（带条件）平台不装 Higress。** 他的话是 §1 第 3 句，条件是评估下来不需要。评估是整理者做的，结论是不需要，依据见 §3；这个结论他没有逐句确认。评估的结论对集群上的部署与单机版都一样。推理服务自己内置的那一套算不算平台装的，见 §2.4 提议四。

### 2.3 读法（整理者的，他没有逐句确认）

1. 【2026-11-27 转成已定：原表第 7 条照建议，见 §10.2】**调用方的凭据落到人和应用头上。** 从 §1 第 1 句的「可以给每个用户固定的额度」读出，因为按人给额度，就得认得出人。照这个读法，契约草案的问题 5 也有了答案，见 S1-DEC-044。
2. 【2026-11-27 转成已定：原表第 15 条照建议，他的原话里也有，见 §10.1、§10.2】**积分系统的开关按租户设**，单租户版就是整个部署一个；**关着时用量照记，不拦调用**。整理时告诉了他这是读法。

### 2.4 提议（整理者的建议，没有裁定）

1. 【2026-11-27 转成已定：原表第 5、11 条照建议，见 §10.2】**模型请求由平台自己的模型入口转发。** 不装 Higress 以后，转发总要有一处做。提议由平台自己做：模型入口是 Kun 的模型组件里的一个独立服务，验调用方的凭据，得到租户与人；查权限与额度；按逻辑模型名选上游，换成上游的模型名与密钥；流式转发；边转边记用量。所有形态、所有版本只有这一条路：调用方 → 模型入口 → 上游。不换装别的现成模型网关。
2. 【2026-11-27 转成已定：原表第 5 条照建议，见 §10.2】**现场已有模型网关，或者一定要某一家的原生协议时，把那个网关的 OpenAI 兼容入口登记成模型入口的一个上游。** 平台不去配它，也不依赖它。团队集群里现有的那一套 Higress 照此处理：不动，要用时登记成一个上游。
3. 【2026-11-27 起按提议推进：成批的丙批「接入更多模型的做法」，归到这一项是整理时的读法；调用方一侧第一版做 OpenAI 兼容的对话、嵌入、模型列表，是原表第 10 条照建议定的，管的不是上游，见 §10.3】**第一版上游只认 OpenAI 兼容这一种协议。** 原生协议的上游以后做成适配，或者照提议二经一个网关接。
4. 【2026-11-27 转成已定：原表第 9、13 条照建议，见 §10.2】**推理服务只当一个 OpenAI 兼容的上游。** 交互分两条线。推理这一条：模型入口调它的推理接口，用一把专门签给平台的 key；人、租户、额度都不传进去，只带一个不含个人信息的请求编号。管理这一条：模型管理读它的管理接口，拿模型清单与健康；管理端里的上下线只动平台的目录，部署与扩缩第一版留在它自己的界面。用量以模型入口记的为准，它自己记的只用来对账。它自带的模型供应方与指向外部的路由不用；它内置的网关由它自己装、自己管，不算平台装的，平台也不往里加配置，D24.4 的「不装」只说平台这一侧。
5. 【2026-11-27 转成已定，是首选：原表第 13 条照建议，他写的是「GPUStack 首选平台集群外的专机」，同一个集群没有排除，见 §10.2】**推理服务放在平台的集群外面的专门机器上。** 理由见 §3.6。客户一定要装进同一个集群时，要先解决两个入口控制器抢 80、443 端口的事，这种装法没有试过。
6. 【2026-11-27 转成已定：原表第 5 条照建议，与 D24.6 同向，见 §10】**两种部署里模型请求走同一条路。** 差别只在上游：带推理服务的，上游是推理服务，也可以再接第三方的模型 API；不带的，上游是第三方的模型 API。平台装在集群上还是一台服务器上，不影响这条路。
7. 【2026-11-27 起按提议推进，细节随 M1 的设计：成批的丙批，见 §10.3】**Agent 调平台能力的路改走平台自己的网关，随 M1 的设计定。** ADR-016 D16.9、D16.10 原定 Agent 经 Higress 的 MCP 路由调平台能力，每个租户的 MCP 门面托管在 Higress 上。不装 Higress 以后，改成经平台自己的网关到每个租户的 MCP 门面。别的不变：不直连服务的裸地址，每次调用在服务端查权限，标了要人确认的能力由平台停下来等人点（ADR-016 §9、§11）。

### 2.5 对 ADR-015 的后果

- 【2026-11-27：注明随提议的几处，随提议一、二、四的定了，随提议七的按提议推进；D15.3 的边界与 D15.5 的前半句放开，D15.10 里的「租户覆盖」与租户自带的端点不再成立，见 §10.4】**D24.5** ADR-015 的各条照下表处理。D15.1 随 D24.4 不再成立。D15.2、D15.3、D15.5 里写着 Higress 的部分随 D24.4 不再成立，与 Higress 无关的部分照旧。D15.3「只做三件事」的边界，与 D15.5 前半句「不自写模型代理层」，放不放开随 §2.4 提议一，没有裁定，不随本文接受（§7）。D15.4、D15.6、D15.10、D15.11 原来由 Higress 承担或写着 Higress 的地方没有了对象，内容不变；新的主语随提议，D15.4、D15.10、D15.11 随提议一，D15.6 随提议二、四，不随本文接受。

## 3 理由（Rationale）

本节是整理者的评估，2026-11-26 做的。「读到」的出自 Higress 与推理服务的上游源码与文档，没有运行；「实测」在本机做。

### 3.1 Higress 在现行设计里承担的事

| 承担的事 | 出处 | 不装以后（提议） |
|---|---|---|
| 转发：按模型名选上游、换密钥、多把密钥失败转移、回落 | ADR-015 D15.1、D15.5；需求文档 10.5 节 | 模型入口自己做；转发这一段实测过（§3.3） |
| 上游是别的协议时转成 OpenAI 的形状 | 同上 | 第一版不做（提议三） |
| 每分钟限流、用量统计、缓存 | ADR-015 D15.2 | 限流与统计由模型入口做；缓存不做 |
| 上游的密钥只有它持有 | 需求文档 10.5.1 节 | 转发用的密钥在模型入口一侧，照旧只以引用出现 |
| Agent 调平台能力的路：每租户的 MCP 门面托管在它上面 | ADR-016 D16.9、D16.10；ADR-010 D10.10 | 改走平台自己的网关（提议七）。这一条在里程碑 M1，还没有开始做 |
| 团队集群里现成的那一套 | ADR-015 §1 | 不动（提议二） |

2026-10-06 选它的理由说的是团队自己的那一个集群。现在变了三件事：

1. 按人的额度与认人都要在平台自己的入口上做。它的额度插件按每个调用方只有一个总数，没有周期，也不按模型折算（读到），做不了按人、按周期的积分；认人照 D15.6 本来就不交给它。
2. 产品要交付到客户现场，有两种形态、两个版本，还要能在一台机器上跑，而且只提供一套（S1-DEC-043 D5；单机版见 S1-DEC-041 D2、D3）。入口本来就得能不靠它工作。
3. 产品负责人点名参考的四个项目，都在自己的进程里直接连上游，没有另装模型网关；额度那一个，额度在厂商自己的服务端判。这是整理者读源码与文档的归纳（契约草案第 4.5 节）。

### 3.2 装它要装哪些东西

读到（上游主干的 Helm 图表，2026-11-26）：

- 总图表由两个子图表组成：核心与控制台。
- 核心里有网关（Deployment 或 DaemonSet）、控制器、可选的插件服务器、可选的 Redis；它自己的三种自定义资源，另加 Istio 的 EnvoyFilter；一批集群级的角色与绑定；一个入口类。
- 做限流与额度的插件要 Redis。团队现网那一套另有网关专用的 Redis 哨兵、专用的日志库与大盘（ADR-015 §1）。
- 插件在运行时从镜像仓库取；不通外网的现场要另架插件服务器，这一句是推断。

平台这一侧还要多写一层：把管理端里登记的上游、模型、密钥翻译成它的几种资源，写进集群，再对账。它的插件语义在小版本之间变过，多条限流规则从「命中第一条」改成了「全部叠加」。这一层要跟着它的版本走。

### 3.3 不经它的那条路：本机实测

做法：用 Kun 的业务网关同一个转发组件（YARP 2.2.0，.NET 10）写了一个最小的模型入口。它认调用方、读请求体里的逻辑模型名、查额度、换成上游的模型名与密钥、流式转发、边转边从响应里读用量、扣积分、记一条用量。积分按输入 token 乘 1、输出 token 乘 3 折算，是试验用的系数。后面接一个 OpenAI 兼容的替身上游。都在本机的回环地址上；认人、额度、路由表是进程里的替身。

| 量了什么 | 结果 |
|---|---|
| 首包多出来的延迟（300 对，直连替身上游对比经入口） | 中位 0.28 毫秒，95 分位 0.82 毫秒，最大 5.2 毫秒 |
| 分片是不是一片一片到（上游每 100 毫秒一片，30 片） | 经入口的间隔最小 100.0、中位 101.1、最大 101.7 毫秒，没有一片被攒起来 |
| 调用方读了 5 片就断开，上游多久停（20 次） | 20 次都停了；从断开到上游察觉最长 4.6 毫秒；上游正好只产出 5 片 |
| 这 20 次入口怎么记 | 都记成「中断」，用量标成「估的」，按已经转出去的片数算 |
| 用量与积分（一次流式、一次非流式） | 两次都从上游的响应里读到用量；扣的积分合计 324，与按系数算的一致 |
| 上游看到的是什么 | 上游的密钥与真实的模型名；调用方的凭据没有带过去；入口替调用方加上了「末尾带用量」 |
| 额度用完、凭据无效、模型不存在 | 分别回 429（带重置时间）、401、404，三种都没有打到上游 |
| 300 路并发的流（每路 40 片，每 50 毫秒一片） | 全部完整；每路最长的片间隔 99 分位 57 毫秒；入口常驻内存 117 到 129 MB |
| 1000 路并发的流（每路 40 片，每 100 毫秒一片） | 全部完整；每路最长的片间隔 99 分位 113 毫秒；入口常驻内存到 161 MB |
| 中间静默 130 秒的流，空闲超时设成 600 秒 | 走完，用量读到 |
| 同样的流，空闲超时不设（转发组件的缺省值） | 第 100 秒被掐断，调用方看到连接被重置。ADR-010 §9 记的 Kun 网关上的 100 秒就是它；入口是自己的服务，设一个值就行 |

没有测的：上游是替身，真实的推理服务与各家第三方 API 末尾那一帧用量长什么样、出错时回什么，没有对过；入口前面集群的入口那一层没有经过；入口多副本时，额度与限流的计数要放在共享的存储里，这里是进程里的替身；真的验平台签发的凭据要多花多少时间，没有量；上游走 TLS 与 HTTP/2、很慢的调用方、几个小时的长流，都没有测。

### 3.4 不装以后的账

平台自己要做的，都在模型入口里：转发（实测过）；一家多把密钥，失败的摘掉、冷却后放回；回落，上游不可用时按顺序换下一个，只在第一片出来以前换，能做成有序的多跳；每分钟限流，计数与额度放同一处；统一的错误体；用量看板。除转发以外都还没有做。

放弃的：原生协议的上游第一版接不了，这几家多数另有 OpenAI 兼容的入口，功能比原生的少一些，这一句凭已知、没有逐家核；它自带的 AI 大盘、语义缓存、内容安全这类插件；ADR-016 里已接受的 Agent 经它的 MCP 路由调平台能力那条路，要改写（提议七）。

### 3.5 结论（整理者的）

结论是不需要。照他第 3 句话里的条件，就不装（D24.4）。口子留在提议二：现场已经有模型网关，或者一定要某一家的原生协议时，把那个网关登记成一个上游。

### 3.6 推理服务一侧读到的

读到（GPUStack v2.3.1 的源码与文档，2026-11-26）：

- 推理接口是 OpenAI 兼容的，在 `/v1` 下；请求里的模型名是它的「路由」的名字。
- 流式的对话与补全，它的网关一律在末尾加上用量那一帧，调用方写了不要也会加、再自己剥掉。所以模型入口不要去写「不要用量」。
- 响应头里带它的请求编号，模型入口记进用量记录，两边对账用。
- 出错时的响应体不止一种，模型入口要统一成自己的。
- 开源版没有按人或按 key 的额度与限流。
- 管理接口与推理接口是同一个入口、同一种 key，靠 key 的范围分；能读模型的部署、实例、路由、工作节点，它按天汇总的用量有读的接口。它的健康端点不查依赖，不能当健康的依据。
- 它的推理入口就是它内置的一套 Higress 加它自己写的插件；用 Docker 装时内嵌在服务端的容器里。
- 装进 Kubernetes 时，它的图表缺省把 Higress 装成集群的入口控制器，同时带进它自己的 Operator、作业排队与节点特征发现；工作节点的 Pod 用主机网络；整件事它自己标着试验性，服务端只能一个副本。

这几条与 §3.3 里替身上游的行为对得上的有两处：末尾带用量的那一帧；流中途断开时没有这一帧。没有拿真实的推理服务对过。

## 4 备选方案与放弃原因（Alternatives）

下面是整理者的评估。

- **照原方案，Higress 必装**：模型入口照样要做，认人与积分都在它上面；再加一层把管理端的登记翻译成 Higress 配置的程序。每个客户现场都要装它与它的 Redis、要运维；翻译这一层跟着它的版本变；单机版装不了，另走一套。不选。
- **两条路并存**：现场装了 Higress 就让入口转给它，没装就入口直连上游。两条路要各测各的，等于两套。不选，只留提议二那个口子。这一种与 §1 那份看法里说的可选不是一回事。
- **换装另一种现成的模型代理**（ADR-015 §4 放弃过的那一类）：没有逐个评估。积分与认人本来就要在平台的入口上做，转发这一段实测不难，再加一个部件就多一份安装与运维。不选。
- **调用方直连上游**（契约草案问题 1 的选项乙）：上游的密钥要发到每个调用方，包括每个人的 Agent 运行时实例；平台拿不到用量，积分做不了。不选。

## 5 后果与代价（Consequences）

- 正面：所有形态、所有版本只有一条路；每个现场少装一套网关、它的 Redis 和那层翻译；积分、认人、计量都在平台一侧，单机版也一样。
- 负面：§3.4 列的几样要平台自己做，流式转发由平台自己扛；第一版接不了原生协议的上游；它自带的大盘与缓存没有了；Agent 调平台能力的路要重新设计（提议七）。转发只在本机回环上测过（§3.3）。
- 配套：契约草案照本文改写（提议）；ADR-015、ADR-010、ADR-016 与需求文档 7.16、10.5 节加标注；模型服务的任务 S1-MGW-001 至 S1-MGW-003 照本文改写或加补记。

## 6 对各阶段的影响

- **S1**：模型服务仍是规划。组件 `qian.model-gateway` 只有配置骨架，模型入口没有代码。任务怎么改见 S1-DEC-044。
- **M1**：Agent 调平台能力的路随 M1 的设计定（提议七）。

## 11 2026-11-27 第二张表的裁定

登记 §10 时冒出几件没有定的事，整理者收成第二张要产品负责人定的表，每条带建议。问的是「第二张表的 11 条，都按建议办吗？」，产品负责人 2026-11-27 答「都按建议」。与本文有关的是表上第 1 条与第 8 条。两张表的各条与定成什么，登记在 [S1-DEC-050](../../pm/tasks/S1-DEC-050.md)。

本节的标法：下面两条都是照表上的建议定的。引号里是表上的文字，不是他逐字说的；他的原话只有「都按建议」。

- **D24.10（已定）开放范围按租户、按角色两级，不做按人。** 表上第 1 条问的是模型「向哪些用户开放」的粒度，建议是「按租户、按角色两级；不做按人，要给某个人单开时把他放进一个角色。」另可选是「三级都做；只按租户。」D24.7 里「决定向哪些用户开放」照此落到两级。
- **D24.11（已定）积分系统关着的时候，积分照算、不拦。** 表上第 8 条问的是「积分系统关着的时候，积分照不照算。」建议是「照算、不拦，这样打开的时候数字是连续的。」另可选是「关着时不算。」D24.2 与原表第 15 条说的「关着时用量照记」照此补全：关着时用量照记，积分也照算，只是用完不拦。

整理时的读法，产品负责人没有逐句确认：

- 两级的规则怎么合起来判（一个模型同时写了租户名单与角色名单时取并集还是取交集），表上没有说，没有定。契约草案第 6.3 节的提议是取并集。
- 「角色」读作本仓库授权模型里的角色（ADR-006）。

§10.5 里其余几条照旧：调用方凭据由谁发、调用面的错误体要不要在规则里写例外，仍没有定；单机版里模型入口并不并进平台的进程、桌面端怎么拿凭据、设备上的本机模型，仍是延期；Agent 调平台能力的路，仍按提议推进。都还没有实现。
