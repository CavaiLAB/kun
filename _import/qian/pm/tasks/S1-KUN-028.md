## 背景

表外几件事：

- 停发的 8 个 Kun 包名（D23.9）里，Kun.Sandbox 与旧线的 Kun.Storage 在这一批。这两个归档可以提前、不占串行道，与在途批次并行，开工前对一次在途批次当时的 diff。两者都在 AOT 清单里，归档时冒烟宿主跟着改。`BannedSymbols.txt` 里旧线 `Kun.Storage.Abstractions.IFileStorage` 一条（连同它上面讲两个同名接口的注释）随归档处理，门禁样例 `bannedapi/LegacyDeclaration`、`LegacyStorage` 引用的就是旧线，跟着调整；`bannedapi/CurrentStorage` 引用新线，不动。
- Kun.Testing.Containers 是新包：要写档位与角色、带公共 API 清单、可打包。Qian.Testing.Containers 现在被 23 个测试项目引用、98 个源文件使用，遍布各域，换包名会扫到之前各批已经搬出去的测试。
- 撞名：Kun.Configuration 现在自己声明了 `Kun.Configuration.Abstractions` 命名空间，与新包 Kun.Configuration.Abstractions 撞名，要先定。
- 测试、工具随域：过渡目录 `_import/qian/tests/` 下的 Qian.Config.Tests、Qian.Config.Secrets.Tests、Qian.Files.Tests、Qian.Testing.Containers.IntegrationTests，`_import/qian/tools/Qian.Config.Tool`、`Qian.Secrets.Tool`；仓库根 `tests/` 下的 Kun.Configuration.Tests、Kun.Storage.Abstractions.Tests、Kun.Storage.Local.Tests、Kun.Storage.S3.Tests、Kun.Storage.Oss.Tests、Kun.Storage.Tests（随旧线归档）、Kun.Testing.Tests、Kun.Testing.EntityFrameworkCore.Tests、Kun.Sandbox.Tests（随 Kun.Sandbox 归档）。过渡目录里随这一批搬出的 .NET 项目共 14 个（7 个包、Qian.Testing.Containers、4 个测试、2 个工具）。门禁样例（`_import/qian/tests/gates/` 下）不随这一批搬，原地跟着换包名、保持能编过，整组归 B10（S1-KUN-029）；随归档调整的 `bannedapi/LegacyDeclaration`、`LegacyStorage` 照下面写的办。`_import/qian/tests/gates/test_config_namespaces.py` 按路径读 Qian.Config.Tool 的构建产物与 Qian.Testing.Containers 里的 Apollo 模拟，这两个搬目录时跟着改（脚本本身随 .NET 门禁自测归 B10）。

破坏性变更随 PR 记：本批每个 PR 的破坏性变更写进仓库根 `CHANGELOG.md` 的 `[Unreleased]`。理由是发版脚本 `scripts/release.sh` 第 4 段把 `[Unreleased]` 变成版本段，首个合并版的版本说明从这里来（S1-KUN-022）。

开工前要补的事：

- 蓝图 §1.2 的未核实事项落在这一域的：文件配额只读了结构，没有读完实现。合文件服务的后端端口之前读完。
- 档位按依赖图复核（仓库根 `scripts/check_deps.py`，项目文件里的 `KunTier` / `KunRole`）：
  - Qian.Config.Secrets（内核档）上一条规则 K 例外：→ Qian.Config.Abstractions（`Until="B9"`），密钥解析器实现的是配置契约里的 `ISecretResolver` 一组端口。这一批定这组端口的去处（放进内核档，或让密钥包改记平台档），例外随之去掉。
  - B7 若把 Qian.Gateway → Qian.Config.Abstractions 那条例外留到了这一批，一并去掉。
  - Qian.Config.Apollo 拆开：内核部分下沉 Kun.Configuration.Apollo（内核档，在 AOT 清单里），其余进平台档的 Kun.Configuration.Platform；平台部分还能不能留在 AOT 清单里，以 AOT 冒烟宿主为准。
- 对前端有没有影响：`plugins/` 下 qian.config、qian.config.apollo、qian.config.flags、qian.files 的清单里写着入口类型与程序集名，随包换；组件 id 与配置命名空间不变。`packages/qian-cli` 的 `test/marketplaces.test.mjs` 按路径 `packages/Qian.Config.Apollo/Qian.Config.Apollo.csproj` 求依赖闭包并写着包名，随搬目录改；`test/private-feed.e2e.mjs` 里有 `using Qian.Files;`（对包源上已发布的包编译，B4 的做法是不改它）；`README.md` 写着 Qian.Config.Apollo。改之前先看。
- 组件版本：`_import/qian/plugins/` 下 system 级组件（`policy.tier` 为 system、`runtime.form` 为 module 的非骨架组件，口径同 `scripts/sign-system-revisions.py` 的签名清单）的文件夹里任何文件一改，目录摘要就变：清单里的入口类型与程序集名随包换、README 改一个字都算。按 S1-DEC-037 的裁决（R167），要连带升该组件的版本，版本号继续唯一对应文件夹的内容。这一批碰到的 system 级组件：qian.config、qian.files。
  - 发布的 HTTP 契约会随换包名漂移：组件 Schema 的键取类型程序集限定名的哈希（`Qian.Capabilities.AspNetCore` 的 `AspNetCoreHttpContractSource`），发布契约三份，是 `plugins/qian.registry`、`plugins/qian.tenancy`、`plugins/qian.tenancy.signup` 下的 `contracts/http-v1.openapi.json`。在主干 691eabad 上按键反推，这一批要换的包里没有类型出现在这三份契约里，不会漂；换包名之后仍以 CI 上三处漂移测试（Qian.Registry.Tests、Qian.Sample.Crm.Tests、Qian.Tenancy.Signup.Tests）通过为准，漂了就重新生成并照上面升版本。
- 文档：两个归档会改到仓库根 `README.md` 的归档名单与 `docs/` 里写到旧线存储、沙箱与配置的页面；`docs/adr/kun/` 下的决策记录是历史文字，不改。
