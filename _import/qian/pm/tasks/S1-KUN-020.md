## 背景

ADR-023 D23.15 的阶段 2，细则在 D23.14 与 D23.12 第 1 点。导入之后两边还是各自构建，这一步并成一个解决方案、一条流水线，仍不改包名。依赖门禁现在按 `Qian.` 前缀和 `.Abstractions` 后缀判定，包名一改就会静默失效，所以门禁改显式档位表这件事排在任何改名之前。

估算是占位：蓝图写的是「数周量级，没有拆解估算」，阶段 2 结束后按域建任务再估。

2026-11-17 补（S1-DEC-038 D17）：目标仓库是 `CavaiLAB/kun`，本任务是迁移执行计划（该仓库的 `docs/migration-plan.md`）的 B3，在两个旧仓库归档之后开工。那时原 Qian 的树在 `_import/qian/` 下，并轨时把两边的构建基线并到仓库根。自托管 runner 要不要接到新仓库，开工前由产品负责人定；2026-11-18 定为先不接（S1-DEC-038 D21）。

## 验收

- [x] 一个解决方案；Qian 对 Kun 由包引用改为项目引用，`KunVersion` 单点钉版与 `Kun.*` 包源映射作废
- [x] 中央包版本：两边同名不同版的 19 个包取高的一边；Microsoft.OpenApi、JsonSchema.Net、xunit.v3 三处跨主版本实测；测试运行器统一到 Microsoft.Testing.Platform，Kun 工作流里的过滤与覆盖率参数重写
- [x] 依赖门禁改为显式的「包 → 档位与角色」表，写在项目属性里，带自测：内核档不引用平台档；平台档只依赖内核档与别的平台组件的契约包；保留「Kun.Core 零依赖」检查（D23.7、D23.14 第 1 点）
- [x] 公共 API 门禁取 Qian 的做法：可打包的项目必须带两份清单，缺文件即报错；分析器升到 5.6.0
- [x] AOT：缺省不声明，逐项目显式打开；开关移到晚于项目文件求值的位置；以宿主原生发布并运行的冒烟为准；Kun 四份 AOT 模块清单并成一份
- [x] 禁用符号与数据层分析器的作用域收到平台档与宿主，不拦被禁类型自己的定义
- [x] CI 全部跑在 GitHub 托管 runner 上；自托管 runner 先不接（S1-DEC-038 D21），基准与对象存储实测先不接、需要时在本机跑；Kun 的格式门禁先不对并入的 Qian 代码打开
- [x] 退出标准：两边全部测试与门禁在一条流水线上通过，仍不改包名
- [ ] 结束时按域建阶段 3 的批次任务并估算，挂到 S1-KUN-021 之下
