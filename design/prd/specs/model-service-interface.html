#1 一页看完

#1.1 草案的要点

  1. 接口分三个面。调用面给调用方用：一组 OpenAI 兼容的 HTTP 端点，调用方只认平台的地址、平台发的凭据和逻辑模型名。接入面给模型后端的适配用：一组 .NET 接口，加清单里的一条声明。管理面给管理端用：一组 HTTP 接口，加权限点。
  2. 两种形态的差别只落在接入面：装哪个适配，登记哪些上游。调用面与管理面两种形态一样。
  3. 适配是代码，上游是数据。接一类新的模型后端，写一个适配组件；同一类后端再加一个地址，只是在管理端里登记一个上游，前提是这个地址已经在出网名单里。
  4. 适配不转发模型请求。它回答四件事：有哪些模型，各自能做什么，是否健康，怎么调。「怎么调」是一份描述，由模型入口读。转发由平台自己的模型入口做，平台不装模型网关（ADR-024 D24.4；2026-11-27 起整理时读作条件得到确认，见 ADR-024 §10.3）。自己管推理的后端多实现一个可选的接口：部署、扩缩与下线。
  5. 调用面后面就是模型入口，Kun 模型组件里的一个独立服务：验平台发的凭据，定租户与主体，查权限与积分，按逻辑模型名选上游，换成上游的模型名与密钥，流式转发，边转边记用量。租户、额度、计量都在平台一侧，上游不知道租户。所有形态、所有版本只有这一条路：调用方 → 模型入口 → 上游（已定：整个平台只有一个 Kun 模型服务，ADR-024 D24.6）。模型入口是 Kun 模型组件里的独立服务，不放在 Kun 的网关上（已定，问题 9）。
  6. 模型的能力用一份机器可读的描述来声明：类型、输入输出的模态、上下文长度、几个能力开关。答不上来的写「不知道」，与「不支持」分开记。同一份描述出现在三处：适配的返回，管理端的目录，调用面的模型列表。
  7. 管理面的每个操作对应一个权限点，判定走 Kun 的鉴权，模型服务不自己判权限（S1-DEC-043 D7；那里的读法 2026-11-27 认可）。「谁能调模型」也是一个权限点，在签发调用方凭据时判。
  8. 额度的单位是积分，积分系统按租户开关，关着时用量照记、积分照算、不拦；周期可选日、周、月，缺省每周一重置；按模型组分桶，用完就拒，不自动换模型，用户可以自己换另一个已获授权且有额度的模型（已定，ADR-024 D24.1 至 D24.3、§10）。折算与谁设额度见第 6.5 节。
  9. 平台管理员统一配模型：上游地址、密钥、模型映射和路由都由平台管；每个模型向哪些用户开放，由他定，按租户、按角色两级，不做按人（已定，ADR-024 D24.10）。用户在可用的模型里选，Web、桌面和 API 都由服务端校验（已定，ADR-024 D24.7）。普通用户、租户管理员和应用都不能自带上游密钥、自填地址或改路由；发给人和应用的凭据只用于调用平台（已定，D24.8）。

#1.2 与现行决策的出入

详见第 10 节。2026-11-26 起草时列了六条。第二条，模型请求从哪里进，随 ADR-024 不再是出入；第一条里的边界，2026-11-27 放开了；第六条，2026-11-27 有了说法。另有一条是这一天新加的。下面照现在的状态写。

  • 多出来两样：平台自己转发的模型入口，调用方凭据的签发。ADR-015 的 D15.3 写的是本仓库一侧只做三件事，D15.5 的前半句是不自写模型代理层；2026-11-27 原表第 5 条照建议定了，这两条随之放开，不再是出入。调用方凭据，长期的密钥只有应用级的，绑人的只有代人签发的短期凭据（第 6.2 节）；身份服务现在没有应用级的固定密钥，也没有代人签发，这两样是依赖，任务见第 10.4 节。
  • 适配从「一个服务，对接一种推理服务」改成一个注册表上的多个适配组件。原来的任务是照一种推理服务写的，2026-11-27 照此改写与拆分，见第 10.3、10.4 节。
  • 两份能力契约，ADR-015 写的是直接用下游的，本仓库里没有这两个文件。草案给了自己的形状。
  • 调用面的错误体跟公开协议走，不是本仓库统一的错误模型。管理面仍然用统一的错误模型。
  • 已定的「统一由管理端管理」，与需求文档 7.16 节验收里「配置变更全部经部署仓库评审」之间的说法，2026-11-27 有了：管理端里改的配置分两类，不改流量出口的点了就生效并留审计，改出口的经评审（问题 6，原表第 8 条照建议）。7.16 节那一条说的是模型网关的配置，已加 ADR-024 的标注。

#2.2 读法

2026-11-27 起，下面两组都不再是待确认的：登记 D5 与 D7 时的读法，照成批的甲批认可；登记 2026-11-26 那几句时的两条，照原表第 7、15 条转成已定。

下面是登记 D5 与 D7 时整理者的读法，产品负责人当时没有逐句确认。出处是 S1-DEC-043 的「读法」一节。

  • 第二种形态是不带模型推理、通过 API 接第三方的模型服务。
  • 两种形态（带不带模型推理）、企业版与单机版（集群还是一台服务器）、多租户与单租户，是三条不同的线。
  • 「标准的接口，只提供一套」：模型服务这一块留一套标准的接口，后面接自己的推理服务还是接第三方的 API，都接在这套接口上，上面的产品不用跟着改。
  • 「尽量使用插件的形式」：模型推理的接入、形态之间与版本之间的差别，尽量做成本仓库的组件。
  • 「统一由管理端进行管理」：两种形态、两个版本用同一个管理端，模型服务也在里面管。管理端在匠心一侧。
  • D7 的读法：平台上的系统判权限只问 Kun，不各做一套。

登记 2026-11-26 那几句时的读法，出处是 S1-DEC-044 的「读法」一节与 ADR-024 §2.3：

  • 他说的「可以给每个用户固定的额度」，读作调用方的凭据落到人和应用头上，因为按人给额度，就得认得出人。
  • 「可以选择是否启用积分系统」读作一个开关，按租户设，单租户版就是整个部署一个；关着时用量照记，不拦。

本文照这些写。

#2.3 没有定的与延期的

#4 成熟做法的归纳

写草案之前读了一批公开资料：公开协议自己的文档，几种自己管推理的服务器与推理管理平台，几种模型网关与聚合服务，几家模型提供方的接口文档。照本仓库的约定，这里不写项目和产品的名字，只写归纳。

#4.1 兼容面通常覆盖什么

  • 公开协议自己的端点族很多：对话，一个较新的统一对话接口，旧的文本补全，嵌入，模型列表，语音，图片，内容审核，批处理，文件，实时语音。协议的提供方现在推荐新项目用那个较新的接口，对话端点仍受支持，没有下线日期；助手一族已经停用，微调与另外几样在陆续停。
  • 读到的十种实现里，对话与嵌入每一种都做。模型列表在自己管推理的一侧每一种都有。旧的文本补全多数还留着。
  • 较新的统一对话接口多数已经带上，但有几种只做了无状态的那一半。
  • 第二种消息协议的端点，读到的实现多数也带了。
  • 带状态的那几族（文件、批处理、助手与会话）在自己管推理的一侧基本不做，网关一侧做的也只是一部分。内容审核在自己管推理的一侧没有读到哪一种做。语音与图片有的做有的不做。
  • 重排不在公开协议里。业界通行的形状是 POST /v1/rerank：请求带 model、query、documents、top_n，响应是 results[]，每项有 index 与 relevance_score，用量只报一个总数。自己管推理的实现除一种以外都有，路径也一致；个别实现的路径或字段名不同。
  • 流式用服务器发送事件：每帧一行 data: 加一个 JSON，以 data: [DONE] 结束。要用量得在请求里显式要，这时结束前多出一帧：没有内容，只带总用量；流断了可能收不到它。流到一半出错，协议没有成文的规定，通行的做法是发一帧带 error 的数据，协议方自己的 SDK 认得这种帧。
  • 工具调用与结构化输出的请求字段是通用的。自己管推理的后端要靠启动参数或聊天模板才支持，并行的工具调用各家不齐。推理过程的文本在响应里叫什么，各家也不一致。
  • 图片输入走对话端点里的内容分段，给地址或内嵌数据都行。音频与文件输入支持得少。
  • 错误是一个 error 对象，带 message、type、param、code。协议里 code 是字符串，有几种实现给的是数字。限流有一组响应头报余量，加 Retry-After。429 分两种：限流，过一会儿可以重试；额度用尽，重试没有用。
  • 网关一侧的状态码不统一：额度用尽有回 402、412、429 的，限流多数回 429，个别缺省回 503。调用方不认识的请求字段，有的实现忽略，有的回 400。

#4.2 模型能力怎么声明

  • 没有统一的标准。公开协议自己的模型列表几乎不描述能力，只有标识、归属和时间。
  • 描述得全的几份目录，字段都落在七组里：类型，输入输出的模态，能力开关，限制，支持的请求参数，成本，治理（区域、是否留数据、弃用日期）。
  • 同一个模型换一个提供方，或者换一组启动参数，能力就变。所以描述的对象是「某个后端上的这个模型」，不是抽象的模型。
  • 自己管推理的后端，能力来自模型文件的元数据、聊天模板和启动参数，能自动得到的只有类别和少数几个开关。第三方的 API 先看提供方的模型列表，不够再靠人维护的目录。最大批量、图片数量上限、是否用于训练、自己推理的成本，各家都拿不到，只能人填。
  • 「没探测到」与「不支持」要分开。有的目录允许能力为空，有的类别里专门有「未知」一项。
  • 同一个词各家意思不同。同样叫「最大 token」，有的指最大输出，有的指上下文，有的指嵌入的最大输入。
  • 模型的类型在增加。有的文档明确要求客户端容忍不认识的取值。
  • Agent 运行时配置一个自定义的模型时，通常要这几项：上下文长度、最大输出、是否支持推理、输入模态、单价。不给就用猜的缺省值。

模型网关把这两类统一起来，做法大同小异：

  • 上游的凭据只写引用，转发时由网关带上。
  • 逻辑名到真实模型名的映射放在网关。失败转移、重试与冷却也在网关。
  • 按调用方做 token 限流与配额，调用方有的叫消费者，有的叫虚拟密钥、团队。这要一个共享的计数存储。
  • 用量从响应里取，写进日志或指标。
  • 有把网关分成两层的：前一层管认证、路由与全局限流，后一层管自己的推理与实例的挑选。

另外三点与第 11 节的问题有关：

  • 只接第三方的 API 时要不要过一层自己的网关，公开资料两边的理由都有。支持的理由：不过网关，重试、熔断、失败转移就散在每个客户端里，成本只能事后靠遥测去分摊。反对的理由：多一个单点和一份运维，多一跳的延迟，流式与带状态的接口容易受影响。也有把路由、限流、计量做成库嵌在应用里的折中，代价是多个实例之间要另找地方共享计数，改一次逻辑要逐个应用发版。
  • 记用量与拦配额是两个部件。拦是事后扣：响应完了才知道用了多少，流不会被中途打断，并发时会略超。流中断时可能拿不到用量。计数存储不可用时，文档里写明了的几种实现缺省都不拒绝：或者放行，或者退回各实例自己计数。
  • 租户自带密钥有两种做法：密钥存在网关一侧，按租户引用；或者每次请求由调用方带上。前一种换密钥不动调用方，代价是网关成了密钥的保管方。还有两个要定的细节：自带的密钥失败时回不回落到平台的密钥，自带密钥的花费算不算进配额。照 2026-11-27 的裁定，平台不做租户自带（ADR-024 D24.8）。

#4.4 草案从中取了什么

  • 兼容面只承诺一小组端点，分档列出，其余明确不做。各家不一致的三处，草案各定一种：error.code 用字符串；流到一半出错，发一帧带 error 的数据再断开；不认识的请求字段原样转给上游。
  • 能力描述的对象是逻辑模型，它背后是某个上游上的某个模型。能力开关分三种取值：支持、不支持、不知道。字段名避开有歧义的词。类型的取值可以增加，调用方要容忍不认识的。
  • 适配必须实现的方法，两类后端都答得上来。部署与扩缩做成可选的接口，只有自己管推理的后端实现。健康分上游与模型两层。发现的结果带一个标记：这份列表全不全。
  • 调用入口与数据面原来分成两层：入口认人、定租户、管配额；数据面管路由、失败转移与限流。2026-11-27 照 ADR-024 合成一层，模型入口全做。
  • 记用量与拦配额分开设计。用量记录写明来源：上游报的，估的，还是没拿到。

#4.5 产品负责人点名参考的几个项目

2026-11-26 产品负责人点了四个开源项目的名字（问题 4）。前三个跟在「可以接入更多的模型」前面，第四个跟在「可以给每个用户固定的额度」前面，下面分开归纳。照本仓库的约定不写名字。整理时读了它们的源码与文档，下面是整理者的归纳，没有逐条核。

接入的三个：

  • 三层都是数据：少数几种协议的适配；供应商的定义，即地址、鉴权、请求头、默认模型；模型目录，即上下文、价格、能力。
  • 模型多，靠的是这几样：加一家只是加一条数据；从上游的模型列表实时拉；用公共的模型登记表补元数据，缺的记「未知」，不记「否」；把聚合网关当作一个上游。
  • 凭据池与冷却、跨上游回落、同一个会话粘住同一份凭据与模型以保住提示缓存、给小任务单设一个便宜模型的槽位。
  • 都在自己的进程里直接连上游，没有另装模型网关。
  • 都没有按调用方或租户的额度、花费上限与计费归属。凭据都属于本机的那一个人，大量用个人的订阅登录。

额度的那一个：

  • 额度是厂商的商业套餐，在厂商的服务端判。单位是积分，按 token 乘模型的系数折算；分一个滚动窗口与每周两档；团队版每个席位单独限额。
  • 客户端只显示、不拦：显示剩余的百分比与重置时间，单个桶剩一成时提醒一次。用完时服务端回专门的错误码，耗尽、并发、限流分开，带重置的时刻。
  • 调用方只拿短期的 token，长期的密钥留在服务端。管理员一侧，即分配成员、按人看用量、设上限，不在它的仓库里；自带密钥时不设额度。

他点了名，草案照问题 4 选项甲的影响一栏，对着它们核了一遍。本文已有、与之同向的：能力分三种取值，不认识的记「不知道」（第 7.3 节）；用途槽位（第 6.3 节）；额度用积分，限流与额度用尽的错误码分开（第 6.4、6.5 节）；上游的密钥留在平台一侧，调用方只拿平台发的凭据，绑人的只有短期的（第 6.2 节）。另有四样要加的，本文没有展开，2026-11-27 照成批的丙批「接入更多模型的做法」按提议推进。照现在的写法，一是供应商模板随平台发、带版本，管理端里加一家是选模板、填密钥、勾模型，没有模板的走「自定义（OpenAI 兼容）」；二是模型目录从模板带的、向上游拉的、手填的三处来，能力与价格随平台带一份快照；三是一家多把密钥，失败的摘掉、冷却后放回；四是用途别名，即默认、快速、看图、嵌入。这四样整理时列给过他；当时第三样写的是用模型网关现成的，现在由模型入口做。不学的一条：每个人挂自己的密钥与订阅。2026-11-27 定了：普通用户、租户管理员和应用都不能自带上游密钥（ADR-024 D24.8），托管的工作区里也不开放个人自带的密钥（原表第 16 条照建议）。

#5 总体形状

图里的每一块都是规划，还没有实现。实线是模型请求走的路，虚线是控制与统计。模型入口是 Kun 模型组件里的一个独立服务，现场已有的模型网关登记成一个上游，都已定；推理服务放在平台的集群外面是首选（ADR-024 §10.3）。所有形态、所有版本只有这一条路：调用方 → 模型入口 → 上游（已定，ADR-024 D24.6）。

#5.2 一次调用怎么走

下面照模型入口是一个独立服务写（已定，原表第 11 条）。

  1. 调用方带着凭据和逻辑模型名，请求模型入口。
  2. 入口验凭据，得到租户与主体。调用方自带的身份类请求头一律丢弃。
  3. 入口查目录：这个逻辑模型在不在这个主体的开放范围里，模型有没有上线。用户选哪个模型，由请求里的 model 说；选得对不对由入口在服务端校验，Web、桌面和 API 一样（已定，ADR-024 D24.7）。
  4. 积分系统开着时，入口查这个主体在这个模型组上本周期还剩多少积分；用完了照第 6.4 节回绝，不自动换模型（已定，原表第 14 条）。每分钟的限流也在这里（第 6.5 节）。
  5. 入口按逻辑模型名选上游，把模型名换成上游认的名字，带上上游的密钥；流式的请求替调用方要上用量。请求体的其余部分不动。
  6. 入口转发。第一个目标不可用、还没有出第一片时，按顺序换下一个。这是同一个逻辑模型背后换一个目标，不是替用户换成别的模型；额度用完不在这一步换（提议）。
  7. 响应原样流回调用方，入口边转边读用量。
  8. 结束时入口扣积分，写一条用量记录（第 8.3 节），投影成计量事件。

#6.2 认证与调用方凭据

形状。 Authorization: Bearer <凭据>。对调用方来说，凭据是一段不透明的字符串。

由谁发。 平台的身份这一套发（提议；由身份服务发，还是由模型组件自己发一种专用的密钥，没有定，见第 12 节）。只用于调用平台，是已定的（ADR-024 D24.8）；受众只限平台的服务，第一版只登记模型服务这一个受众（提议）。模型服务不另建一套账号（提议）。落到人和应用头上是原表第 7 条照建议定的。按调用方分三种来路：

调用方凭据怎么来现状
平台上的服务与应用用自己的服务身份取短期令牌，到期自己换签发已有；把模型服务登记成一个受众是规划
只能填一把固定密钥的客户端：现成的 SDK、外部系统一把有期限、可吊销的密钥，绑着一个登记过的应用。不发绑人的长期密钥规划。对应 ADR-010 D10.8 里应用级的 API Key；D10.8 废弃了用户级的密钥
代人：托管的 Agent 运行时实例启动实例的服务代登录的人申请一把，申请时要出示这个人当前有效的会话。凭据绑人，绑实例，期限不超过这个会话；实例回收或会话结束就吊销规划。身份服务现在没有代人签发

绑人的凭据只有短期的这一种（已定，原表第 7 条）。桌面端同理：由登录了的桌面应用替这个人取短期的凭据，不落长期的密钥；这一段在匠心一侧，是提议。桌面端怎么拿到凭据延期，前置条件是匠心桌面端的对接设计（成批的丁批）。ADR-016 第 10 节为确认卡提过同一种调法，由有专门权限的服务主体声明这次是代某人，那里也是提议。

凭据里带什么。 入口验完凭据，得到下面这些，字段与冻结的服务间令牌契约同名同义，不另造一套：

字段意思
tenant_id租户。为空是平台级的主体
sub，principal_kind主体和它的种类：人、服务、智能体
membership_id人在这个租户里的成员身份
project_id可空，只透传
session_id会话，或这把凭据自己的编号。吊销按它
act代人签发时，记下代办的是谁。契约里留了这个位置，现在不签发

到期时间过期即 401

调用方不能自报身份。 请求头与请求体里的租户、用户标识一律不当作身份。公开协议里给调用方标注终端用户的字段（如 user），只算调用方自己的标注。

谁能拿到凭据。 「能调模型」是一个权限点（第 8.2 节），签发时由 Kun 的鉴权判定。每次调用入口只认凭据，不再问一遍权限。权限变了，入口靠身份修订号发现，重新判一次；不再有这个权限的，凭据失效。

入口放在哪。 模型入口是 Kun 模型组件里的一个独立服务（已定，原表第 11 条），验凭据、查开放范围、权限与积分、选上游、转发、记用量都在它里面。现行需求文档里没有这个入口：所有客户端只对接模型网关，凭据是模型网关上的消费者 key，模型流量不经 Kun 的网关（ADR-010 D10.1、D10.10，需求文档 10.5.1 节）；照 ADR-024 平台不装模型网关，这几处加了标注。2026-11-26 提问时列过两种放法：放在 Kun 的网关上作为一组模型路由，或者由模型网关自己验；都没有选。几点说明：

  • 对调用方没有差别：都是平台给的一个地址，一把平台发的凭据。
  • 独立的服务不占 Kun 网关的容量，长连接的空闲超时自己设。本机实测，不设时转发组件在第 100 秒掐断，设成 600 秒走得完（ADR-024 §3.3）。Kun 网关的宿主现在配不了这一项（ADR-010 §9），放在网关上要先补。
  • ADR-010 D10.11（网关不解析 JSON 请求体做鉴权）只管 Kun 的网关，不管模型入口：2026-11-27 成批的丙批里的一条，按提议推进。模型入口读请求体里的 model，用来选上游，也用来校验用户选的模型在不在他的开放范围里。
  • S1-DEC-038 的 Q8 针对设备上的 Agent 提过同一件事，当时推荐经模型网关、备选经 Kun 的网关，调用路径没有裁定。照 ADR-024，推荐的那条路不在了。设备怎么调平台的模型延期，前置条件是设备一侧用什么运行时定下来（成批的丁批）；整理时读作定的时候照统一模型服务的裁定办（第 2.3 节）。

#6.3 逻辑模型名的解析

  • 名字的形状：小写字母开头，只用小写字母、数字与连字符，不超过 64 个字符。调用面只认逻辑模型名：不认后端的模型名，不认带提供方前缀的名字，不做模糊匹配。
  • 目录只有平台一层，由平台管理员管：上游地址、密钥、模型映射和路由都由平台管理（已定，ADR-024 D24.7）。租户、普通用户和应用都不能改路由（已定，D24.8）。ADR-015 D15.10 的「产品默认 + 租户覆盖」与配坏了回落，2026-11-27 起不再成立；2026-11-26 的版本里写的租户层，随之去掉。
  • 解析与选上游都在入口做。入口读请求体里的 model，按目录选好上游以后把它换成上游认的模型名，请求体别的部分不动。响应里的 model 字段要不要换回逻辑模型名，入口做得到，没有定，见第 12 节。
  • 每个条目带开放范围，即这个模型向哪些用户开放，由平台管理员定（已定，D24.7）。粒度是按租户、按角色两级，不做按人；要给某个人单开时，把他放进一个角色（已定，第二张表第 1 条照建议，ADR-024 D24.10）。草案提议条目上记一组规则，可以写全部、一份租户名单或几个角色，判定时取并集；取并集还是取交集，第二张表没有说，没有定。看不见与不存在回同一个错误，调用方分不出来，与组件模型规格里的「不可区分原则」一致。凭据还可以把可用的模型再收窄。
  • 用户在可用的模型里选（已定，D24.7）。GET /v1/models 只列这个调用方可用的模型（第 6.7 节）；请求里写的 model 不在他可用的范围里，入口回 404，与看不见是同一个错误。Web、桌面和 API 都走这一处校验，不靠客户端。一个模型组的积分用完，入口不替他换模型；他可以自己选另一个已获授权且有额度的模型再调（已定，D24.9）。
  • 一个逻辑模型指到一串目标，每个目标是「哪个上游上的哪个模型」，按顺序用：前一个不可用才用后一个。流式的请求只在第一片出来以前换。一串目标都不可用，回 503。这是同一个逻辑模型背后的失败转移，由平台管理员配，不算替用户换模型（提议）。
  • 逻辑模型名是稳定的。换它背后的模型不用通知调用方，但能力变窄的变更（如上下文变短）要在管理端里提示，并发事件。
  • 用途槽位与 Agent 表面里的模型别名，是平台内部的上一层：一张「槽位到逻辑模型名」的表，只有平台一层。调用面不认它们。
  • 现有文档里嵌入的缺省名有两种写法。逻辑模型名的清单随实现任务定一份，本草案不定名字。

#6.4 错误

调用面的错误体跟公开协议走，好让现成的 SDK 和 Agent 运行时照常分支：

{ "error": { "message": "…", "type": "…", "param": null, "code": "…" } }

  • 上游报的错分三类处理。请求本身的错原样转回：上游的 400、413、422，连同它的错误体；上游把 code 给成数字的，转成字符串。平台与上游之间的错不交给调用方：上游拒绝平台的凭据（401、403）、上游不认平台配的模型名（404），先换下一个目标；都不行，归成 502 并告警，因为调用方换自己的凭据没有用。上游的 5xx 同样先换下一个目标，都不行归成 502，不带上游的原文。
  • 上游对平台的账号限流（429）时，先换下一个目标；都不行，回 429 rate_limit_exceeded，带 Retry-After。上游说平台的账号额度用尽时，先换下一个目标；都不行，回 503 model_unavailable 并告警。
  • 「积分用尽」要一个新的平台错误码。需求文档 10.5.11 节用过 MODEL_BUDGET_EXCEEDED，错误码目录里还没有，登记随实现任务。
  • 积分用尽时带上重置的时间，调用方可以等到重置。重置时间放在响应头里，因为平台自己的信息只出现在响应头与模型列表的扩展对象里（第 6.8 节）。本机实测时，入口把重置时间放在错误体里，并带了 Retry-After；正式的写法随实现任务定。
  • 用完以后拒绝，按模型组分桶，不自动换模型（已定，原表第 14 条）。
  • 限流与积分用尽必须分得开：前者过一会儿就好，后者要等到重置，重试没有用。Agent 运行时靠这个区别决定是退避还是停下。两者都回 429、靠 code 区分，是公开协议自己的做法；读到的网关在这一处并不统一。

#6.5 限流与额度的语义

额度的单位是积分，积分系统可以选择启用或不启用，周期可以选择（ADR-024 D24.1 至 D24.3）。2026-11-27 原表第 14、15 条照建议定了下面写明「已定」的几项；没有写的是提议。

三层都在模型入口：

层管什么超了回什么
防打爆每个凭据、每个来源地址的请求数429，rate_limit_exceeded
每分钟的限流每个桶每分钟的请求数与 token 数429，rate_limit_exceeded
积分每个主体在一个周期里、每个模型组上用了多少积分429，insufficient_quota，带重置时间
  • 积分的折算已定：按 token 乘模型的系数算，输入输出分开，自建的模型也计（原表第 15 条）。系数由平台管理员定，原始 token 照记，系数先全填 1 也能跑，这几句是提议。本机实测的入口就是这样算的（ADR-024 §3.3）。
  • 额度的分配已定：租户管理员设每人的默认额度，多租户版由平台给租户封顶，应用单独一桶（原表第 15 条）；他的原话是「租户管理员可以按第 15 条分配额度。」个别人单独调，是提议。
  • 周期已定：可选日、周、月，缺省每周一重置（原表第 15 条）。
  • 积分系统按租户开关，关着时用量照记、不拦（已定，原表第 15 条照建议；他的原话里有「积分按租户开关，关闭时仍记录用量。」）。单租户版只有一个租户，就是整个部署一个开关。关着时积分照算，只是不拦，这样打开的时候数字是连续的（已定，第二张表第 8 条照建议，ADR-024 D24.11）。
  • 按模型组分桶：一个模型组的积分用完，不影响别的组；用完就拒，不自动换模型，用户可以自己选另一个已获授权且有额度的模型（已定，原表第 14 条与 ADR-024 D24.9）。模型组怎么分，由平台管理员在目录里定，是提议。
  • 剩余的积分在 DSH 里显示，剩一成时提醒（已定，原表第 15 条）。显示与提醒在匠心一侧；平台给的是剩余与重置时间，接口见第 8.1 节（提议）。
  • 限流的桶由入口从验过的凭据里取，不读调用方的请求头；现行需求文档里的 x-qian-consumer 不再需要。缺省一个租户一个桶，可以再按凭据分。
  • 带 Retry-After 的只有限流这两层。积分用尽带重置时间，写法见第 6.4 节。
  • token 的限流与积分都是事后扣：一次请求完了才知道用了多少，所以并发时会略超。这是通行的做法，不当作缺陷。
  • 入口多副本时，计数要放在共享的存储里，这一点没有实测过。计数存储不可用时放行并告警，沿用需求文档 10.5.3 节的口径；接第三方时放行是要花钱的，所以这一条做成配置项。
  • 每分钟的限流要做（已定，原表第 14 条）。

#6.6 流式

  • 服务器发送事件。每帧一行 data: 加一个 JSON，以 data: [DONE] 结束。入口不缓冲；本机实测，分片一片一片到，没有被攒起来（ADR-024 §3.3）。
  • 用量：不管调用方要没要，平台都要拿到这一次的用量。调用方没带「把用量放进流里」的请求选项时，由入口补上，实测做了。多出来的那一帧只带用量，调用方没要就不下发；这一步要在入口里做，实测时没有专门验。有的推理服务不管调用方怎么写，都在末尾带上这一帧（ADR-024 §3.6）。
  • 流到一半出错：状态行已经发出去了，改不了。这时发一帧带 error 对象的数据，然后断开，不发 [DONE]。调用方要把「没等到 [DONE]」当成失败。
  • 调用方断开，入口就取消对上游的请求。本机实测 20 次都停了，从断开到上游察觉最长 4.6 毫秒。已经产生的用量照上游报的记；上游没报的，按已经转出去的量估，用量记录里标成估的。
  • 超时：对话类单次请求的上限照需求文档 10.5.9 节，是 600 秒。一路上每一跳的空闲超时都要够得着它。模型入口自己设一个值就行：实测不设时第 100 秒被掐断，设成 600 秒走得完。
  • 工具调用在流里的增量原样透传。

#6.8 兼容的承诺

  1. 调用面跟公开协议走。平台不要求调用方带任何私有的请求字段。
  2. 平台自己的信息只出现在两处：响应头，模型列表里的那个扩展对象。
  3. 端点与字段只做加法。要做破坏性的变更，换一个路径前缀。
  4. 换形态、换上游，调用面不变；现场把一个模型网关登记成上游，调用面也不变。这一条是「只提供一套」落到调用面上的意思，也是他 2026-11-27 写的「增加上游、模型或服务副本，都不另设面向用户的入口。」

#7 接入面

#7.1 注册表 seam 与清单里的声明

需求文档里的扩展点 qian.model-gateway.provider/v1 是清单 v1 的写法。照组件模型 v2，模型后端的适配是连接器，连接器一律走注册表 seam（规格 3.6、6.1 节，R38），与身份连接器同一个写法。v2 里「扩展点」这个词指的是事件定义，这里不用它。两个名字（2026-11-26 的版本里另有数据面绑定的注册表，见第 7.5 节）：

  • 服务键 ModelGateway：模型服务本身，单例 seam，由模型组件提供。
  • 注册表 ModelGateway.Providers：适配按名字登记，清单里写 ModelGateway.Providers:<名字>。

Definition 包叫 Kun.ModelGateway.Abstractions，平台档的契约包。

一个适配组件的清单，以 OpenAI 兼容的通用适配为例（示意，组件编号与版本随实现任务定）：

{
  "$schema": "https://qian.dev/schemas/plugin/v2",
  "id": "qian.model-gateway.provider.openai-compatible",
  "version": "1.0.0",
  "description": "模型后端的适配：对接 OpenAI 兼容的模型后端，回答有哪些模型、是否健康、怎么调",
  "author": { "name": "Qian" },
  "license": "MIT",
  "interface": { "displayName": "OpenAI 兼容的通用适配", "category": "platform" },
  "runtime": {
    "form": "module",
    "entry": "Kun.ModelGateway.Provider.OpenAiCompatible.OpenAiCompatibleProviderComponent, Kun.ModelGateway.Provider.OpenAiCompatible",
    "configSchema": "./schemas/config.schema.json"
  },
  "inject": ["Config", "ModelGateway"],
  "provides": ["ModelGateway.Providers:openai-compatible"],
  "policy": {
    "tier": "system",
    "sandbox": "none",
    "authentication": "ON_INSTALL",
    "egress": ["api.example.com:443"],
    "permissions": {
      "secrets": [
        { "name": "model-gateway/upstreams/*", "scope": "platform" }
      ]
    }
  },
  "scopes": ["global"]
}
  • provides 里的名字是适配的注册名，一个组件一个名字。同一个适配带多个上游，靠管理端里登记多条上游，不靠把组件挂多次。
  • policy.egress[] 列出这个适配可以连的外部主机，模型入口出网的名单与它保持一致：上游的地址必须落在这份名单里，模型入口转发时只连名单里的主机；多连一个主机是部署层的变更。
  • policy.permissions.secrets[] 声明适配可以解析的密钥范围，只有平台的；scopes 只写 global，适配只装在全局。上游只归平台（已定，ADR-024 D24.8）。声明与宿主的审批取交集，这是已有的规则。
  • 适配只对 system 与 official 两档开放，因为它是进共享进程的代码（规格 11.1 节）。要接一个新的模型后端，由平台管理员走「OpenAI 兼容」这个通用适配登记上游，不用写代码；租户不能自己登记（已定，D24.8）。

能力的声明。

  • 必填的只有类型。对话类要填上下文长度才能上线，嵌入类要填维数。别的都可以是「不知道」。
  • 能力有三个来源：适配发现的，适配自带的静态表，管理端的人填的。目录里存合并以后的结果，人填的优先，并记下每一项的来源。
  • 类型的取值可以增加，调用方要容忍不认识的取值。
  • 字段名避开「最大 token」这类各家意思不同的词：上下文长度与最大输出分成两个字段。

#8 管理面

#9.3 三条线

带不带推理，多租户还是单租户，集群还是一台服务器，读作三条不同的线（S1-DEC-043 D5 的读法，2026-11-27 认可）。哪几种组合要交付，2026-11-27 定了两套：企业版，集群、多租户、带推理；单机版，一台服务器、单租户、不带推理；别的组合先不承诺（原表第 19 条照建议）。他写的是「企业版和单机版共用上述模型服务。」对模型服务有影响的原来有一处：单机版里装不装模型网关（问题 1）。两套都不装，这一处不在了。两套各装什么的清单延期，前置条件是装配清单草案（成批的丁批）；单机版里模型入口要不要并进平台的进程，随它延期。

#问题 1：不带模型推理的形态，模型请求也过模型网关吗？

答复（2026-11-27）。 丙。不装模型网关，模型请求都过平台自己的模型入口，两种形态同一条路（原表第 5 条照建议）。他写的长期约束是「整个平台只有一个 Kun 模型服务。」

选项是什么影响
甲过。两种形态用同一个数据面，差别只是上游不带推理的部署也要装、要运维模型网关和它依赖的计数存储；多一跳，延迟通常是毫秒级。限流、失败转移、统计两种形态一样。ADR-015 不用改
乙不过，调用方直连第三方上游的密钥要发到每个调用方，包括每个人的 Agent 运行时实例。平台拿不到用量，配额与限流做不了。调用方要认第三方的地址和模型名，换供应商要改调用方；照第 2.2 节的读法，调用方就不是只对着一套接口了。要改 D15.5

建议：集群上的部署选甲。单机版要不要丙，等单机版的装配清单定下来再答。草案把数据面做成了可以换的绑定，哪个答案都不用改调用面与适配。

乙租户自带：每个租户登记自己的上游与凭据每个租户都要先有第三方的账号才能用
丙平台统一配是缺省，租户可以自带并覆盖两边的事都要做

乙与丙多出来的事：一个给租户用的密钥写入口，现在没有；租户填的地址要过出网名单，防止借平台去连不该连的地方；自带的密钥失败时回不回落到平台的密钥要定；自带密钥的花费算不算进配额要定。单租户版里甲与丙是一回事。ADR-015 的 D15.10 已定：租户自带的端点只能登记成模型网关的上游。

建议：第一版甲。契约按丙留好：上游带归属，凭据的引用分平台与租户两种范围。有客户要再做。

#问题 4：「可以参考框架」指的是哪一个？

答复（2026-11-26）。 他点了四个开源项目的名字，前三个跟在「可以接入更多的模型」前面，第四个跟在「可以给每个用户固定的额度」前面。名字不写。归纳出的做法在第 4.5 节，是整理者的归纳。

原话在「通过 API 方式」后面，没有说是哪个。

选项是什么影响
甲他点名一个草案对着它再核一遍：端点、能力的声明、配额的做法，有出入的地方照它改
乙不特指，照公开的成熟做法第 4 节的归纳与取舍就算数

建议：请他点名。没有特指，就按乙。

#问题 5：调用方的凭据发到哪一级？

答复（2026-11-27）。 乙，落到人和应用头上：应用用长期密钥，人用代人签发的短期凭据（原表第 7 条照建议）。他的原话是「第 7 条发给人和应用的凭据只用于调用平台。」

选项是什么影响
甲每个租户一把固定的 key。这是现行任务的写法不用调用入口，ADR-010 不用改。用量只能算到租户。一把 key 所有人共用，哪里漏了都要全租户换。key 的增删是模型网关的配置变更
乙落到人和应用头上：应用用应用级的密钥，人用代人签发的短期凭据。都由平台签发，绑租户与主体，可吊销用量能算到人和应用。离职、会话结束、实例回收可以单独吊销。要一处验平台凭据的调用入口，放在哪是问题 9；要签发接口。身份服务要补两样现在没有的：应用级的固定密钥，代人签发。鉴权要补服务主体的授权，见第 8.2 节

建议：乙。

#问题 6：管理端里改模型的配置，是点了就生效，还是经变更评审后生效？

答复（2026-11-27）。 丙，分两类：不改流量出口的点了就生效并留审计，改出口的经评审（原表第 8 条照建议）。选项丙里的「租户覆盖」随租户不能改路由不在了（ADR-024 D24.8）。下面背景里说的「现行验收」是模型网关的配置，已加 ADR-024 的标注；「D15.2 的映射入库」已被 ADR-024 取代。

背景：已定的是「统一由管理端管理」。现行验收写的是模型网关的配置变更全部经部署仓库评审，适配不持有线上直改的权限；ADR-015 的 D15.2 写的是供应商与逻辑模型名的映射入库。

选项是什么影响
甲点了就生效，留审计管理端最好用。出网的地址和凭据的引用能被一次点击改掉。D15.2 的「映射入库」要改
乙都生成变更，评审合入后生效。这是现行验收里写的做法，还没有实现最稳，D15.2 不用改。管理端只是一个提变更的界面。没有部署仓库的部署走不通
丙分两类。不改流量出口的点了就生效：模型上线下线、租户覆盖、限流与配额、调用方凭据。改流量出口的生成变更，评审后生效：上游的地址与出网，上游凭据的引用数据面的配置要分成运行期可改和评审才能改两部分。D15.2 的「映射入库」要改

建议：丙。

#问题 7：带推理的形态，管理端对推理服务管到哪一步？

答复（2026-11-27）。 乙：看清单与健康、管上下线；部署与扩缩留在推理服务自己的界面，接口留出以后加（原表第 9 条照建议）。

选项是什么影响
甲只看：目录、健康、用量。部署与扩缩留在推理服务自己的控制台管理端与推理服务的控制台并存
乙甲，加上下线：把已经部署好的模型挂进或摘出目录同上，但调用方看到什么由管理端说了算
丙乙，加部署与扩缩：在管理端里发起部署、调副本、下线并释放资源三种里把「统一由管理端管理」读得最宽的一种。每接一种推理服务，都要把它的部署参数做进适配；GPU 的排布与故障也要在管理端里看得懂

建议：第一版乙。接口按丙留好，丙随第一个要它的客户做。

#问题 8：调用面第一版只做 OpenAI 兼容的对话、嵌入与模型列表，其余按需再加，可以吗？

答复（2026-11-27）。 甲：第一版只做 OpenAI 兼容的对话、嵌入与模型列表；要加先加重排（原表第 10 条照建议）。下面选项乙的影响里「数据面一侧不难」是照模型网关写的；第一版上游只认 OpenAI 兼容（ADR-024 提议三），照成批的丙批按提议推进。

背景：ADR-015 的 D15.7 已定先做对话与嵌入。现行需求文档 10.5.1 节写的是两种协议都留。

选项是什么影响
甲可以：第一版一种协议，三类端点与 D15.7 一致。现在用的 Agent 运行时走的就是这一种协议
乙第一版就要第二种协议读到的模型网关与推理服务器多数原生带它，数据面一侧不难。多出来的在平台一侧：计量多认一种用量的格式，错误体多一套，测试的用例翻一倍
丙第一版就要重排、语音、图片里的某几样每加一样，适配、能力描述与测试都要跟着加。重排是其中最容易的：通行的形状一致，自己管推理的实现几乎都有

建议：甲。要提前加一样的话，先加重排。

#问题 9：平台发的调用方凭据在哪一层验：模型请求先过 Kun 的网关，还是由模型网关自己验？

答复（2026-11-27）。 问题换了。不再是「Kun 的网关还是模型网关」，而是「模型入口是独立的服务，还是 Kun 网关上的一组路由」。答的是甲，Kun 模型组件里的独立服务（原表第 11 条照建议）；本机实测的就是这种（ADR-024 §3.3）。新问法的两个选项：

选项是什么影响
甲模型入口是模型组件里的一个独立服务不占业务网关的容量；空闲超时自己设；读请求体里的 model，不算 D10.11 管的（2026-11-27 丙批按提议推进）。多一个要部署、要观测的服务，认凭据、限流要在它里面再装一遍，可以用本仓库的包
乙模型入口是 Kun 网关上的一组路由认凭据、限流、可信代理这些网关上已有。网关的宿主要先补空闲超时，现在满 100 秒就掐断；网关要扛长连接与流式；读请求体要给 D10.11 开一处例外；要过网关宿主的 NativeAOT 门禁

下面是提问时的原文。

背景：只在问题 5 答乙时才有这个问题。现行的写法是所有客户端只对接模型网关，模型流量不经 Kun 的网关（ADR-010 D10.1、D10.10）；凭据落到人和应用头上以后，要有一处验平台发的凭据，放在哪一层都至少要改 ADR-010 的一条。S1-DEC-038 的 Q8 针对设备上的 Agent 提过同一件事：当时推荐由模型网关校验令牌，备选是经 Kun 的网关转交，调用路径没有裁定。

选项是什么影响
甲模型请求先过 Kun 的网关上的调用入口，再到模型网关凭据、租户、可见范围、配额都在平台一侧判。换一种模型网关，或者部署里没有模型网关（问题 1 的丙），调用面与凭据怎么验都不变。模型网关仍然不碰身份、不知道租户。代价：模型流量多一跳，Kun 的网关要扛长连接与流式；它现在空闲满 100 秒会断、宿主里配不了，gateway 这个装配的宿主也还没接遥测；入口要读请求体里的模型名。要改 D10.1，给 D10.11 开一处例外
乙调用方直接连模型网关，由它验平台发的凭据流量路径最短，三层的图不变。代价：验凭据、取租户、判可见范围与配额都要做进模型网关，用插件，或者每次请求回头问平台；换一种模型网关要重做一遍。应用级的固定密钥要么每次回头问，要么同步成模型网关上的消费者。没有模型网关的部署要另找入口。要改 D10.10 与 ADR-015 的 D15.6、D15.4

两种放法对调用方没有差别，先照一种做、以后换另一种，调用方不用改。甲有一个变体：入口不放进业务网关的宿主，而是模型组件自己的一个服务，不占业务网关的容量；对 D10.1 的出入相同，而且新起一个转发服务，比借现成的网关离 D15.5 的「不自己写模型代理」更近。Agent 调平台能力的那条路（ADR-016 D16.9，经模型网关上的 MCP 路由）有同一个问题，两处最好一起定。

建议：甲。先做一次验证：流式不缓冲，首包多出的延迟，空闲超时，凭据吊销多久生效。验证不过，改乙。

#12 本文没有覆盖的

  • 进程内的调用接口。平台里的组件怎么调模型，接口长什么样，要不要直接用 .NET 官方的那套对话与嵌入的抽象，没有评估。
  • 调用方凭据由身份服务发，还是由模型组件自己发一种专用的密钥。草案提议前者；后者见效快，代价是多一套凭据的存储。两者的工作量没有比较过。
  • 模型入口的转发这一段在本机实测过（ADR-024 §3.3）：分片不被攒起来，首包多出的延迟中位 0.28 毫秒、95 分位 0.82 毫秒、最大 5.2 毫秒，调用方断开即取消上游，空闲超时可以设，一千路并发的流全部走完。没有测的：真实的上游；入口前面集群的入口那一层；多副本共用计数；凭据吊销多久生效。
  • 开放范围的两级规则取并集还是取交集，没有定（第 6.3 节）。粒度本身 2026-11-27 定了，见 ADR-024 §11。
  • 上游的错误按第 6.4 节归并。实测只做了入口自己的三种拒绝，上游各家的错误体没有对过，读到的推理服务就有好几种（ADR-024 §3.6）。
  • 入口替调用方补上「把用量放进流里」，实测做了；调用方没要时把多出来的那一帧筛掉，没有专门验。
  • 响应里的 model 字段。上游填的是后端的模型名，入口不改写的话，调用方会看到它。入口做得到；要不要一律换回逻辑模型名，没有定。
  • 用量由入口边转边记，实测读到了；流中途断了按已经转出去的量估。真实上游末尾那一帧的形状没有对过。
  • 各家后端在同一个协议下的小差别要不要在模型入口上抹平，没有定。读到的有两处：推理过程的文本在响应里的字段名不一致；并行的工具调用有的缺省关着。
  • 推理服务装进平台同一个集群的做法没有试过。放在集群外面是首选（原表第 13 条），同一个集群没有排除。
  • 价格表、金额与账单。
  • 提示词与回复内容的留痕、内容安全。
  • 设备上的本机模型。
  • 各部件的部署清单。产品的部署清单在匠心一侧。
  • 逻辑模型名的清单，适配的组件编号。随实现任务定。
