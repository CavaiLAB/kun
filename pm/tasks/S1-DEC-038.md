## 背景

2026-11-17 产品负责人在会话里给产品族定了新的总名、组成与仓库归属。这些裁定与同一天接受的合并蓝图 [ADR-023](../../docs/adr/ADR-023-kun-qian-merge-blueprint.md)（[S1-DEC-036](S1-DEC-036.md) D1–D14）有四处对不上。本任务登记裁定，列出蓝图要修订的条目。只新增本文件，ADR、`AGENTS.md` 与其它任务都没有改。

### 裁定（产品负责人，2026-11-17）

- D1 总名与定位。「我现在要做的事情不是一个 toC 的，它是一个企业级的框架」；以前是低代码、无代码的拖拽式构建，现在要「基于原生 AI，可以完成基于自然语言的系统构建」。「所以我把这个系统取名叫匠心智能体平台，不再使用 Yi」。
- D2 组成。平台之下三个框架：Kun；Qian，即现在的前端框架 yue（「后期改名为 Qian」，与 S1-DEC-036 D6 一致）；SanYuanAgent，即 iClaw 的 Python Agent 引擎，原名 NeuroAgent，「改名为 SanYuanAgent」。
- D3 底座不变。仍然基于 K8s、云原生与微服务；「之前的整个框架的定位是没有问题的，只是把它做一些拆分和聚合」，原因是「以前还是太乱了，现在可能需要更多人参与或协同」。
- D4 新仓库。平台迁到 CavaiLAB 组织下的新仓库：一个主页仓库加各子项目，名字不带前缀，`jiangxin`（主页与总览）、`kun`、`qian`、`sanyuan-agent`；先对内，四个仓库都是私有。「先不要完全的迁移代码，先创建库吧，后期慢慢进行迁移，但是可以写文档。主要是框架级的文档」。
- D5 一切皆插件。沿用为三个框架共同的原则（ADR-020）；目标是社区里现成的开源 Agent 组件能装进平台直接用。
- D6 Agent 协同。「每个人都有一个或多个 Agent」；Agent 之间沟通的机制要定义，「发给每个 Agent 的内容需要人来进行审核」；可以承接 iClaw 已有的实现。
- D7 文档站。「文档 还是使用 rspress」：文档站继续用 Rspress（ADR-022），不换工具。
- D8 文档站的位置。现在就在 `CavaiLAB/jiangxin` 仓库里搭 Rspress 站点：对「要不要现在在 jiangxin 仓库里搭 Rspress 文档站」答「现在搭」。本仓库 `website/` 的内容怎么并过去见 Q2。
- D9 文档站的部署。「部署到 K3s」：站点部署到内网的 K3s；发布方式选的是「CI 自动发布」，合并到 `CavaiLAB/jiangxin` 的主干后由 CI 发布。
- D10 SanYuanAgent 的形态。「SanYuanAgent 这应该是一个独立运行的 SDK，因为它是一个后面每个端都需要用到的例如机器人等边缘设备。应该安装上就可以用」：它是独立运行的 SDK，每个端都要用到它，包括机器人这类边缘设备，装上就能用。同时要求把它与 Kun、与模型服务怎么往来设计出来：「所以你要考虑和 Kun 这个框架如何去交互，如何和模型服务进行交互」。
- D11 模型服务。「因为后面模型服务也有 Kun 提供，但是还有可能机器人本地也会有小模型」：模型服务由 Kun 提供（原话的「也有」按「也由」理解）；机器人这类设备本地可能还有小模型。前半句与 ADR-015、ADR-023 不冲突：模型网关 adapter（组件 `qian.model-gateway`）并入 Kun 之后就是 Kun 的平台组件。后半句与 ADR-015 的出入见 Q8。

### 现状

2026-11-17 四个仓库已在 CavaiLAB 建成，各有一份框架级文档（规划稿）。代码没有迁，`idadawn/kun`、`idadawn/qian` 照常开发，本仓库 `AGENTS.md` 的现行规则照旧。

`CavaiLAB/jiangxin` 里已经搭起 Rspress 站点，聚合四个新仓库的框架级文档；已合入该仓库的主干，并已部署到内网的 K3s（D9）：合并到该仓库的主干后由 CI 发布，部署清单在部署仓库、由 Argo CD 管理。本仓库的 `website/` 没有动。

D10、D11 带出的设计已经写成规划稿：独立 SDK 的形态，设备上的引擎怎么接入 Kun，平台的模型与设备上的小模型怎么一起用。它们在三个新仓库的 PR 里（CavaiLAB/sanyuan-agent#1、CavaiLAB/kun#1、CavaiLAB/jiangxin#4），没有合并。除 D10、D11 两句之外都是主会话的提议，没有经过确认。

新建 `CavaiLAB/kun` 之后，旧地址 `CavaiLAB/kun` 不再跳转到 `idadawn/kun`。README 与文档站「产品族」页里的「旧地址重定向」已不成立，仍按旧地址取 Kun 源码的地方要改成 `idadawn/kun`。

### 与合并蓝图对不上的四处

待产品负责人确认。推荐是主会话的意见，没有实测。

- Q1 合并后的仓库（S1-DEC-036 D1，ADR-023 D23.1；另涉及 ADR-021 §7 与 S1-PM-003 的「产品族所有者 = `idadawn`」）。蓝图写合并后的仓库是 `idadawn/kun`，D4 之后 Kun 的家是 `CavaiLAB/kun`。推荐：`idadawn/kun` 与 `idadawn/qian` 都保留历史导入 `CavaiLAB/kun`，导入后两个旧仓库归档为只读；蓝图的五个阶段、冻结窗口的时点与「先导入、再并轨、最后按域归并」的顺序不变，只换目标仓库。D23.13 第 3、5 点改写历史 PR 号、改指仓库地址的做法照用，地址换成新仓库；Kun 自己的历史 PR 号原来不用动，现在也要改写成 `idadawn/kun#N`。产品族所有者随之由 `idadawn` 改为 CavaiLAB。
- Q2 仓库划分与布局（ADR-023 D23.13）。蓝图按一个仓库写：.NET、前端工作区、TS 运行时与命令行、文档站、看板、契约、部署清单都在 kun 仓库。D4 把前端单独放进 `qian` 仓库，另有总览仓库 `jiangxin`。拆开之后后端与前端之间又要跨仓库钉版本，蓝图 §5 写的「跨层修复在一个 PR 里完成」对前后端不再成立。要重定的见下表。

  | 项 | 推荐 | 说明 |
  |---|---|---|
  | 前端八个包、组件演练场、TS 运行时、插件 SDK、外壳工具包与外壳应用 | 进 `qian` 仓库 | 插件 SDK 与外壳都建在前端包上，TS 运行时的使用方也是它们 |
  | 命令行 `qian` 与声明式表面的校验库 | 留在 `kun` 仓库 | 两者不依赖任何前端包；蓝图 D23.6 把命令行与目录市场算在 Kun 的定位里 |
  | 平台组件自带的界面（身份、租户运营、租户开通三个界面包）与参考应用的远程模块 | 没有推荐，待评估 | 跟组件走，kun 仓库就要留一套前端工具链并钉前端包的版本；跟前端走，一个组件的表面就分在两个仓库里 |
  | 契约、Schema、TCK、`plugins/`、`profiles/`、部署清单、现有的 ADR 与 PRD | 留在 `kun` 仓库 | 与蓝图一致 |
  | 文档站 | 继续用 Rspress（D7），站点在 `jiangxin`（D8），部署在内网（D9）。新站点现在只聚合四个新仓库的框架级文档，各框架仓库的按钉住的提交取来源，这个做法是主会话的提议。本仓库 `website/` 的组件页、API 参考与示例迁不迁过去、怎么并，待评估 | 它同时用到前端包、.NET 的 API 参考与设计文档；蓝图 D23.13 第 5 点的「改为同仓来源」不再成立 |
  | 看板与任务 | 待评估，倾向任务跟代码走，各仓库各有 `pm/`，`jiangxin` 放汇总看板 | 任务即文件靠的是一次提交同时改代码与任务 |
  | 新 ADR 的位置 | 跨框架的记在 `jiangxin`，各框架自己的记在各自仓库 | 现有 ADR-001 至 ADR-023 的编号不变，蓝图 D23.13 第 4 点的其余内容照用 |
  | 前端何时拆出 | 更名那一批（S1-YUE-022）同时迁入 `qian` 仓库，只动一次 | 外壳的真实栈端到端测试现在靠仓库里的开发宿主工具从源码拉起后端，拆仓后要改用已发布的镜像或包 |

- Q3 跟着仓库所有者走的名字（S1-DEC-036 D9，ADR-023 D23.18 第 2 点与 D23.12）。D9 定 8 个前端包叫 `@idadawn/qian-<原名>`。GitHub Packages 上 npm 包的作用域必须是所有者的名字，所有者换成 CavaiLAB 之后这个前缀发不出去。推荐：作用域跟新所有者走，叫 `@cavailab/qian-<原名>`，名字的其余部分不变。这些包本来就要以新名首发，变的只是首发时用哪个作用域。已经发布在 `@idadawn` 之下的 TS 运行时与插件 SDK 同样处理。平台档 NuGet 包走的 GitHub Packages 源也跟所有者走，一并改；内核档在 nuget.org 上的包名不受影响。
- Q4 总名（S1-DEC-034 D1，S1-DEC-036 D8，ADR-023 D23.18 第 1 点）。S1-DEC-034 的总名 Yi 由 D1 取代，蓝图里「平台发行版不单独起名」「总名 Yi 之下怎么写留给 S1-DEC-034」两句随之失效。推荐：三个框架合在一起的平台就叫匠心智能体平台，不再另起发行版的名字；S1-DEC-034 作废，它余下的问题并入本任务（涵盖范围见 D2，「Agent SDK 指什么」见 Q5）。英文写法没有推荐，待产品负责人定；新仓库的名字用的是拼音 `jiangxin`。D8 的其余部分不受影响：「Qian」只作前端框架的名字，运行期字面不改。

### 带出的其它待定

- Q5 SanYuanAgent 进入产品族。ADR-016 按两个产品划边界：平台不写 Agent 运行时，Agent 运行时归 iClaw。现在 Agent 引擎是平台的第三个框架，这条边界要改写；分工本身（.NET 一侧不实现 Agent 循环）可以不变，变的是引擎的归属。iClaw 其余部分的去向待定。S1-DEC-034 D4 问的「Agent SDK 指什么」，是否就是 SanYuanAgent，待确认；D10 说 SanYuanAgent「应该是一个独立运行的 SDK」，两者很可能是同一个东西，但产品负责人没有明说。蓝图的「许可全部改 MIT」（D23.11）没有覆盖 Python 引擎，它的许可与是否公开待定。
- Q6 Agent 协同的机制（D6）。要定的有：Agent 的归属与身份（contracts/v0 的主体类型里已有 `agent`，标为 S4 预留、S1 不签发；委托链见 ADR-016 §6）；Agent 之间的消息走什么通道、带什么信封；由谁审、审在收件一侧还是发件一侧；审过之后的授权范围与审计。规划稿在 `CavaiLAB/jiangxin`，都是提议，没有经过确认。
- Q7 可见性与发布。`idadawn/kun`、`idadawn/qian` 是公开仓库，内核档的包发在 nuget.org、许可 MIT；新仓库先对内。代码导入之前要定：新仓库何时公开；公开之前，nuget.org 上的包指向哪个源码地址。

- Q8 设备上的本机模型与 ADR-015（D11）。ADR-015 D15.5 不绕过模型网关直连推理层，D15.10 不允许应用直连模型端点，为的是统一计量、限流与租户隔离。D11 说机器人本地可能有小模型，设备上的本机模型过不了模型网关。推荐：登记成一条明确的例外，只限设备本机地址上的模型；用量由引擎记录后上报平台，和模型网关计的分开；ADR-015 的其余条目不变。另有一处要定：设备调用平台的模型走哪个入口。推荐经平台的网关，用 `agent` 主体的令牌，由服务端标注租户与 Agent，不给设备发长期的模型密钥；这与 D15.6「业务 API 的身份边界仍在网关」的方向一致，前提是 `agent` 主体启用（见 Q6）。两条推荐都是主会话的意见，没有实测。
