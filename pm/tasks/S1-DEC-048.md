## 背景

产品负责人 2026-11-26 对远程授权接口的十个问题答了「远程的授权接口 也按照建议执行」（[S1-DEC-045](S1-DEC-045.md)）。照答复，[契约草案](../../docs/prd/specs/authz-remote-interface.md)改成了裁定后的版本，任务也建了（草案第 13 节）。往下落的时候有四件事接不上，要他定。

下面每个问题的选项、影响与建议都是整理时写的，都没有问过。前两个不定，对应的东西没有任务承接，或者开不了工。后两个不定也能照缺省往下做，缺省写在各问里。

本任务的优先级标 P0。[S1-AZ-023](S1-AZ-023.md) 沿用原任务的 P0，在「初步可用」的路径上，它依赖问题 2 的答复；决策任务挡着路径上的任务，就排在前面。这是整理时定的，没有问过。

### 待裁定的问题

1. **「要人确认的操作只能经平台执行」要有的两样东西，现在建任务吗，归到哪个领域？**
   - S1-DEC-045 D6 定了别的系统里标了要人确认的操作只能经平台执行。平台一侧要有两样东西，现在都没有任务承接：
     - 甲：等人输入的任务与能力执行入口的契约，即任务长什么样、点击怎么交给平台、能力经平台的入口怎么调。看板上相邻的只有 [S1-RT-007](S1-RT-007.md)，它只预留 Operation 资源的形状。确认卡的最小一圈（[S1-DEC-042](S1-DEC-042.md) D1）也要用到这一样；那一圈拆出来的任务进不进看板，当时没有定。
     - 乙：平台按 `http` 绑定把调用转给别的系统的执行器，以及转调用时随调用给的凭据。
   - 选项：（一）现在先建甲的任务，只出契约，归运行时与能力的领域（RT）；乙等甲的契约定了再建，也归 RT，核验凭据的那一侧留在鉴权（[S1-AZ-012](S1-AZ-012.md) 留的那一条）；（二）两样现在都建；（三）都先不建，等确认卡那一圈或里程碑 M1 排上再说。
   - 影响：（一）判定接口与网关的区分做出来以后有契约可以对；执行器晚一步，在它做出来以前，别的系统里要人确认的操作还走不通。（二）乙的范围靠甲的契约，现在就定容易返工。（三）不占人手；在那之前 D6 定的那条路没有东西承接：判定接口会对不算人本人的调用回「要人确认」，平台一侧没有入口接，[S1-GW-004](S1-GW-004.md) 交付的那处区分也没有地方用。
   - 建议：（一）。甲那份契约也是确认卡的最小一圈要用的，是同一份。两样的范围由建出来的任务自己写，这里不替它们定。
2. **最小角色授权页放在哪、用什么做？**
   - 这一页原来在 [S1-AZ-005](S1-AZ-005.md) 里，要用前端框架的组件做；前端框架的仓库已归档（[S1-DEC-043](S1-DEC-043.md) D1）。已定的是最终的界面放匠心，也可以放到另一个仓库（[S1-DEC-041](S1-DEC-041.md) D6）；本仓库现有的管理页面以后怎么办没有定。拆分以后这一页是 [S1-AZ-023](S1-AZ-023.md)，端点（[S1-AZ-020](S1-AZ-020.md)、[S1-AZ-021](S1-AZ-021.md)、[S1-AZ-022](S1-AZ-022.md)）不等它。成员管理页（[S1-IDP-018](S1-IDP-018.md)）是同一类的问题，这一问不替它答。
   - 选项：（一）这一页不在 Kun 里做：Kun 交付管理端点与契约，页面在匠心的管理端里做，S1-AZ-023 关掉，验收里说页面的两条随页面走；（二）在 Kun 里留一页最小的，接着用现有的外壳与已发布的前端框架包；（三）先不做页面，等管理端有了再定，S1-AZ-023 挂着。
   - 影响：（一）与「Kun 不负责业务、界面放匠心」一致；原验收里的端到端测试不在本仓库里跑了，本仓库只测端点；匠心的管理端还是规划，这一页要等它。「初步可用」路径里「管理后台可用」那一段当初是照前端框架的页面排的（S1-YUE-010 → S1-IDP-010 → S1-AZ-005，S1-AZ-007、S1-TEN-016、S1-IDP-017 → S1-IDP-018，见 [S1-DEC-033](S1-DEC-033.md) 的里程碑路径）；选（一）以后，在匠心的管理端做出来以前，角色授予只有端点、没有页面。（二）现在就能做出一页能用的；它建在已归档、不再发新版的包上，以后多半要重做。（三）不占人手；在那之前角色授予只有端点，没有页面。
   - 建议：（一）。
3. **两个客户端包谁先做：第一个要在服务端判权限的使用方是谁？**
   - S1-DEC-045 D9 定了先出 TypeScript 与 .NET 两种，谁在前看第一个使用方。登记时看得到的两个使用方：匠心的工作区服务要在服务端判权限，照 [ADR-010](../../docs/adr/ADR-010-gateway-layers.md) 第 9 节它装本仓库的 .NET 登录组件；匠心的管理端只有浏览器一侧（S1-DEC-041 D5），用得上的是 TypeScript 包里浏览器的入口，那个入口只做预判。
   - 选项：（一）第一个是匠心的工作区服务，它是 .NET 的宿主：先做 .NET 的远程模式（[S1-AZ-015](S1-AZ-015.md)），TypeScript 包先只出浏览器的入口；（二）第一个是 Node 写的后端服务：先做 TypeScript 包的两个入口（[S1-AZ-014](S1-AZ-014.md)），.NET 在后。
   - 影响：先做的那一个要把一致性用例与替身服务一起带出来。先后排反了，第一个使用方要么等，要么照契约自己写调用。
   - 建议：这是一个要确认的事实，不是取舍。不答的话缺省照（一）排，前提是工作区服务确实是 .NET 写的。
4. **这些任务排在「初步可用」之前还是之后？**
   - 「按照建议执行」没有说排期。「初步可用」的路径是 2026-11-11 定的（[S1-DEC-033](S1-DEC-033.md) D1），路径上的任务标 P0。原 S1-AZ-005 在路径上，拆出的四个（S1-AZ-020 至 S1-AZ-023）先沿用 P0。契约定稿（[S1-AZ-011](S1-AZ-011.md)）因为 S1-AZ-020 依赖它，也标了 P0；本任务因为 S1-AZ-023 依赖问题 2 的答复，也标了 P0。远程接口新建的其余任务先标 P1，其中等数据权限求值与等里程碑 M1 的两个标 P2。这些优先级都是整理时标的。
   - 拆分以后路径上的量变了：原来是一个任务（S1-AZ-005，估 3 天），现在是四个（S1-AZ-020 至 S1-AZ-023，各估 3 天）再加契约定稿（估 3 天）。估时是拆分时重估的，没有问过。其中 S1-AZ-023 还等问题 2。
   - 选项：（一）远程接口的最小一条线也提到 P0，排进「初步可用」：执行前的判定、登记过的系统代问（连同登记机器身份的入口 [S1-AZ-024](S1-AZ-024.md)）、第一个使用方用的那个客户端包。契约定稿已经因为上面那条依赖在路径上。（二）这三样排在「初步可用」之后，照现在标的优先级。
   - 影响：（一）匠心的工作区服务可以早一步在服务端判权限；「初步可用」的路径再变长。（二）路径上不再加东西，S1-AZ-020 仍要等 S1-AZ-011；在那之前别的系统在服务端判不了权限，只有给界面用的端点可用：现有的两个只读端点，与已经在路径上的 [S1-AZ-020](S1-AZ-020.md)。
   - 建议：（二）。这条线的使用方是匠心的工作区服务，还没有开工；「初步可用」是 2026-11-11 定的范围，即多租户、管理后台、模型服务（S1-DEC-033 D1），里面没有工作区服务。管理端只有浏览器一侧，它用的预判（S1-AZ-020）已经在路径上，不在这一问里。等确认卡的最小一圈排上时，它要用的几样跟着那一圈排，不等这条线的其余部分：登记机器身份的入口（S1-AZ-024）；网关那处区分（[S1-GW-004](S1-GW-004.md)），要守住「任务上的动作只能人做」就要它；问题 1 的甲。不答的话缺省照（二），即现在标的优先级。
