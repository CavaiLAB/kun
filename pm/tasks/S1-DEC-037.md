## 背景

2026-11-17 把 staging 换到 main `9399cf9584` 的镜像时，`qian.identity.server`（新增权限点 `member:create` 与角色授予）与 `qian.tenancy`（契约 `http-v1.openapi.json` 加了 `initialPassword`）的组件文件夹变了，版本号仍是 `1.0.0`。staging 库里已有这两个组件 `1.0.0` 的权限目录与修订，系统组件修订 Job 失败。产品负责人确认后删除 8 个 `plugin_qian_*` schema 清库重来，过程见 S1-DEP-011 的进度日志、idadawn/qian#324 与运维手册第 4、7、9 节。签名脚本覆盖的 13 个 system 级 module 组件从建立起版本号都没改过，带功能的 staging 部署几乎每次都会再撞上。

事实核实、三种做法（要改的代码、要补的用例、对审计、回切与现有租户的影响）和推荐写在 [决策文档](../../docs/decisions/system-component-same-version.md)。要点：

- 同版本换内容在两处被拒：authz 的权限目录按「组件 + 版本」不可变，authz 挂不起来，宿主只报 capabilities 未就绪、内层异常为空；Lifecycle 不让同一版本对应两个制品。
- 只升版本也不行（按代码推断）。修订 Job 会成功，但已有租户的授权策略停在旧版本，authz 只登记预装的新版本，这些租户对该组件的全部权限点都被拒绝，平台超管的旁路同样拒绝。把租户升到新版本的 Lifecycle `UpgradeAsync` 与 Authz `InstallDefaultsAsync` 在生产代码里都没有调用方。
- 平台宿主每个组件只预装一个版本，契约准入找不到基线，升版本时既不拦也不比较。手册第 9 节与平台宿主 README 的 fail-closed 说法与此不符。
- CI 的 `PlatformIdentityHostTests` 每次空库、用同一份文件夹跑两遍，测不到这种情况。

本任务只做决策准备，不改实现代码、不动集群。

## 待拍板

- D1 选哪种做法：A 升版本门禁，并让升版本在有数据的库上走通（推荐，分三步）/ B 允许 system 级预装组件同版本受控替换 / C 维持现状，组件文件夹一变 staging 就清库重来。
- D2（选 A 时）「上次发布」的基线放哪：推荐仓库里的基线文件，初值取 `9399cf9584`，随部署登记的 PR 更新；备选：每次部署打 git 标签。
- D3（选 A 时）门禁范围：推荐与签名清单同一口径的 system 级 module 组件，按整个文件夹算；备选：`plugins/` 下全部非骨架组件。
- D4（选 A 时）第二步落地之前，staging 遇到组件文件夹变化怎么办：推荐仍按手册第 7 节清库，每次先经产品负责人确认；备选：清库改为常设授权。
- D5（选 A 时）跨版本回切镜像：推荐修订 Job 双向对齐租户；备选：只支持向上，跨版本回切时清库。
