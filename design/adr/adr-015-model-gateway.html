#ADR-015 模型服务网关

#1 背景与问题（Context）

模型服务网关是本期唯一的 AI 范围。现网（2026-10-03 合入）已有 Higress 2.2.3（gateway 2 副本 + PDB，console 内网）、McpBridge 上游注册（DashScope 与 OpenRouter 已注册）、key-auth 双形态 consumer、网关专用 Redis Sentinel HA、MaaS 专用 Loki 90 天访问日志（账单原始数据，按请求 ID 去重）、官方 AI 大盘与 4 条告警、maas-* 路由命名约定（基线 K §4.2、§6.4）。差距：ai-proxy 供应商与逻辑模型名映射、ai-quota / ai-token-ratelimit / ai-statistics 插件绑定、maas-* 业务路由与消费者、价格表、账单脚本尚未入 git；推理层是 Xinference（0 副本）+ Ollama，无 GPUStack manifest；首节点两块 3090 已借出一块（基线 K §4.2、§6.4）。

［下游智能体平台］已落地可直接复用的契约与控制面：Higress 对租户无感、纯数据面 chokepoint；x-<product>-consumer 头由服务端生成作限流桶键；usage 由调用方从响应回流落库；租户级模型路由「产品默认 + 租户覆盖」、坏配置 fail-open 到默认；BYO 端点只能注册为 Higress 上游；模型目录用 model-capabilities 契约（模态 / 工具 / 上下文 / 数据驻留 / 隐私 / 时延 / 成本档）描述；租户 API Key + OpenAI 兼容面 + QuotaEnforcer + Usage Ledger；认证收编（Wasm）明确延后（基线 K §4.1）。Kun.Gateway 与 Higress 是两个不同层次的网关（基线 K §6.4）。

#2 决策（Decision）

  • 【已被 ADR-024 取代（2026-11-27）：平台不装 Higress，见 ADR-024 D24.4、D24.5】D15.1 不另起一套：Qian 的模型服务网关并入团队正在推进的 Higress / MaaS 基础设施，复用 maas-* 路由、网关专用 Redis HA、MaaS Loki、AI 大盘。
  • 【部分被 ADR-024 取代（2026-11-27）：Higress 一侧的映射、插件绑定、价格表与账单脚本随平台不装 Higress 不再成立；推理层切到 GPUStack、OpenRouter 出网白名单放行两项不受影响；见 ADR-024 D24.4、D24.5】D15.2 按《GPUStack + Higress 模型服务整合方案》第 1–2 阶段补齐：ai-proxy 供应商与逻辑模型名（chat-default 等）映射入 git；ai-quota / ai-token-ratelimit / ai-statistics 绑定；价格表与账单脚本；推理层从 Xinference 切到 GPUStack；OpenRouter 出网白名单放行。
  • 【部分被 ADR-024 取代（2026-11-27）：注册进 Higress 随平台不装 Higress 不再成立；GPUStack 作为 OpenAI 兼容的本地上游、Provider Adapter、逻辑模型目录照旧；「只做三件事」的边界放不放开，随 ADR-024 的提议一与读法一，没有裁定；见 D24.5】【S1-DEC-049（2026-11-27）：「只做三件事」的边界放开，模型入口与调用方凭据的签发也在本仓库一侧做；见 ADR-024 §10.4】D15.3 Qian 侧只做三件事（qian.model-gateway，service 形态的控制面 adapter，可选独立 Pod）：GPUStack 作为 OpenAI 兼容本地上游注册进 Higress；Provider Adapter（发现模型、健康、生命周期）；填写 model-capabilities 契约形成逻辑模型目录。
  • 【经 ADR-024 修订（2026-11-27）：内容不变；租户、配额、计量仍在平台一侧，原来经 Higress 的部分改由模型入口做；模型入口是 ADR-024 的提议，见 D24.5】【S1-DEC-049（2026-11-27）：模型入口已定，见 ADR-024 §10】D15.4 租户 / 配额 / 计量在平台侧：Higress 对租户无感；consumer 头由服务端生成；按租户的限流与计量经 consumer 与统计插件；计量表从第一天带 tenant_id + project_id 双键。
  • 【部分被 ADR-024 取代（2026-11-27）：后半句随平台不装 Higress 没有了对象，应用不直连推理层由换主语以后的 D15.10 承接；前半句「不自写模型代理层」放不放开，随 ADR-024 的提议一，没有裁定；见 D24.5】【S1-DEC-049（2026-11-27）：前半句放开，转发由平台自己的模型入口做，已定；见 ADR-024 §10.4】D15.5 不自写模型代理层，不绕过 Higress 直连推理层。
  • 【经 ADR-024 修订（2026-11-27）：内容不变；Higress 换成登记成上游的模型网关与推理服务，是整理者的换法，随 ADR-024 的提议二、四；平台发的调用方凭据由模型入口验，是提议一；见 D24.5】【S1-DEC-049（2026-11-27）：随提议二、四的换法定了；平台发的调用方凭据由模型入口验，是从原表第 11 条推出来的，整理时的读法；见 ADR-024 §10】D15.6 不在 S1 把 SSO / S2S 交给 Higress；业务 API 的身份边界仍在 qian.gateway（ADR-010）。
  • 【S1-DEC-049（2026-11-27）：调用面首版做对话、嵌入、模型列表，下一项先加重排；GPUStack 装在平台集群外的专门机器上（他写的是首选），适配由 Kun 维护；末尾的 GPU 归属没有另说，仍没有定；见 ADR-024 §10.2】D15.7 接入范围（Q17）：先 LLM + Embedding；ASR / TTS / Rerank 后续按需评估；GPU 归属由产品负责人决定。
  • 【S1-DEC-049（2026-11-27）：S1 那一项里的上游注册，改成在平台的目录里登记上游，随 ADR-024 提议四定了；S4 那一项「Higress 托管每租户 MCP 逻辑门面」随提议七按提议推进，细节随 M1 的设计；见 §12；本项不改】D15.8 阶段：S1 可选做底座接线（上游注册、adapter、逻辑模型目录）；S2 模型目录与按用途路由；S3 租户可见的模型门户、成本与配额预算告警；S4 Higress 托管每租户 MCP 逻辑门面。
  • 【S1-DEC-049（2026-11-27）：待定的计量共用方案与下游智能体平台有关，与它有关的旧待定事项随成批的戊批关闭，这一项照此读，是整理时的读法；计量双键照 D15.4；本项不改】D15.9 与［下游智能体平台］的计量共用：Qian 应用经租户 API Key 的 OpenAI 兼容面调模型、计量进同一 Usage Ledger 的方案待 S3 定（Q15）；S1–S2 只保证契约形状与双键约定一致。
  • 【经 ADR-024 修订（2026-11-27）：内容不变；租户自带的模型端点只能登记成模型入口的上游，不允许应用直连；模型入口是 ADR-024 的提议，见 D24.5】【S1-DEC-049（2026-11-27）：「租户覆盖」与租户自带的模型端点不再成立，路由由平台管理员统一配；不允许应用直连照旧；见 ADR-024 §10.4】D15.10 租户级模型路由：「产品默认 + 租户覆盖」，坏配置 fail-open 到默认；BYO 模型端点只能注册为 Higress 上游，不允许应用直连。
  • 【经 ADR-024 修订（2026-11-27）：内容不变；转发时带上密钥的，由 Higress 换成模型入口；模型入口是 ADR-024 的提议，见 D24.5】【S1-DEC-049（2026-11-27）：模型入口已定；上游的密钥只由平台管理，见 ADR-024 §10】D15.11 密钥：模型供应商密钥只以 secretRef 出现在配置与清单中。
  • D15.12 Provider Adapter 的对外契约：model-capabilities 与 model-governance（［下游智能体平台］契约）；模型目录含类型 / 能力标签 / 配额，S4 可经 MCP resources 暴露。

#3 理由（Rationale）

  • Higress 已是团队的唯一 LLM chokepoint，另起一套会分裂计量、限流与账单（基线 K §4.1、§6.4）。
  • 自写模型代理既无增量价值又会绕过 Higress 的 token 限流与缓存；Qian 的差异化在平台侧的租户 / 配额 / 权益，而非代理层。
  • 把 SSO 交给 Higress 会让 S1 的身份边界依赖第三方网关的认证收编能力，而该能力已被［下游智能体平台］明确延后。
  • 先 LLM + Embedding 是低代码与 Agent 场景的最小集；ASR / TTS / Rerank 涉及不同的上游与计量口径。

#4 备选方案与放弃原因（Alternatives）

  • 自研模型代理层（绕过 Higress）：重复建设，分裂计量。放弃。
  • 引入 LiteLLM / One-API 类代理：与 Higress 职责重叠，再加一层运维对象。放弃。
  • 应用直连 GPUStack / 推理层：无限流、无计量、无租户隔离。放弃。
  • Higress 承担 SSO / S2S：认证收编延后、对租户无感。放弃（S1 明确不做）。

#5 后果与代价（Consequences）

  • 正面：Qian 零成本继承 MaaS 的限流、统计、账单与大盘；模型目录契约与［下游智能体平台］同形，S4 对接顺畅。
  • 负面：Qian 的模型能力受制于团队 MaaS 的推进节奏与 GPU 资源（首节点 GPU 已借出一半）；Provider Adapter 的维护方未定；GPUStack 控制面是否已在仓外存在待确认。
  • 配套：整合方案第 1–2 阶段的 GitOps 入库；GPUStack manifest；maas-* 路由与消费者；价格表。

过渡态（2026-10-06）：推理层为 Xinference（0 副本）+ Ollama；ai-proxy 等插件配置未入 git；无 GPUStack manifest。S1 若做底座接线，以 PoC 方式先接 OpenRouter / DashScope 上游，GPUStack 待 GPU 归属确认后接入。

#6 对各阶段的影响

  • S1：可选底座接线（上游注册 + adapter + model-capabilities 填写）；计量表双键约定。
  • S2：模型目录与按用途路由（chat-default / embedding-default）；低代码公式与表单可调用模型能力经 OpenAI 兼容面。
  • S3：租户可见的模型门户；成本与配额预算告警；Usage Ledger 共用方案落地。
  • S4：Higress 托管每租户 MCP 门面；Agent 经 Higress MCP 路由调用 Qian 能力；OTel GenAI 语义约定仍为 Development 级，计量 schema 不以其属性名持久化。

#9 两种形态与模型服务的标准接口（2026-11-26）

产品负责人 2026-11-26 说（S1-DEC-043 D5；平台级裁定 P83，原文在 CavaiLAB/jiangxin 的 2026-11-26 平台级裁定）：「企业级框架分为两种 1.K8s集群，包括模型推理服务， GPU Stack 等 2.不包括直接接入第三方模型服务，通过 API 方式，可以参考框架。 3.提供多租户和单租户两个版本。 但是不管哪种方式 统一由管理端进行管理。以上尽量使用插件的形式进行实现。所以你要设计一些标准的接口，方便我对接后面的模型推理服务，因为我只想提供一套。」

  • 读法（整理者的读法，产品负责人没有逐句确认）：
    • 两种形态按带不带模型推理分。第一种是 K8s 集群，集群里带模型推理服务。第二种的原话读作：不包括模型推理，通过 API 直接接入第三方的模型服务。
    • 「标准的接口」读作模型服务这一块留一个标准的接口：后面接自己的推理服务，还是接第三方的 API，都接在它上面。「只提供一套」读作上面的产品只做一套，不跟着形态分叉。
    • 「尽量使用插件的形式」读作模型推理的接入做成组件，换形态换组件。
    • 「统一由管理端进行管理」读作两种形态用同一个管理端，模型服务也在里面管。管理端在匠心一侧（S1-DEC-041 D5、D6）。
    • 「可以参考框架」读作做法可以参考现成的开源框架，没有说是哪个。
  • 与本文的关系：没有出入。D15.3 把本仓库一侧收成三件事：上游登记、Provider Adapter、逻辑模型目录；D15.12 给适配留了对外契约；D15.10 定了「产品默认 + 租户覆盖」的模型路由；D15.4 把租户、配额、计量放在平台一侧。这次加上的是：同一套要管两种形态，形态的差别尽量落在装哪个适配上，并由管理端统一管理。
  • 没有定的：
    • 标准接口的形状，连同给管理端用的那一部分。
    • 第二种形态的数据面要不要也过模型网关。照 D15.5、D15.10，应用不绕过模型网关直连，租户自带的模型端点只能登记成它的上游；第二种形态是不是也这样，没有定。
  • 现状：规划。组件 qian.model-gateway 现在只有配置骨架；S1-MGW-001 至 S1-MGW-003 都没有开始，这次没有动它们，没有新建任务。

#10 模型服务标准接口的契约草案（2026-11-26，提议）

§9 记为没有定的「标准接口的形状」，现在有了一份契约草案：模型服务的标准接口：契约草案，对应任务 S1-MGW-004。它是提议，产品负责人没有裁定；本文的决策没有因为它改动。

  • 草案把接口分成调用、接入、管理三个面，与本文各条的对照在草案第 10.1 节。有出入的是两条：D15.3，草案多出验平台凭据的调用入口与调用方凭据的签发；D15.12，那两份能力契约不在本仓库，草案给了自己的形状。另有四条随问题的答案而定：D15.2 的「映射入 git」随问题 6，D15.5 随问题 1，D15.4 与 D15.6 随问题 9。
  • 要产品负责人定的九个问题由 S1-DEC-044 跟踪，§9 记为没有定的「第二种形态的数据面要不要也过模型网关」是其中的问题 1。草案里的调用入口放在哪一层，牵涉 ADR-010 的 D10.1、D10.10，是其中的问题 9。
  • S1-MGW-001 至 S1-MGW-003 的内容没有改。草案第 10.4 节有一份建议的任务清单，裁定之后再建。

#11 平台不装 Higress，额度用积分（2026-11-27）

产品负责人 2026-11-26 讨论模型服务接口，定了额度的单位用积分，积分系统可以选择启用或不启用，周期可以选择。说到 Higress，他的原话是「评估一下，不需要就不安装了吧。你觉得有这个必要吗？因为它安装起来还是挺复杂的。」评估是整理者做的，结论是不需要。这些登记在 ADR-024；答复的原话与九个问题各到哪一步，在 S1-DEC-044。

对本文各条：

  • 被取代：D15.1 整条；D15.2、D15.3、D15.5 里写着 Higress 的部分。D15.2 里推理层切到 GPUStack、OpenRouter 出网白名单放行两项不受影响；D15.3 里 GPUStack 作为 OpenAI 兼容的本地上游、Provider Adapter、逻辑模型目录照旧。D15.5 的后半句没有了对象，应用不直连推理层由换主语以后的 D15.10 承接。
  • 随提议、没有裁定：D15.3「只做三件事」的边界与 D15.5 的前半句「不自写模型代理层」。平台不装 Higress 以后由谁转发，ADR-024 的提议是平台自己的模型入口；这条提议定了，这两处才放开。
  • 换主语、内容不变：D15.4、D15.6、D15.10、D15.11。原来由 Higress 承担或写着 Higress 的地方没有了对象。D15.4、D15.10、D15.11 的新主语是模型入口，随那条提议；D15.6 换成登记成上游的模型网关与推理服务，是整理者的换法，随 ADR-024 的提议二、四，S1 照旧，S1 以后怎样原文没有说。
  • 阶段不变：D15.8。S1 那一项里的上游注册，改成在平台的目录里登记上游，随 ADR-024 的提议四；S4 那一项「Higress 托管每租户 MCP 逻辑门面」随提议七，改走平台自己的网关，随 M1 的设计定。
  • 不受影响：D15.7、D15.9、D15.12。

§9 记为没有定的「第二种形态的数据面要不要也过模型网关」，照 ADR-024 两种形态都不装 Higress，不会再过它；要不要过平台自己的模型入口，提议是要（ADR-024 提议一、六），没有裁定，也就是契约草案的问题 1 在乙、丙之间还没有定。§10 写的随问题的答案而定的四条，现在是这样。D15.2 写着 Higress 的部分被取代，原来随的问题 6 不再牵涉它，问题 6 本身没有答。D15.5 部分被取代，前半句随提议一，也就随问题 1。D15.4、D15.6 换了主语，原来随的问题 9 换成了「模型入口是独立的服务，还是 Kun 网关上的一组路由」，没有答。§3 到 §6 是 2026-10-06 照团队那一个集群写的，原文不改；现在的理由见 ADR-024 §3。

#12 统一的模型服务（2026-11-27）

产品负责人 2026-11-27 对《决策表》一次定稿，与模型服务有关的登记在 ADR-024 §10，原话与列给他的话在 S1-DEC-049。他明确写出的一条长期约束，原话是「整个平台只有一个 Kun 模型服务。」；还写了「普通用户、租户管理员和应用都不能自带上游密钥、自填地址或改路由。」

对本文各条：

  • 放开：D15.3「只做三件事」的边界，D15.5 的前半句「不自写模型代理层」。原表第 5 条照建议定了：不装 Higress 以后，模型请求都过平台自己的模型入口，两种形态同一条路，ADR-015 原来这两条随之放开。
  • 不再成立：D15.10 的「产品默认 + 租户覆盖」，与租户自带的模型端点那一句。路由由平台管理员统一配；不允许应用直连照旧。
  • 换主语以后的新主语定了：D15.4、D15.10、D15.11 的模型入口，D15.6 的登记成上游的模型网关与推理服务。
  • 有了结论：D15.7 的前两句，§7 的第 2、3 项，见各条前的标注；§7 的后两项过时，关闭。D15.7 末尾与 §7 第 1 项的 GPU 归属没有另说，仍没有定。
  • D15.8：S1 那一项在平台的目录里登记上游，随提议四定了；S4 那一项随提议七按提议推进，细节随 M1 的设计。§11 里讲 D15.8 的那一条照此读。
  • D15.9：与下游智能体平台有关的旧待定事项随成批的戊批关闭，这一项照此读，是整理时的读法。
  • 不受影响：D15.12。

§9 记为没有定的「第二种形态的数据面要不要也过模型网关」，定了：两种形态都不装 Higress，模型请求都过平台自己的模型入口。§10、§11 里写的随问题的答案而定的几条，问题都答了，见 ADR-024 §10.2。
