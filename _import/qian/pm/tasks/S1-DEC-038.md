## 背景

2026-11-17 产品负责人在会话里给产品族定了新的总名、组成与仓库归属。这些裁定与同一天接受的合并蓝图 [ADR-023](../../docs/adr/ADR-023-kun-qian-merge-blueprint.md)（[S1-DEC-036](S1-DEC-036.md) D1–D14）有四处对不上。本任务登记裁定，列出蓝图要修订的条目。只新增本文件，ADR、`AGENTS.md` 与其它任务都没有改。

### 裁定（产品负责人，2026-11-17 起）

- D1 总名与定位。「我现在要做的事情不是一个 toC 的，它是一个企业级的框架」；以前是低代码、无代码的拖拽式构建，现在要「基于原生 AI，可以完成基于自然语言的系统构建」。「所以我把这个系统取名叫匠心智能体平台，不再使用 Yi」。
- D2 组成。平台之下三个框架：Kun；Qian，即现在的前端框架 yue（「后期改名为 Qian」，与 S1-DEC-036 D6 一致）；SanYuanAgent，即 iClaw 的 Python Agent 引擎，原名 NeuroAgent，「改名为 SanYuanAgent」。
- D3 底座不变。仍然基于 K8s、云原生与微服务；「之前的整个框架的定位是没有问题的，只是把它做一些拆分和聚合」，原因是「以前还是太乱了，现在可能需要更多人参与或协同」。
- D4 新仓库。平台迁到 CavaiLAB 组织下的新仓库：一个主页仓库加各子项目，名字不带前缀，`jiangxin`（主页与总览）、`kun`、`qian`、`sanyuan-agent`；先对内，四个仓库都是私有。「先不要完全的迁移代码，先创建库吧，后期慢慢进行迁移，但是可以写文档。主要是框架级的文档」。可见性后来改了，见 D16。
- D5 一切皆插件。沿用为三个框架共同的原则（ADR-020）；目标是社区里现成的开源 Agent 组件能装进平台直接用。
- D6 Agent 协同。「每个人都有一个或多个 Agent」；Agent 之间沟通的机制要定义，「发给每个 Agent 的内容需要人来进行审核」；可以承接 iClaw 已有的实现。
- D7 文档站。「文档 还是使用 rspress」：文档站继续用 Rspress（ADR-022），不换工具。
- D8 文档站的位置。现在就在 `CavaiLAB/jiangxin` 仓库里搭 Rspress 站点：对「要不要现在在 jiangxin 仓库里搭 Rspress 文档站」答「现在搭」。本仓库 `website/` 的内容怎么并过去见 Q2。
- D9 文档站的部署。「部署到 K3s」：站点部署到内网的 K3s；发布方式选的是「CI 自动发布」，合并到 `CavaiLAB/jiangxin` 的主干后由 CI 发布。
- D10 SanYuanAgent 的形态。「SanYuanAgent 这应该是一个独立运行的 SDK，因为它是一个后面每个端都需要用到的例如机器人等边缘设备。应该安装上就可以用」：它是独立运行的 SDK，每个端都要用到它，包括机器人这类边缘设备，装上就能用。同时要求把它与 Kun、与模型服务怎么往来设计出来：「所以你要考虑和 Kun 这个框架如何去交互，如何和模型服务进行交互」。
- D11 模型服务。「因为后面模型服务也有 Kun 提供，但是还有可能机器人本地也会有小模型」：模型服务由 Kun 提供（原话的「也有」按「也由」理解）；机器人这类设备本地可能还有小模型。前半句与 ADR-015、ADR-023 不冲突：模型网关 adapter（组件 `qian.model-gateway`）并入 Kun 之后就是 Kun 的平台组件。后半句与 ADR-015 的出入见 Q8。
- D12 先迁核心。「首先迁移核心的 Agent 框架 到 SanYuanAgent」：Python 引擎分核心、服务层、媒体适配层三部分，先把核心迁入 `CavaiLAB/sanyuan-agent`，另两部分随后。
- D13 名字。对「核心迁入 SanYuanAgent 后叫什么名字」选的是 `sanyuan-agent`：发行名 `sanyuan-agent`，导入名 `sanyuan_agent`，命令行 `sanyuan-agent`，环境变量前缀由 `NEUROAGENT_` 改为 `SANYUAN_AGENT_`。服务层与媒体适配层的名字没有定。
- D14 历史与原仓库。对「核心的提交历史带不带进新仓库」选「带历史」：动过核心的提交带过去，保留作者与时间，路径改写到新位置。对「核心迁过来之后，iClaw 里原来那一份怎么办」选「这一步先不动 iClaw」：原仓库里那一份照旧在用，不删不改；让 iClaw 改为依赖新包、删掉旧的那一份是以后单独的一步，过渡期原仓库核心上的改动同步到新仓库。
- D15 核心的许可。对「核心迁入后用什么许可」选「保持 Apache-2.0」：核心保持 Apache-2.0，许可文件里对所借鉴开源项目的附加声明保留。服务层与媒体适配层的许可没有定。
- D16 新仓库公开。四个新仓库已由产品负责人本人在 GitHub 上改为公开：「我手动改成的 public ，直接推送吧」。D4 的「先对内，四个仓库都是私有」由此改写；核心的迁移结果直接推到公开的 `CavaiLAB/sanyuan-agent`。
- D17 Kun 与 Qian 迁入 `CavaiLAB/kun`，现在开始。「Kun 和 Qian 开始进行迁移，迁移过程中进行改名，迁移至（https://github.com/CavaiLAB/kun）。你来制定迁移计划。使用子会话进行迁移工作」。由此：合并后的仓库是 `CavaiLAB/kun`，Q1 已裁；迁移现在开始，S1-DEC-036 D13 的「冻结窗口放在『初步可用』里程碑在途任务收口之后」由此改写；改名是迁移的一部分，在迁移过程中做完。执行计划写在 `CavaiLAB/kun` 的 `docs/migration-plan.md`（CavaiLAB/kun#2），迁移工作由子会话做。
- D18 前端迁入 `CavaiLAB/qian`，现在开始。产品负责人同一天在另一个会话（前端迁移计划）里说：「前端开始进行迁移，迁移过程中进行改名，迁移至（https://github.com/CavaiLAB/qian）」，原话取自那个会话的记录。由此：Q2 表里前端的去处已裁；S1-DEC-036 D7 与 D9 里「与后端改名同窗口、排在阶段 3 的最后一批」由此改写为并行迁移。前端的计划、路径归属的细目与 Q3 的包作用域由那个会话登记，本条只记去处与时点。 范围随后由产品负责人在那个会话里选定为「只迁框架库」：前端八个包、组件演练场、前端插件开发包、TypeScript 运行时及其门禁与发布工作流迁入 `CavaiLAB/qian`；外壳应用与外壳工具包、三个组件界面包、参考应用的远程模块、文档站、命令行与声明式表面的校验库留在后端仓库，后端仓库按钉住的版本消费前端仓库发出的包。
- D19 导入内容的清理范围。产品负责人同一天在另一个会话（平台架构规划）里定了 Kun 与 Qian 导入内容里引擎原名与私有下游产品名怎么清，原话取自那个会话的记录。提给产品负责人的范围是那个会话与迁移计划会话一致的意见：只清搬进 `docs/`、会上站的现行文档，以及对外说明的当前版本；过渡目录里没有搬出的原件、任务日志与提交历史原样保留，同 SanYuanAgent 核心迁移时的「只清当前版本」；源码里的标识跟着后面的改名批次处理。产品负责人没有改这个范围，只裁了其中的分歧：原 Kun 的 17 份决策记录要搬进 `docs/adr/kun/`、会上站，清不清，答「决策记录也清」。由此决策记录也在清理范围内，以后搬进 `docs/` 的原 Qian 决策记录也一样；改法照那个会话的建议，被替换的地方用方括号标出，文首说明一句，私有产品照公开仓库的规矩只写能力类别。
- D20 `CavaiLAB/kun` 的合并方式与主干保护。2026-11-18 产品负责人在迁移计划会话的提问里选「只留合并提交并保护 main（推荐）」：关掉压缩与变基合并，只留合并提交；main 禁止强推和删除，必须经 PR 合入，不要求审批；暂不设必需检查，等 B3 并好流水线、有了每个 PR 都会跑的汇总检查再加。当天已照此设置：仓库只允许合并提交，默认分支上有一条不设例外的规则集。这是迁移执行计划第 8 节列给产品负责人的「仓库设置」一项。
- D21 自托管 runner 先不接到 `CavaiLAB/kun`。2026-11-18 产品负责人在同一次提问里选「先不接（推荐）」：检查全部留在 GitHub 托管 runner 上；基准测试与对象存储实测先不接，需要时在本机跑；以后要从本仓库把镜像推到预发环境用的镜像仓库时再单独定。这是执行计划第 8 节「B3 之前定」的一项，S1-KUN-020 验收里「自托管 runner 只留基准与对象存储实测」随之改写。

2026-11-19 产品负责人对一份整体方案的十一个待定项答「十一项都按推荐定，写进平台文档」，随后对其中第 5 项另作裁定；连同当天说定的方向，记成平台级裁定 P22–P33，原文在 `CavaiLAB/jiangxin` 的 [2026-11-19 平台级裁定](https://github.com/CavaiLAB/jiangxin/blob/main/docs/decisions/2026-11-19-platform.md)。下面 D22–D26 照那份裁定的第 4 节，只登记其中与本仓库过渡目录里已接受的决策记录有出入的几条；括号里是平台级裁定的编号，「第 N 项」指那十一个待定项。ADR 与需求文档的原文都没有改；回写之前两边有出入时，以平台级裁定为准。

- D22 Agent 一级的范围（P29）。第 7 项「给『我的 Agent』挂组件用什么范围」按推荐定：加一种 Agent 一级的范围，用来给某个 Agent 长期挂组件。与 ADR-020 D20.5 有出入：S1 的范围种类是租户、应用、Agent 会话三种。新的一级与这三种谁遮蔽谁、授权范围变大时由谁确认，待定；平台文档的提议是 Agent 一级排在租户之下、会话之上，授权范围变大由主人本人确认（jiangxin 的 `docs/03-plugin-model.md` 第 9 节）。D20.5 定的是两层扁平、范围不继承，而这个提议要的是范围之间的先后，两者怎么相容要一起定。
- D23 知识库（P30）。第 8 项「知识库怎么进组件」按推荐定：组件里新增一种「知识库」内容，即一批资料连同它的整理方式。与 ADR-020 D20.6 有出入：组件的目录约定与表面里没有知识库。另有一处出入不在平台级裁定第 4 节的表里，是这次登记时核对原件发现的：ADR-016 D16.8 把私有智能体产品自有的知识库算作它的 AI 资产，权威在它那边；需求文档 §10.6 与 §12.8 把知识库列在平台的范围之外，归那个产品的 AI 资产控制面。这一处随 Q5（ADR-016 的边界改写）一起处理。知识库的格式、由谁存放、整理与检索，待定；平台文档的提议是 Kun 登记并按范围与权限过滤、SanYuanAgent 检索（jiangxin 的 `docs/03-plugin-model.md` 第 3、9 节）。
- D24 拖拽设计器缓做（P32）。第 11 项「拖拽设计器」按推荐定：缓做，先让 Agent 写，设计器以后作为第二种编写方式。与 S2 的安排有出入：ADR-012 D12.2 定 S2 交付节点树视图的流程设计器，ADR-013 的 S2 交付里有三大设计器，需求文档 §08 把表单、列表、审批流三大设计器（`qian.designer`）列为 P0，即 S2 退出标准的关键路径。设计器什么时候做、S2 里依赖设计器的部分怎么调整，待定（jiangxin 的 `docs/06-roadmap.md` 第 5 节）。
- D25 最小的一圈提前，`agent` 主体在里程碑 M1 启用（P31）。第 10 项「路线要不要重排」按推荐定：重排，最小的一圈提前。路线的里程碑 M0 至 M8 的顺序已定（jiangxin 的 `docs/06-roadmap.md` 第 2.1 节）：M0 是迁移收口；M1「能问能查」启用智能体主体，能力目录给 Agent 用，先只读。与 S4 的安排有出入：ADR-006 D6.12 定 `agent` 主体 S1 设计到位、S4 启用；ADR-016 D16.9 把 Agent 调用平台能力的路径排在 S4；需求文档的阶段划分（§15）与 §12.8 把 S1–S3 的 AI 范围限定为模型服务网关。本看板的四个阶段与在途的里程碑怎么对应到路线的里程碑，待定（同一篇第 5 节）。
- D26 应用互通的缺省（P26）。2026-11-19 产品负责人说「所有发布的应用（或者叫插件可能更合适），它们之间都是可以互相通讯的」；缺省按第 4 项的推荐定：应用提供的能力与事件在目录里看得到，调用与订阅按声明、经批准放行。「在目录里看得到」与 ADR-020 D20.5「被过滤掉的项既不出现在目录与提示词里，也拒绝执行」是什么关系，待确认。平台文档提议的读法（jiangxin 的 `docs/10-app-interop.md` 第 6 节）：看得到的是本租户里做构建与安装的人，以及替他们干活的 Agent，用来写声明；运行时不变，每个主体看到的目录与工具照旧按范围过滤。与 ADR-014 没有出入：开通与升级时逐项批准组件向平台申请的权限是现行的决策，P26 的缺省与它一致；应用之间的调用与订阅怎么并进这份申请，是提议。

平台级裁定第 4 节还记了两处没有出入：ADR-014，见 D26；ADR-010 的网关分层与 ADR-016 D16.9 的 Agent 调用路径，本次不改流量路径，D25 改的只是启用的时点。

2026-11-19 产品负责人就构建并轨（B3，S1-KUN-020）事后复核提出的一项另作决定，与合并蓝图 ADR-023 D23.14 第 4 点有出入，记为 D27，写法同 D22–D26。ADR 的原文没有改；回写之前两边有出入时，以本条为准。

- D27 过渡期禁用符号与数据层分析器的作用域。对「过渡期把这 14 个包接回分析器吗？」答「接回去」：包还在过渡目录 `_import/qian/` 下的这段时间，该目录下的项目全部接入禁用符号清单（RS0030）与数据层分析器（现行文档里叫平台分析器，QIAN0002–QIAN0006），内核档的包也在内；各域批次把包搬出过渡目录时再按归属收窄。与 ADR-023 D23.14 第 4 点有出入：那里写的是把规则的作用域收到平台档与宿主。起因是构建并轨的 CavaiLAB/kun#34 按这一点收窄之后，过渡目录下 14 个内核档的包不再受检；事后复核指出，它们失去的规则里 QIAN0003、QIAN0004、QIAN0005 是安全类规则，而「Kun 旧类型上的 `Obsolete` 诊断号照旧报错」这条兜底对清单里禁止令牌透传的两个符号不成立，这两个符号没有标 `Obsolete`。这 14 个包不定义被禁的类型，接着零命中，目前没有代码违反这些规则。落地在 CavaiLAB/kun#35：接入的项目恢复为 107 个，正好是过渡目录下的全部。没有出入的部分：仓库根上 Kun 的项目照旧不接，D23.14 第 4 点要避免的「拦住被禁类型自己的定义」不受影响；平台档的包与宿主照旧受检。按归属收窄的做法随各域批次定（S1-KUN-021）；过渡目录搬空之后，这处出入随之消失。

### 执行中定下的出入

2026-11-19 合并的执行批次 B7（S1-KUN-026）在已裁的范围内定下两项，已告知产品负责人，与合并蓝图 ADR-023 D23.9 有出入，记为 D28、D29，写法同 D27。ADR 的原文没有改；回写之前两边有出入时，以本条为准。

- D28 Principal 一组的契约进新包 `Kun.Security.Abstractions`，实现留 `Kun.Security`（B7，S1-KUN-026）。`Principal`、`DelegationActor`、`PrincipalKind`、`IdentityClaimNames` 与 `PrincipalKind` 的 JSON 转换器从 `Qian.Identity.Abstractions` 挪进新建的内核契约包 `Kun.Security.Abstractions`（零依赖，AOT 兼容，命名空间 `Kun.Security`）；转换器随之改为公开类型，因为身份契约的 JSON 源生成上下文要跨程序集引用它。服务间令牌的契约校验照表并进 `Kun.Security`。与 ADR-023 D23.9 有出入：「身份、安全、网关」表写的是 Principal 与声明词汇表并进 `Kun.Security`，全表 84 个包；这样做之后是 85 个（内核 41、平台 44）。理由：`Kun.Security` 记内核提供者，照字面放进去，公共表面带 Principal 的两个契约包（`Qian.Identity.Abstractions` 与 `Kun.Plugin.Sdk`）就要直接依赖提供者，违反 D23.7 保留的 seam 三角色（ADR-020 D20.4，`specs/component-model.md` §6：契约只依赖 `Kun.*.Abstractions`，无实现）与依赖门禁的规则 D，而 S1-KUN-026 的验收不许为此新增例外。新包的名字照 D23.8 第 2 点（`.Abstractions` 是契约），命名空间照表上的 `Kun.Security`，域与实现的去处不变。`Kun.Core` 的 `ICurrentUser` 端口不加 Principal 成员；库模式从声明读主体，解析规则在 `Kun.Security` 里并成一份，B8 的缺省执行端口与服务间令牌校验共用。

- D29 身份客户端保留平台职责（B7，S1-KUN-026）。ADR-023 D23.9 将身份客户端描述为薄外壳。主体、服务认证和会话的实现并入 `Kun.Identity.AspNetCore`；`Kun.Identity.Client` 保留平台依赖方服务、人员和成员查询端口、会话吊销与连接器端口，以及浏览器端点、组件注册和配置。内核继续通过依赖方身份与会话端口工作。

- D30 运行时类型化配置契约（S1-KUN-022）。`Kun.Runtime` 对外标记支持 NativeAOT。`IKunPlugin<TConfig>` 的实现提供采用 Web 约定的源生成 `JsonTypeInfo<TConfig>`，运行时在进入组件前完成配置绑定。非泛型组件仍可读取 `JsonElement`。
- D31 权限内核的数据过滤端口（S1-KUN-027）。`IDataPermissionFilter.GetExpressionAsync<T>` 提供进程内过滤表达式；移除 `DataPermissionPredicate` 与 `GetPredicateAsync`。序列化的数据范围规则使用数据契约的过滤 AST。角色之间取 OR，各数据范围方案之间取 AND。HTTP、gRPC、命令和配置入口改用 `AuthorizationSubject`，并显式传递身份修订与委托状态。gRPC 通过标记接口识别共用的权限拦截器。

### 带出的其它待定

- Q5 SanYuanAgent 进入产品族。ADR-016 按两个产品划边界：平台不写 Agent 运行时，Agent 运行时归 iClaw。现在 Agent 引擎是平台的第三个框架，这条边界要改写；分工本身（.NET 一侧不实现 Agent 循环）可以不变，变的是引擎的归属。iClaw 其余部分的去向待定。S1-DEC-034 D4 问的「Agent SDK 指什么」，是否就是 SanYuanAgent，待确认；D10 说 SanYuanAgent「应该是一个独立运行的 SDK」，两者很可能是同一个东西，但产品负责人没有明说。蓝图的「许可全部改 MIT」（D23.11）没有覆盖 Python 引擎：核心保持 Apache-2.0（D15），仓库已公开（D16）；服务层与媒体适配层的许可待定。
- Q6 Agent 协同的机制（D6）。要定的有：Agent 的归属与身份（contracts/v0 的主体类型里已有 `agent`，标为 S4 预留、S1 不签发；委托链见 ADR-016 §6）；Agent 之间的消息走什么通道、带什么信封；由谁审、审在收件一侧还是发件一侧；审过之后的授权范围与审计。规划稿在 `CavaiLAB/jiangxin`，都是提议，没有经过确认。
- Q7 可见性与发布。`idadawn/kun`、`idadawn/qian` 是公开仓库，内核档的包发在 nuget.org、许可 MIT。新仓库起初对内，2026-11-17 已改为公开（D16），「何时公开」不再待定。还要定的是：代码导入新仓库之后，nuget.org 上的包何时改指新的源码地址。

- Q8 设备上的本机模型与 ADR-015（D11）。ADR-015 D15.5 不绕过模型网关直连推理层，D15.10 不允许应用直连模型端点，为的是统一计量、限流与租户隔离。D11 说机器人本地可能有小模型，设备上的本机模型过不了模型网关。推荐：登记成一条明确的例外，只限设备本机地址上的模型；用量由引擎记录后上报平台，和模型网关计的分开；ADR-015 的其余条目不变。另有一处要定：设备上的 Agent 调平台的模型与能力走哪条路。ADR-010 D10.1 / D10.10 与 ADR-016 D16.9 已定模型与 MCP 流量走 Higress，不经 `qian.gateway`。推荐照此不变：设备带 `agent` 主体的短期令牌调 Higress 上的模型与 MCP 路由，不给设备发长期的模型密钥。设备是不可信的调用方，consumer 不能像 D15.4 那样由调用方自己生成，要由 Higress 从校验过的令牌里取；这要求把 `agent` 令牌的校验交给 Higress，D10.10 / D15.6 只说了 S1 不做，`agent` 主体启用时（见 Q6）怎么办要定。备选是设备的调用都经 `qian.gateway` 转交，设备一侧只有一条路，但与 D10.1 的分层有出入。推荐都是主会话的意见，没有实测。

2026-11-19 补：Q6 里「由谁审、审在收件一侧还是发件一侧」已由平台级裁定 P28 定下：每个 Agent 发出去的内容都要由人审核，发给 Agent 的内容也是（D6），起步出站、入站两道都必审；「发出去」包括发给别的 Agent、发给别人、写外部系统三类。过渡目录里没有与它相反的决策记录，所以不另编 D 号。Q6 的其余几项仍是提议，见 jiangxin 的 `docs/04-agent-collaboration.md`。
