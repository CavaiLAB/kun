## 背景

自 [S1-AZ-005](S1-AZ-005.md) 拆出，是[契约草案](../../docs/prd/specs/authz-remote-interface.md)第 13.1 节四个里的第二个。原任务背景里的「角色与授权 CRUD」归这里，连同管理用的权限点：授权变更操作标 `write` + `confirm`，授予平台超管标 `humanOnly`。它承接原任务验收的第 3、6 条，与第 5 条里说端点的那一半。优先级沿用原任务的 P0；排期后来问过，产品负责人 2026-11-26 定（[S1-DEC-048](S1-DEC-048.md) D4）：优先级这次都不动。

最小角色授权页不在本仓库里做了（S1-DEC-048 D2）：页面放匠心的管理端，本仓库只交付接口，[S1-AZ-023](S1-AZ-023.md) 关闭。在那一页做出来以前，给人授角色只有本任务的端点，没有页面。

这一部分不在契约草案里展开，草案也没有改它的范围；它不等远程授权接口的契约定稿。

S1-AZ-005 的进度日志里登记过给这一部分的接口与口径，开工前先读。要点：

- 管理端点建在已有的授予端口上：`ITenantRoleGrant` 的 `AssignAsync` 与 `RevokeAsync`，撤销租户最后一个成员管理绑定时返回 `AUTHZ_LAST_ADMIN_LOCKOUT`。
- 授予平台超管走平台角色存储，必须在没有租户上下文的平台流程里。
- 角色与权限目录的两个读接口（`GET /api/authz/roles`、`GET /api/authz/permissions`）有一份界面组件一侧的草案契约，接线时以本任务为准。
- 解释别人要校验调用方持有授权管理权限，不能把别人的角色当公开信息返回；跨租户的主体不带命中的信息。本人解释自己在 [S1-AZ-020](S1-AZ-020.md)。

## 验收

- [ ] IT：角色与授权的增、改、撤经 HTTP 可用，建在已有的授予端口上；管理用的权限点登记进权限目录；防自锁照现行。这一条是拆分时新写的，原任务没有单列
- [ ] UT（承接 S1-AZ-005 验收第 3 条）：授予平台超管的能力标 `humanOnly`；授权变更标 `write` + `confirm`
- [ ] IT（R103，承接 S1-AZ-005 验收第 5 条里端点的那一半）：Authz API 列出的租户成员不含平台超管；超管经旁路访问不在租户内产生角色、绑定或成员记录（ADR-006 D6.11）
- [ ] IT（R163 ⑤ 的延伸，承接 S1-AZ-005 验收第 6 条）：恢复本租户删过的成员时，除 `tenant.user` 外撤销他的全部角色绑定，含本任务引入的组件角色与自定义角色；`granted_roles` 与实际一致，身份 README 恢复原成员那一条同步
- [ ] IT：持有授权管理权限的人可以解释别人的一次判定，没有这项权限的被拒；这样的解释留审计。这一条是拆分时新写的，依据是 S1-AZ-005 日志里 2026-10-16 登记的口径
