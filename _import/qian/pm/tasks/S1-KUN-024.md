## 背景

合并阶段 3（S1-KUN-021）的第 2 批，迁移执行计划（仓库根 `docs/migration-plan.md` 第 4 节）的 B5，对应合并蓝图 ADR-023 D23.9 第二张表「数据、租户、权限」里的数据与租户部分，权限部分在 B8（S1-KUN-027）。租户号只收 Guid 在这一批落地（D23.5、D23.20）。命名照 D23.8，档位照 D23.7。

表外几件事：

- 租户号。租户上下文端口是 Kun.Core 的 `ITenantContext`（`src/Kun.Core/MultiTenancy/ITenantContext.cs`）：`TenantId` 现在是 `string?`，`BeginScope` 收 `string?`。缺省回落在 Kun.MultiTenancy 的 `KunMultiTenancyOptions.FallbackTenantId`，缺省值 `"default"`。改为 `Guid`、去掉回落、缺租户即拒绝，与 ADR-004「租户上下文只来自令牌、缺失即拒绝」一致；`contracts/v0` 的服务间令牌与事件信封本来就把 `tenant_id` 定为 Uuid。主干上 `ITenantContext` 出现在 246 个 C# 文件里（仓库根 62 个、过渡目录 184 个），这一项是全仓库的改动，单独一个 PR。分布式 ID 的做法保留：缺省 Guid v7，要数值主键的地方用雪花算法，WorkerId 经 Redis 租约分配（D23.20 第 2 点，PRD 7.6）。
- Kun.Infrastructure 的前置与归档都在这一批。主干上引用它的是 Kun.EntityFrameworkCore（`EfRepository.cs`、`SpecificationEvaluator.cs`，即旧仓储与规约求值器；`tests/Kun.IntegrationTests/Repository/SpecificationEvaluatorTests.cs` 测的就是后者）、AOT 冒烟宿主与门禁样例 `bannedapi/LegacyRepository`。先从 Kun.EntityFrameworkCore 摘掉这两个文件，再归档：移出解决方案与 AOT 清单，`BannedSymbols.txt` 里它的 3 条与那个门禁样例相应调整。
- 停发的 8 个 Kun 包名（D23.9）里，Kun.Infrastructure、Kun.Dapper、Kun.MultiTenancy.EntityFrameworkCore 在这一批。
- 测试、工具随域：过渡目录 `_import/qian/tests/` 下的 Qian.Data.Tests、Qian.Data.Abstractions.Tests、Qian.Data.AspNetCore.Tests、Qian.Data.Native.Postgres.Tests、Qian.Data.Native.Postgres.AotTests（不在解决方案里）、Qian.Tenancy.Tests、Qian.Tenancy.Signup.Tests、Qian.Common.Tests（租户字段与 schema 规则），`_import/qian/tools/Qian.Data.Native.Probe`；仓库根 `tests/` 下的 Kun.MultiTenancy.Tests、Kun.EntityFrameworkCore.Tests、Kun.Dapper.Tests（随 Kun.Dapper 归档）。过渡目录里随这一批搬出的 .NET 项目共 20 个（11 个包、8 个测试、1 个工具）。

开工前要补的事：

- 蓝图 §1.2 的未核实事项没有落在这一域的。
- 档位按依赖图复核（仓库根 `scripts/check_deps.py`，项目文件里的 `KunTier` / `KunRole`）：
  - Qian.Data.Abstractions（平台契约）拆成两半：EF 部分并入内核档的 Kun.EntityFrameworkCore，其余是平台档的 Kun.Data.Abstractions。它上面两条规则 D 例外（→ Kun.EntityFrameworkCore、→ Kun.MultiTenancy.EntityFrameworkCore，`Until="B5"`）随之去掉。
  - Qian.Events 上两条规则 K 例外（→ Qian.Data.Abstractions、→ Qian.Tenancy.Abstractions，`Until="B5"`，最晚 B6）：它用的是 `QianDbContext`、`IDataContextCatalog`（Outbox 写入端与投递循环）与 `ITenantContextPropagator`（订阅端恢复租户上下文）。严格基类与 `IDataContextCatalog` 落进 Kun.EntityFrameworkCore、上下文传播移到 Kun.MultiTenancy 之后，Qian.Events 改指内核档，两条都能在这一批去掉；`IDataContextCatalog` 若留在平台档的 Kun.Data.Abstractions，第一条留到 B6。
  - 新包 Kun.EntityFrameworkCore.PostgreSQL 记内核档；Kun.MultiTenancy 吸收的上下文传播与严格入口边界不能带进平台档的依赖。
  - 若 B4 留下了 Qian.Plugin.Sdk → Qian.Data.Abstractions 那条例外，这一批去掉。
- 重复实现的位置：模型缓存键工厂是 Kun.EntityFrameworkCore 的 `MultiTenancy/TenantAwareModelCacheKeyFactory.cs` 与 Kun.MultiTenancy.EntityFrameworkCore 的 `KunMultiTenantModelCacheKeyFactory.cs`；租户过滤在 `KunDbContext.cs` 与 Kun.MultiTenancy.EntityFrameworkCore 的 `ModelBuilderExtensions.cs`。
- EF 迁移：这一批第一次把带 `Migrations/` 的项目搬出过渡目录，仓库根的 `.editorconfig` 要补过渡目录那份里把 `**/Migrations/*.cs` 当生成代码的一节；迁移里写死的全名跟着换，核对生成的 SQL 不变。
- 平台分析器 QIAN0003（非测试的 DbContext 必须派生自严格基类）按 `Qian.Data.QianDbContext` 这个全名找类型，找不到时会把接了分析器的项目里每个 DbContext 都报成违规，严格基类另起名时跟着改；data、events 两组门禁样例引用 Qian.Data.Abstractions，跟着改。
- 对前端有没有影响：`plugins/` 下数据与租户组件的清单（qian.data、qian.data.native、qian.data.dialect.pg、qian.tenancy、qian.tenancy.signup）里写着入口类型与程序集名，随包换；组件 id 不变。改之前先看。
- 文档：两个归档与租户号的改动会改到仓库根 `README.md`（归档名单一句）、`docs/` 里讲读侧、多租户与行级安全的页面，以及根 `AGENTS.md` 的运行时约定（读侧用 Kun.Dapper、租户号只收 Guid 是 B5 的事）。

估算 11d（10–12 人日），依据是在主干上量的：

- 来源 16 个包：过渡目录 11 个共 9310 行（其中迁移 1516 行），仓库根 5 个共 2421 行（非空行）；公共 API 2322 行（过渡目录 2089，三个契约包各 632、587、663）；测试与工具 12 个项目共 6557 行；要搬出 20 个项目。
- 换包名要扫的面：出现这一批 Qian 名字的代码、构建、清单与脚本文件 480 个（其中 .cs 342 个）；C# using 284 行，分布在 230 个文件；带 Qian 前缀的类型与成员名 41 个，七批里最多（如 `QianDbContext`）。租户号另扫 `ITenantContext` 的 246 个文件。
- 要合一的有 5 处：入口处建立租户范围的代码（3 份）、隔离策略枚举（2 份）、EF 三处并一、Kun 内部的租户过滤与模型缓存键工厂（各 2 份）。另有契约包一拆二、新包、两个归档与 4 条例外。
- 分配：换包名与搬目录 2d，EF 三处并一（含严格基类、过滤与缓存键）3d，契约拆分与新包 1.5d，租户号、入口与枚举 2.5d，Kun.Infrastructure 的前置与两个归档 1d，全量测试与文档 1d。
