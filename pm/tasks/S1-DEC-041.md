## 背景

2026-11-25 产品负责人对平台的整体蓝图和三个要实现的场景作了一批裁定，原文记在 `CavaiLAB/jiangxin` 的 [2026-11-25 平台级裁定](https://github.com/CavaiLAB/jiangxin/blob/main/docs/decisions/2026-11-25-platform.md)（P57–P74）。其中几条与本仓库已接受的决策记录有出入，或者要在本仓库记一笔。本任务照 [S1-DEC-038](S1-DEC-038.md) 里 D22–D26、D37–D48 的写法登记它们，括号里是平台级裁定的编号。ADR 的原文不改：对应的 ADR 末尾追加带日期的小节，受影响的条目前加标注。需求文档里受影响的小节加带日期的修订注，原文不删。

引号里是产品负责人的原话。「甲 1 至甲 3」是蓝图草稿里与旧决策有出入的三项的编号。「单机版」指给小企业的、一台服务器上能跑的部署，产品负责人 2026-11-24 的原话是「有些企业可能比较小，能不能同时适配一个小型的企业在单机上可以跑的，大模型通过 API 进行调用。」；「企业版」指跑在集群上的全套部署。两个版本各装什么，除 D2、D3 以外都是提议。

### 裁定（产品负责人，2026-11-25）

- D1 运维侧的登录也接 Kun 的身份服务（P57）。问的是「与旧决策有出入的甲 1 至甲 3，都按提议定吗？」，答「都按提议定」；这是甲 1。交付给客户的产品里，运维侧各个控制台的登录也接身份服务，不带 Authentik；每个控制台保留一个本地的应急管理员。与 ADR-017 D17.11 有出入：那里写「客户 CIAM = `qian.identity`；运维侧 = Authentik」。同一口径的还有 ADR-017 D17.3、ADR-005 D5.7 与 ADR-007 D7.1 里 Portal 的登录。范围是交付给客户的产品；现有环境运维侧的身份提供方先不动，等身份服务稳定以后再换。
- D2 单机版默认不装 Apollo（P58）。同一句答复；这是甲 2。企业版照旧装。单机版默认读配置文件，要在运行期改配置的客户可以加装。与 ADR-007 有出入：第 1 节开头写「Apollo 是硬性要求」，D7.1 把它定为 L1 共享的平台组件；ADR-017 D17.3 的 L1 清单里也有它。
- D3 单机版里身份与平台同一个进程（P59）。同一句答复；这是甲 3。单机版里身份服务与平台服务同一个进程，网关仍独立成进程；企业版仍是三个进程分开。与 ADR-017 第 10 节有出入：那里把同进程定为只用于 staging 的过渡形状，写「生产不采用这个形状」。
- D4 工作区的域名不经过本仓库的网关（P64）。问的是「工作区这个域名的入口，由谁来接？」，答「工作区服务直接接」。匠心的 Web 端分成管理系统与 Agent 工作区两块，放在两个域名上（P63）。工作区的域名由匠心的工作区服务直接接：它装本仓库发布的登录组件 `Kun.Identity.Client` 认人，登录仍然到身份服务，本仓库不用改；管理系统的域名照旧过网关。另一条路是先补网关、再让工作区走它，没有选。与 ADR-010 D10.1 有出入：那里定的是三层网关，业务 API 的边界在 `qian.gateway`。这是有意的偏离，原因写在 ADR-010 第 9 节。
- D5 匠心的管理端在浏览器一侧用 Cordis（P65、P66）。产品负责人说管理端也要支持 Cordis，管理端的内容要能显示在 DSH 右侧的页签里，原话「主要我想让管理端也能支持 Cordis，还有，我管理端最终其实也想在 DSH 的右侧展示一些内容，可以通过 table 页签这种形式。举个例子，我想生成一个什么什么系统，然后在右侧可以生成界面并进行发布。」（「table 页签」读作「tab 页签」）；又对「管理端只要浏览器一侧，这样定吗？」答「这样定」。管理端的界面是浏览器里的 Cordis 应用，页面是只有浏览器一半的 Cordis 插件；管理端里不设多人共用的 Node 运行环境。与 ADR-020 没有出入：第 4 节放弃的是「直接采用 Cordis 作为 .NET 侧的运行时」，D20.11 写的是不把 Cordis 的源码搬进 .NET，说的都是服务端。记一笔，免得以后被读成相冲突。
- D6 Kun 的定位（P60）。原话「我想 Kun 是一个通用的组件，Jiangxin 首先是一套企业级的管理系统+Agent」「例如，Kun 提供一些登录等组件，但是不负责任何业务，最终的界面肯定是要放到Jiangxin 也可以放到另外一个库。」Kun 是通用的组件，提供登录这类组件，不负责任何业务；最终的界面放在匠心，也可以放到另一个仓库。与合并蓝图 ADR-023 的定位没有出入，说得更细。
- D7 标了要人确认的能力，平台自己停下来等人点（P73）。给产品负责人列的表里，这一行是「Agent 调要人确认的能力时，平台自己停下来等人点」，提议是「照这样定，并回写 Kun」；表下面写明这一件与本仓库已接受的写法有出入。问的是「与 Kun 现行写法对不上的两处，都按提议定吗？」，答「都按提议定」。能力条目上 `agent.requiresConfirmation` 为真的能力，调用方不是人本人时（是 Agent，或者带着委托链），平台自己不执行，生成一条等人输入的任务，等人点；人点了平台才执行。等人输入的任务就是 [PRD 第 8 章](../../docs/prd/08-s2-lowcode.md) 8.12 节的 Operation，状态 `input_required`。人自己在界面上直接调同一个能力不拦。与 [ADR-016](../../docs/adr/ADR-016-agent-boundary.md) D16.3 (c) 有出入：那里写「［下游智能体平台］据此生成默认 ToolPolicy，运行时权威仍是［下游智能体平台］的 ToolPolicy / RiskGate」。同一口径的还有 [PRD 第 10 章](../../docs/prd/10-s4-agent.md) 10.3 节「范围与边界」的末一条、10.1.2 节表的第一行与 10.6 节表的第二行。需求文档里另有三句与 D7 同向的话，都没有展开成契约：10.3 节「危险操作 Agent 只能发起申请（「待确认票据」契约）」；[PRD 第 13 章](../../docs/prd/13-security.md) 13.5 节把 confirm-required 解释为「Agent 发起时平台返回 `input_required`，由人确认后继续」；3.10 节的例子「Agent 调用一个需人工确认的工具，同样收到 `input_required`」。范围是整理者的读法：只定了这一件，没有把 ToolPolicy / RiskGate 整个搬到平台；D16.3 与 10.3 节在别的事情上照旧，调用方自己的策略可以更严。
- D8 等人点头的任务上的动作，缺省只能人做（P74）。同一句答复。表里这一行是「等人点头的动作，缺省只能人做」，提议是「照这样定；Agent 代办以后要用再单独放开」；表下面同样写明有出入。等人点头的任务上的动作，缺省只能人做；Agent 代办不是缺省，以后要用再单独放开，怎么放开没有定。与 [ADR-012](../../docs/adr/ADR-012-workflow-engine.md) D12.7 有出入：那里只把签名类动作标 `humanOnly`，转审、协办、撤销在 S4 前对 Agent 禁止；其余动作在有效权限之内 Agent 可以代办。同一口径的还有 PRD 8.8 节「Agent 契约」里 Agent 代办的一条与验收的末一条（「以 Agent 主体（委托某用户）调用 `actions/approve` 成功」），以及 13.5 节表里「流程：同意 / 拒绝 / 退回（Agent 代办）」一行。8.12 节没有相反的话：那里写 `humanOnly` 的输入动作对 Agent 不可用，没有写缺省；按 D8，等人点头的任务上的动作缺省对 Agent 不可用。范围是整理者的读法：说的是任务上的动作这一层（8.8、8.12 节），不是冻结契约里能力那一层的 `humanOnly`，即 `agent.expose: false`（`contracts/v0/README.md` 第 8 节第 8 条）。

### 没有出入的与没有定的

- 平台级裁定里另外几条不单独登记。P61 把产品的部署清单放在 `jiangxin` 的 `deploy/`，只定了 base 放在哪；ADR-017 D17.1 的约定与 D17.6 的每个客户一套 overlay 照旧。P62、P63 说的是每人一个 DSH 实例与 Web 端的形状，是匠心一侧的服务，本仓库不用改。
- P67 至 P72 是同一天对三个场景（应用市场与生成应用、平台的定位、对话里的审批）定下的几条：生成的应用界面只能是数据描述，等人点头的事记在平台、确认卡的点击由浏览器直接交给平台，审批时模型默认不参与，以及这几样的先后。本任务没有把它们登记成 D 项，ADR 也没有动：
  - 生成的应用（P67）与本仓库的现行规格没有出入，照的是 [PRD 第 10 章](../../docs/prd/10-s4-agent.md) 10.4 节与[组件模型规格](../../docs/prd/specs/component-model.md) 11.1、11.2 节。
  - 等人点头的事（P68、P69）用的任务模型是 [PRD 第 8 章](../../docs/prd/08-s2-lowcode.md) 8.12 节的那一种，即 `input_required` 的 Operation。那边写的做法原有两处与本仓库现行的写法对不上，产品负责人 2026-11-25 已裁定，登记为 D7、D8（P73、P74）。
  - 这几节都还没有实现，D7、D8 也是：`agent.requiresConfirmation` 现在只登记在能力条目上，平台不按它拦调用。看板上相关的只有预留 Operation 契约的 [S1-RT-007](S1-RT-007.md) 与验证主体模型和委托链的 [S1-AGT-003](S1-AGT-003.md)，都没有动；没有新建实现任务。
- D7、D8 那句答复没有覆盖的，都没有定：
  - 接口的形状，即路径、字段、回什么状态、错误码怎么登记，是提议，随契约定稿。冻结的契约 `contracts/v0` 这次没有动；那里的对齐差异说明第 4 节引 D16.3 (c) 的一句，照 D7 读。
  - Agent 代办怎么放开。
  - 起步的办法：`agent` 主体启用之前，先用一个代替它的调用方来演示还是等它；演示用的那条要人确认的能力放哪；谁做、什么时候做；拆出来的任务进不进看板。
  - [S1-DEC-038](S1-DEC-038.md) 的 Q5，即 ADR-016 的边界怎么改写：这次只定了 D7 这一件，Q5 其余的仍然挂着，「Agent SDK 指什么」、服务层与媒体适配层的许可、D23 里知识库的归属都没有新的裁定。
- 蓝图草稿里其余的内容是提议，没有裁定，不在本任务里回写：两个版本各装什么，配置中心是否改用 Nacos（评估的建议是维持 ADR-007，产品负责人没有表态），Agent 运行时以后可替换。它们列在那份平台级裁定的第 6 节。
- 本仓库里现有的应用外壳与界面包以后怎么用，没有定，仍是匠心 2026-11-21 裁定 P42 留下的待定项。看板上相关的任务没有动。
