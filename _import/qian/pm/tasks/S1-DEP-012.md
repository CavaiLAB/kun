## 背景

R167（S1-DEC-037）的第一步。system 级预装组件的文件夹变了而版本号没变时，系统组件修订 Job 在已有数据的库上必然失败：权限目录按组件版本不可变，Lifecycle 也不让同一版本对应两个制品。只升版本又会让已有租户静默失去该组件的权限，要等第二步 S1-DEP-013 补上。本任务先把同版本换内容挡在合入之前，并让 Job 在租户还停在旧版本时报错，而不是静默放行。做法见[决策文档](../../../../docs/decisions/system-component-same-version.md)第 3 节 A，以及 R167 ②、④。

## 验收

- [ ] 门禁脚本：复用 `scripts/sign-system-revisions.py` 的目录摘要算法，按与签名清单同一口径的 system 级 module 组件、整个文件夹（含 README）比较。摘要相对基线变了而 `plugin.json` 的版本没变即失败，报出组件名并提示升版本；版本低于基线也失败；基线里没有的新组件放行。门禁跑在 docs-and-pm 工作流里，签名脚本签名前再查一遍。
- [ ] 基线文件入库（暂名 `deploy/images/released-components.json`，记组件 id、版本、摘要与源码提交），初值取 staging 现部署的 `9399cf9584`；它与 main 的 system 级组件文件夹一致时，不需要升任何版本。运维手册第 4 节加一步：部署后随部署登记的 PR 更新基线。
- [ ] 修订 Job 护栏：有租户开通在别的版本上时拒绝激活新版本，报出组件、版本与受影响的租户数，退出码 1。`PlatformSystemRevisions` 注释里的「新摘要安装后激活」改成只在升了版本时成立的写法。
- [ ] 宿主诊断：平台插件树未就绪时，先报 Failed 的条目与错误码，再报 Pending 的条目和它在等的服务键。今天只报第一个未就绪的条目，内层异常可能为空。
- [ ] 用例：
  - 门禁自测（`tests/gates/`）：同版本改摘要失败、升版本通过、版本回退失败、只改 README 也算改动、新组件放行、基线文件格式；
  - 同一个库先用 V1、再用 V2'（X 的文件夹变了、版本仍是 1.0.0）跑 Job，尽快失败，错误里点名 X 与目录冲突；
  - 有租户开通在 X@1.0.0 时换成 X@1.1.0，护栏拒绝激活。
- [ ] 文档：版本规则（只改文档升修订号，加权限点或可选字段升次版本，破坏性变化升主版本）写进 `plugins/README.md` 与运维手册；Lifecycle、Authz 的 README 写明门禁与护栏。平台宿主 README 按 R167 更正两处：Job 一节的「新摘要安装后激活」只在升了版本时成立；「已知限制」里「跨版本升级 fail-closed」改为决策文档第 2.4 节核实的情况（运维手册第 9 节已随 S1-DEC-037 的登记更正）。
