## 背景

产品负责人 2026-11-27 发来的新方向（登记在 [S1-DEC-051](S1-DEC-051.md)）定了次序：「先列清各个包的去向，修订文档，再用登录页跑通前后端流程。」登录页在匠心重新设计，Kun 继续负责认证、会话和权限。本任务做第三步里 Kun 这一侧要补的，接口进公开契约是 [S1-IDP-031](S1-IDP-031.md)，页面与身份服务怎么接是 [S1-IDP-032](S1-IDP-032.md) 的设计，这两件不在本任务里。

要补的（整理时列的，开工时照 S1-IDP-032 的结论改）：

- 匠心的开发者在本机起一个能登录的身份服务：现在有 `tools/Kun.Dev.Shell`（连旧外壳一起起）与 `tools/Kun.Dev.TenantOps`（起运营宿主与身份发行方，不起页面），都绑着旧的界面或运营场景；要一个只起身份服务、带种子账号、能让匠心的页面接上的办法。
- 一个能跑的示例：照 S1-IDP-031 的契约走一遍登录、选择租户、拿到会话、调一个要权限的接口，放进 `samples/`，平时跟着源码编译运行（比照 [S1-DOCS-012](S1-DOCS-012.md) 的做法）。
- 跑通以后，本仓库旧登录页的检查换成什么（[S1-QA-033](S1-QA-033.md) 里留着的那部分）。

种子账号与密钥只用本机生成的测试值，不写进文档与示例的明文。估时是整理时的估计。

## 验收

- [ ] 有一个只起身份服务的本机办法，带种子账号，匠心的页面照公开契约能接上；用法写进对应的 README
- [ ] `samples/` 里有一个能跑的登录示例，照公开契约走完登录、选择租户、拿会话、调一个要权限的接口，CI 里跟着源码跑
- [ ] 与匠心那一侧的登录页一起跑通一次，结果记进日志；旧登录页的检查换成什么写进 S1-QA-033
