## 背景

2026-11-17 产品负责人提问：「评估一下 Kun 和 Qian 是否可以合并为一个框架。」合仓此前被否决过三次：ADR-001 §4、ADR-021 D21.2、框架细化备忘录 §3.3 (d)。主会话按当日的代码重核后，认为当时的理由大多已不成立，产品负责人随后裁定合并，并定了方向。

### 裁决（产品负责人，2026-11-17）

依次四句：

1. 「那就 Qian 并入 Kun 这个框架。」
2. 并入范围在两个选项里选了「包名也并成 Kun.*」：搬进 kun 仓库，同时 `Qian.*` 改名为 `Kun.*`，一个包族、一条日历版本线。
3. 「但是，不是单纯的合并。在合并的过程中，要考虑到一些复用的东西。可以将两个库进行合并，重新定位 Kun 这个框架。」
4. 「租户号统一用 Guid。」

据此记为五条已裁：

- D1 方向：Qian 并入 Kun，合并后的仓库是 `idadawn/kun`。
- D2 包族：`Qian.*` 并入 `Kun.*`，一个包族、一条日历版本线。
- D3 合并方式：不是原样搬运。合并时清点两边重叠与可复用的部分，同一职责合成一份。
- D4 定位：Kun 重新定位，不再只是 Qian 之下的底座 SDK。
- D5 租户号：统一用 Guid。Kun 现在接受任意标识并在缺租户时回落到 `default` 租户，合并后只收 Guid、去掉缺省回落。

合并蓝图的初稿是 [ADR-023](../../docs/adr/ADR-023-kun-qian-merge-blueprint.md)（Proposed），下面「两边重叠的初稿」与「待定」两节已被它取代：初稿只按包名整理，蓝图按分域核实的结果重写了归并对照，并逐条回答了 Q1–Q9。蓝图确认之前不动代码与仓库结构，ADR-001、ADR-019、ADR-020、ADR-021 与 `AGENTS.md` 的现行规则照旧执行。

### 原先的否决理由与现在的情况

| 当时的理由 | 出处 | 2026-11-17 的情况 |
|---|---|---|
| 跨仓库源码引用下，Kun 的破坏性变更直接打断构建 | ADR-001 §4 | 同仓之后变更与修复在同一个 PR 里过 CI，这条不适用 |
| 镜像构建依赖私有仓库 | ADR-001 §4 | kun 与 qian 都已是公开仓库 |
| 第三方无法依赖源码 | ADR-001 §4 | 第三方仍然只装包，合并不改变这一点 |
| Kun 有独立下游与发布节奏 | ADR-021 D21.2 | Kun 10 月以来 22 个非合并提交里 18 个带 Qian 任务号；10 月发了 11 个 tag，Qian 的 `KunVersion` 同期换了 10 次；11 月至评估日没有提交 |
| 单人维护下合并只会放大耦合 | ADR-021 §3 | 耦合已经在：Qian 以 `[$(KunVersion)]` 精确钉版，每次修复都多走一轮 Kun 发版与 Qian 升级 |
| 两套版本线与许可二选一会破坏 iClaw 的还原 | 备忘录 §3.3 (d) | 版本线已裁为一条（D2）；许可见 Q4，iClaw 见 Q9 |

代码层面两边已是一套词汇：Qian 的 56 个包项目里 23 个直接引用 Kun 包，`ITenantContext` 在全仓库出现 352 行，`QianDbContext` 继承 `KunDbContext`，24 个公共 API 清单文件里有 72 行 Kun 类型。

### 两边重叠的初稿（D3 的起点）

按包名与项目的直接引用整理，没有逐个读实现，蓝图里要逐行核实。

| 职责 | Kun 模块 | Qian 包 | 现在的关系 |
|---|---|---|---|
| 错误模型与中介 | Kun.Core、Kun.Mediator、Kun.Validation | Qian.Runtime、Qian.Runtime.Errors | Qian.Runtime 引用 Kun.Core 与 Kun.Mediator，错误码目录是 Qian 自有 |
| 数据与租户隔离 | Kun.EntityFrameworkCore、Kun.MultiTenancy 及其 EF 包 | Qian.Data、Qian.Tenancy | Qian 建在 Kun 上，`QianDbContext` 继承 `KunDbContext` |
| 权限 | Kun.Authorization | Qian.Authz | Qian 复用 Kun 的端口，引擎是 Qian 自有 |
| 身份 | Kun.Identity 及其 AspNetCore 包、Kun.Security | Qian.Identity.Client、Qian.Identity.Server | Client 包装 Kun.Identity；Server 只在 Qian |
| 网关 | Kun.Gateway、Kun.RateLimit | Qian.Gateway | Qian.Gateway 包装 Kun.Gateway |
| 配置 | Kun.Configuration、Kun.Configuration.Apollo | Qian.Config 及其 Apollo、Secrets 包 | Qian.Config.Apollo 包装 Kun.Configuration.Apollo |
| 文件存储 | Kun.Storage.Abstractions 及 Local、S3、Oss，旧线 Kun.Storage | Qian.Files | Qian.Files 引用 Kun.Storage.Local |
| 事件 | Kun.EventBus 及其 Abstractions、RabbitMQ 包 | Qian.Events | Qian.Events 不直接引用 Kun 的事件包；另有 6 个 Qian 包引用 Kun.EventBus.Abstractions |
| 审计 | Kun.Audit、Kun.Auditing、Kun.Audit.EntityFrameworkCore | Qian.Audit | Qian 不引用 Kun 的三个审计模块，两边各有一套 |
| 编排与调度 | Kun.Saga | Qian.Lifecycle、Qian.Scheduler | Qian 不引用 Kun.Saga |
| 测试夹具 | Kun.Testing 及其 EF 包 | tests/Qian.Testing.Containers | 两边各有一套 |
| 只在 Kun | Kun.Sandbox、Kun.Dapper、Kun.Grpc、Kun.Observability、Kun.Caching、Kun.AspNetCore、Kun.Infrastructure | — | — |
| 只在 Qian | — | Qian.Capabilities、Qian.Registry、Qian.Surfaces、Qian.Profiles、Qian.Plugin.Sdk、Qian.Docs、Qian.Tenancy.Signup | — |

### 切换要处理的量

- Qian：3000 个跟踪文件、1738 个提交、16 条工作流、56 个包项目（`packages/` 约 6.4 万行）、87 个测试项目。Kun：957 个文件、106 个提交、5 条工作流、35 个模块约 2.4 万行。
- `Qian.*` 改名涉及全部命名空间、公共 API 清单与已发布的 `Qian.*` 0.2.0 包；全仓库另有 317 个源文件引用 Kun 命名空间。
- 任务文件里有 721 处历史 PR 号落在 #62–#321，kun 仓库今后会把这些号发给别的 PR。
- 92 个文件写着 `idadawn/qian`，包括看板、文档站、镜像模板的部署清单与三条发版工作流。
- 评估当日 Qian 有在途工作：1 个开着的 PR、105 个远端分支，近 14 天 168 个提交合入 main。Kun 没有在途工作。

### 待定（由合并蓝图回答，推荐是主会话的意见）

- Q1 Kun 的新定位与内部分层。推荐：Kun 是多租户平台与 Agent 框架一体的 .NET 框架。内部分两档：内核模块不带产品语义、可以单独安装、保持 AOT 兼容；平台模块承载租户、身份、权限、能力目录等。依赖只能从平台模块指向内核模块，由门禁守。这样只用内核的下游与 AOT 网关不受平台模块拖累。
- Q2 「Qian」这个名字的去留。候选：不再使用；或留作基于 Kun 装配出的平台产品名。与 Q7、S1-DEC-034 的总名 Yi 一并裁。
- Q3 归并规则（D3 的落地）。推荐：同一职责只留一套公共 API；Qian 包只是包装 Kun 模块的，合成一个模块；两边各有实现的，以在用且有测试的一方为准；两边都没有使用方的模块归档，不搬。
- Q4 许可。Kun 是 MIT，Qian 是 Apache-2.0，一个包族要定一个。推荐 Apache-2.0；已按 MIT 发布的旧版本不受影响。ADR-019 §7 的许可条目随之改写。
- Q5 发布渠道。Kun 在 nuget.org，`Qian.*` 在 GitHub Packages。候选：并成一族后全部上 nuget.org；或平台模块在对外发布时点之前继续走 GitHub Packages，包源映射按模块名单细分。推荐后者，因为 nuget.org 上的包发了就撤不掉。ADR-019 D19.7 随之改写。
- Q6 目录与历史。推荐分两步：先保留历史把 Qian 整棵树导入 kun 仓库的子目录，再按蓝图把项目归并进 Kun 的 `src/`、`tests/`、`docs/`。历史 PR 号改写为 `idadawn/qian#N`，`idadawn/qian` 归档为只读。两边的 ADR 编号重叠，归并时定编号规则。
- Q7 周边名字是否跟着改：`qian` 命令行、`.qian-plugin/plugin.json`、`@qian/*`、yue。推荐 yue 不动，其余随 Q2。
- Q8 时点。推荐蓝图现在就可以写；代码切换要一个冻结窗口，放在「初步可用」里程碑（S1-DEC-033）当前在途任务收口之后，切换前开着的 PR 全部合入或关闭。
- Q9 iClaw。它以项目引用消费 Kun 源码（ADR-001 §1），归并会动到它在用的模块。其现状属私有仓库，不写进本仓库；安排由产品负责人定。

受本裁决影响的其它决策任务：S1-DEC-034 的 D2–D5（总名 Yi 之下的三层口径、不改包名）要按 D2、D4 重看；S1-DEC-035 Q4（Kun 路线）里「不合仓」与「`Qian.*.Abstractions` 不再暴露 Kun 类型」两句失去前提，归档瘦身一句并入 Q3。
