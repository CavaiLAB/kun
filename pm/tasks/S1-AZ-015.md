## 背景

[契约草案](../../docs/prd/specs/authz-remote-interface.md)第 13.2 节第 5 项。[S1-DEC-045](S1-DEC-045.md) D9 定了客户端包先出 TypeScript 与 .NET 两种。条件：两个谁在前看第一个使用方。谁在前后来问过，产品负责人 2026-11-26 定（[S1-DEC-048](S1-DEC-048.md) D3）：先 .NET。落到任务上是整理时定的：本任务排在 TypeScript 的那一个（[S1-AZ-014](S1-AZ-014.md)）前面；一致性用例与替身服务照草案第 7.1 节的提议由先做的那一个带，现在就是本任务，那一个对着它跑。

不在平台宿主里的 .NET 服务今天用的是库模式：三种声明权限点的写法最后都只调宿主登记的判定器的「查一条」，不写决策审计，不比对身份修订。只换一个远程的判定器不够，那样走的是预判。本任务加一种远程模式（草案第 7.3 节）：

- 远程的执行端口：`IAuthzEnforcement` 的远程实现，调执行前的判定，本人的令牌取自当前请求。
- 远程模式的登记方式，与现有的库模式、平台模式并列：HTTP 与 gRPC 的执行点走远程的执行端口；命令的管道行为现在直接调判定器，要改成能走执行端口。
- 远程的判定器，给预判用。

列给产品负责人的理由是工作区服务照现在的设计是 .NET 写的。照这条理由，第一个使用方读作匠心的工作区服务；这半句是问题 3 选项（一）的写法，列给他的话里没有。照 ADR-010 第 9 节，它装本仓库的登录组件 `Kun.Identity.Client`，那是 .NET 的包。它还没有开工；它改用别的语言写的话，两个包的先后要重看。

估时 5 天是建任务时估的，那时没有定一致性用例与替身服务由谁带。现在照上面的做法由本任务带，估时没有重估。开工时先量，超出任务看板 1 至 5 天的粒度，就把用例与替身服务单列成一个任务。

## 验收

- [ ] IT：远程模式下，端点、gRPC 方法、命令上声明权限点的三种写法在使用方的代码里不用改；判定经远程的执行端口到平台，平台一侧留下决策审计并比对身份修订
- [ ] IT：远程的判定器给预判用；预判的结果不当执行的依据
- [ ] UT：判不了一律拒绝，没有放行的开关：不是 200 的响应、超时、连不上、解析不了、缺布尔的放行结果、响应自己对不上，都当作判不了，执行点对外回 503，不回 403
- [ ] UT（D4）：执行前的判定不缓存；预判照平台给的时长缓存，可以关掉，不可以调长
- [ ] 交付一致性用例与可以本机起的替身服务：一组请求、响应的样例，重点查「判不了一律拒绝」的那几条；本包对着它跑通，TypeScript 的包（S1-AZ-014）接着对着同一份跑（由本任务带是整理时落的，见背景）
- [ ] 包的档位与角色写进项目文件，过依赖门禁；公共 API 登记；`AGENTS.md` 里组件设计的四个问题在包的说明里回答
- [ ] 文档站「在 .NET 里接权限」一页补上远程模式怎么用
