## 验收

- [x] 复现与归因：本机或限 CPU 容器（`mcr.microsoft.com/dotnet/sdk:10.0 --cpus=1/2`）复现「领取后处理器超过 5 秒未进入、租约在准备阶段被接管」，给出领取、`BeginAsync` 完成、首次心跳、接管四个时刻与 CPU 争用证据；分清 Scheduler 自身并行（四类同时起 worker 与容器）与分片邻居（同时起宿主的重模块）各自的贡献
- [x] 测试侧修法：不削弱断言（接管语义、attempts / effects 计数、「尚未接管」快照）且用例数不少的前提下，让 Takeover / Renewal 用例在慢 runner 上稳定——候选：调度前让 worker 真正预热（首个领取循环已跑过）、首次尝试等待与租约按比例而非写死 10 秒、错开四个主题类起进程的时刻；改法写进 `tests/README.md`「调度验收的用例写法」
- [x] 产品侧评估：初始租约从领取的 `now()` 起算、心跳在 `BeginAsync` 之后才启动，准备阶段耗时超过 LeaseSeconds − 续租间隔即被接管——是否符合设计写明结论；若要改（如 `BeginAsync` 内先续一次、或初始租约单独配置），说明对生产的影响，生产缺省值不变并单独验证
- [x] 分片放置依据：给出 Scheduler 适合的分片条件（开跑时同分片起宿主的模块数、是否能一开始就跑）与 runner 分组后的数据，交 S1-QA-021 第 2 条 / S1-QA-019 重做配平
- [x] 门禁：修复合入后 main 连续 5 次（不含取消）`Qian.Scheduler.Tests` 全过且首尾跨度 ≤ 250 秒；`pm.py validate` 通过
