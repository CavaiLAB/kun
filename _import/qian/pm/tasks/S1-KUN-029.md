- 组件版本：`_import/qian/plugins/` 下 system 级组件（`policy.tier` 为 system、`runtime.form` 为 module 的非骨架组件，口径同 `scripts/sign-system-revisions.py` 的签名清单）的文件夹里任何文件一改，目录摘要就变：清单里的入口类型与程序集名随包换、README 改一个字都算。按 S1-DEC-037 的裁决（R167），要连带升该组件的版本，版本号继续唯一对应文件夹的内容。这一批碰到的 system 级组件：qian.capabilities、qian.lifecycle、qian.registry。
  - 升版本：同一个组件被先后几个 PR 改到，每个 PR 各升一次，不看前一次升的版本部署过没有（何时部署另定，可能落在任意两次合入之间）。升哪一位照 R167 采纳的做法：只改说明文字升修订号；对外行为不变的改动（清单里的入口类型与程序集名、契约文件里的 Schema 键）与兼容的增加（加权限点、可选字段）升次版本；对外行为变了、不兼容（线上契约、权限点、配置 Schema）升主版本。
  - 发布的 HTTP 契约会随换包名漂移：`Qian.Capabilities.AspNetCore` 的 `AspNetCoreHttpContractSource` 给组件 Schema 取键用的是类型程序集限定名的哈希，类型的命名空间、程序集名或程序集版本一变，键就变（过渡目录里的程序集版本是 1.0.0.0，搬进 `src/` 后照 `src/Directory.Build.props` 的 `VersionPrefix` 是 0.1.0.0）。发布契约有三份，是 `plugins/qian.registry`、`plugins/qian.tenancy`、`plugins/qian.tenancy.signup` 下的 `contracts/http-v1.openapi.json`，分别由 Qian.Registry.Tests 的 `ScopeWriteContractTests`、Qian.Sample.Crm.Tests 的 `TenantOperationsTests`、Qian.Tenancy.Signup.Tests 的 `SignupContractTests` 比对。换包名之后跑这三处，漂了就照测试里的 `QIAN_UPDATE_*_CONTRACT=1` 重新生成；三个组件都是 system 级，重新生成就要照上面升版本。租户那处要容器，注册表与租户两处还要 oasdiff，本机多半跑不全，以 CI 为准。这一批碰到 qian.registry：它的请求与响应类型 `RegistryScopePatchRequest`、`RegistryScopePatchResult` 在 Qian.Registry.Abstractions。Qian.Registry.Tests 与 Qian.Sample.Crm.Tests 随这一批搬出，它们按 `Qian.slnf` 往上找根、契约路径按过渡目录写，搬的时候一并改。
  - 契约键去掉程序集版本，在这一批做：组件 Schema 的键不再带程序集版本、区域（Culture）与公钥标记（PublicKeyToken），泛型实参与数组元素同样处理；只换成 `FullName` 去不干净，泛型类型的 `FullName` 里带着类型实参的程序集限定名。程序集名保留，免得不同程序集里同名的类型撞键。算法用单元测试钉住（普通类型、泛型、数组、嵌套类型，名字里都不出现版本）。改完之后三份发布契约最后重新生成一次、升版本。要排在首个合并版（B12，S1-KUN-022）之前完成：发版构建会传入版本号，`src/Directory.Build.props` 的 `VersionPrefix` 以后也可能变，键里带着版本，契约就跟着漂。不在 B4 改：从 B4 到这一批，程序集搬进 `src/` 总是和换名同时发生，只因版本而漂的情况不会单独出现；B4 的 PR 在关键路径上，不加别的域的改动；能力的 HTTP 契约导出属于这一批的域，注册表那份契约也在这一批重新生成。
