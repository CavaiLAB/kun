# Kun

[匠心智能体平台](https://github.com/CavaiLAB/jiangxin)的企业级后端框架：为 Agent 时代构建的多租户平台框架，.NET 10。

> **状态：规划稿（2026-11-17）。本仓库目前只有框架级文档，没有代码。**
>
> 代码在两个原仓库里：[`idadawn/kun`](https://github.com/idadawn/kun)（原 Kun 框架）与 [`idadawn/qian`](https://github.com/idadawn/qian)（原 Qian 平台的后端）。它们按合并蓝图归并之后迁入这里。
>
> `CavaiLAB/kun` 这个地址以前会跳转到 `idadawn/kun`，本仓库建立之后不再跳转。要取现在的 Kun 源码，请直接用 `idadawn/kun`。

## 定位

已定的表述（2026-11-17）：

> Kun 是为 Agent 时代构建的多租户平台框架（.NET 10）。它由三部分组成：一组不带产品语义、可以单独安装的内核包；一组以组件形式装配的平台组件（租户、身份、权限、数据、文件、配置、事件、审计、能力目录）；以及组件运行时、命令行与目录市场。

Kun 由两部分归并而成：

- **原 Kun**：.NET 10 的云原生微服务框架。领域建模、命令与查询分离、可靠事件、网关与服务间认证、多租户、存储、缓存、可观测。
- **原 Qian 的后端**：建在原 Kun 之上的多租户平台。组件运行时、租户、身份、权限、数据、事件、审计、配置、文件、调度、注册表、能力目录。

两者合成一个框架、一个包族 `Kun.*`、一条日历版本线。合并不是原样搬运：两边重叠的职责合成一份。

在平台的理念「三元全智生命体」里，Kun 是「三元」的后端一半，也就是躯体。它为智能体提供身份、能力目录、协同与人审，但不写智能体的推理循环，那是 [SanYuanAgent](https://github.com/CavaiLAB/sanyuan-agent) 的事。

## 两档

| 档位 | 是什么 | 规则 |
|---|---|---|
| 内核档 | 通用机制：错误模型、命令与查询调度、租户上下文、事件总线、数据访问约定、令牌校验、网关、存储后端、配置源。它不知道租户目录、人员、角色、组件清单这些产品概念 | 可以在任意 .NET 10 应用里单独安装使用；不得引用平台档的包 |
| 平台档 | 带产品语义：租户主档与开通、身份服务、权限引擎、文件服务、能力目录、注册表、生命周期、调度 | 以组件形式装配；只依赖内核档，以及别的平台组件的契约包 |

按合并蓝图，合并之后共 84 个包：内核档 40 个，平台档 44 个。原来「框架不带产品语义」靠两个仓库隔开，合并之后改由档位和门禁保证。档位的判据与逐个包的归属写在蓝图里，随蓝图整体确认。

## 它负责什么

| 能力域 | 内容 |
|---|---|
| 运行时与组件 | 上下文、服务注册、类型化事件、可撤销的副作用、装载器；profile、组合包与补丁；注册表与生命周期 |
| 命令行与目录市场 | 组件的安装、移除、列出、健康检查、打印配置树；目录市场的清单格式 |
| 多租户 | 租户上下文贯穿全栈，数据按租户行级隔离；租户主档与开通；租户范围的组件启用与定制 |
| 身份 | 单点登录的签发方与客户端，外部身份源连接器，会话 |
| 权限 | 权限点与角色，数据与字段级判定，入口缺省拒绝的强制执行点 |
| 数据 | 数据访问约定，行级隔离，不经 ORM 的原生通道，数据库方言与迁移 |
| 事件 | 领域事件与集成事件，同事务落库后可靠投递，消费端幂等 |
| 审计 | 审计记录与业务同事务，串成哈希链，事后可核验 |
| 配置与密钥 | 强类型配置，配置中心接入，密钥只以引用出现 |
| 存储与文件 | 存储后端（本地、对象存储）；带配额与策略的文件服务 |
| 网关 | 反向代理，外部令牌校验，内部短期令牌签发，限流 |
| 调度 | 定时与后台作业 |
| 能力目录 | 每项能力登记输入输出 Schema、副作用等级、所需权限、是否对 Agent 暴露 |
| 缓存与可观测 | 统一缓存；追踪、指标、日志 |
| 对智能体的支撑 | `agent` 主体与委托链、Agent 归属与目录、协同信箱与人审、把能力目录暴露成工具。大部分是规划，见[框架架构](docs/architecture.md) |

## 设计原则

1. **没有特权内核。** 运行时只有一个很小的核心，租户、身份、权限这些平台能力都是组件，任何一项都能从配置里替换。
2. **契约与实现分包。** 一项能力拆成契约包（接口与词汇）和提供方包（实现）。使用方只依赖契约包，换一个实现不影响使用方。
3. **装一个包就能用。** 内核档的包装一个就能在别的 .NET 项目里独立使用，不要求先部署整个平台。
4. **多租户贯穿。** 租户上下文只来自令牌，缺失即拒绝。租户号统一用 Guid。
5. **入口缺省拒绝。** HTTP、命令、gRPC 入口都经过强制执行点，没有声明权限的入口不放行。
6. **契约冻结后只做加法。** 跨服务的契约冻结之后，只增加字段，不改、不删。
7. **门禁把关。** 公共 API 清单、包的档位与依赖方向、一致性测试都由 CI 检查。

## 已定与待定

已定（产品负责人，2026-11-17）：

- 原 Qian 的后端并入 Kun；包名并为 `Kun.*`，一个包族，一条日历版本线；合并时归并重叠；Kun 重新定位，表述见上。
- 租户号统一用 Guid，去掉缺省租户的回落。
- 许可：.NET 包族、命令行与前端包全部用 MIT。
- 发布：内核档照旧发 nuget.org；平台档在正式对外发布之前只发 GitHub Packages，之后全族上 nuget.org。
- 归档五个没有使用方或已废弃的模块：`Kun.Saga`、`Kun.Sandbox`、`Kun.Dapper`、`Kun.Infrastructure`、旧线的 `Kun.Storage`。
- 「Qian」只作前端框架的名字。组件 id 前缀 `qian.`、清单与配置的文件名、`qian` 命令行这些运行期的字面保留不改，不再表示产品名。
- 合并后的 Kun 放在本仓库，代码分批迁入。

待定：

- 合并蓝图整体还没有确认。确认之前不动代码和仓库结构，两个原仓库照现行规则开发。
- 冻结窗口放在什么时候；用源码引用 Kun 的下游怎么安排。
- 蓝图是按「并进 `idadawn/kun` 一个仓库」写的。现在改为迁入本仓库，并且前端单独一个仓库，蓝图里的目标仓库与目录布局要相应修订，见[迁移与归并](docs/migration.md)。
