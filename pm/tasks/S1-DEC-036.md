## 背景

2026-11-17 产品负责人提问：「评估一下 Kun 和 Qian 是否可以合并为一个框架。」

合仓此前被否决过三次：ADR-001 §4、ADR-021 D21.2、框架细化备忘录 §3.3 (d)。主会话按当日的代码重核后，认为当时的理由大多已不成立，推荐合到「一个框架、一个仓库、一次发版」为止，包名与分层不动。本任务登记这次重评，D1–D7 是主会话的推荐，由产品负责人逐条确认或改裁。拍板前，ADR-001 §4 与 ADR-021 D21.2 的「不建大单仓」仍是现行口径。

### 「合并」分四层

| 合并到哪一层 | 能不能 | 推荐 |
|---|---|---|
| 口径：对外是一个框架 Yi，Kun 是它的内核包族 | 能，成本很低 | 做（D1） |
| 仓库：Kun 源码并入 qian 仓库，包名与命名空间不变 | 能，粗估 5–8 人日 | 做，时点见 D3（D2） |
| 包族：`Kun.*` 改名并入 `Qian.*` 或 `Yi.*`，一个版本号 | 能，但要改 Qian 全仓库 317 个引用 Kun 命名空间的源文件，nuget.org 上的旧包全部弃用 | 不做（D5） |
| 分层：取消「Kun 不带产品语义、不引用 Qian」 | 不该合 | 保留为仓库内门禁（D6） |

### 当时的理由与现在的情况

| 当时的理由 | 出处 | 2026-11-17 的情况 |
|---|---|---|
| 跨仓库源码引用下，Kun 的破坏性变更直接打断构建 | ADR-001 §4 | 同仓之后变更与修复在同一个 PR 里过 CI，这条不适用 |
| 镜像构建依赖私有仓库 | ADR-001 §4 | kun 与 qian 都已是公开仓库 |
| 第三方无法依赖源码 | ADR-001 §4 | 第三方仍然只装包，合仓不改变包的发布 |
| Kun 有独立下游与发布节奏 | ADR-021 D21.2 | Kun 10 月以来 22 个非合并提交里 18 个带 Qian 任务号；10 月发了 11 个 tag，Qian 的 `KunVersion` 同期换了 10 次；11 月至评估日没有提交 |
| 单人维护下合并只会放大耦合 | ADR-021 §3 | 耦合已经在：Qian 以 `[$(KunVersion)]` 精确钉版，10 月 8 日到 25 日升级 10 次，每次修复都多走一轮 Kun 发版与 Qian 升级 |
| 两套版本线与许可二选一会破坏 iClaw 的还原 | 备忘录 §3.3 (d) | 合仓不要求二选一（D5、D7）；受影响的是 iClaw 指向同级目录的源码路径（D4） |

代码层面两边已是一套词汇：Qian 的 56 个包项目里 23 个直接引用 Kun 包，`ITenantContext` 在全仓库出现 352 行，`QianDbContext` 继承 `KunDbContext`，24 个公共 API 清单文件里有 72 行 Kun 类型。规模上 Kun 是小的一方：35 个模块约 2.4 万行，Qian 的 `packages/` 约 6.4 万行。

仍然成立的约束：iClaw 以项目引用消费 Kun 源码（ADR-001 §1），其现状属私有仓库，不写进本仓库，评估当日已在对话里向产品负责人说明；`Kun.*` 在 nuget.org 已发到 2026.10.25，包名不变就并不进 0.x 的语义版本线；两边同名的中央包依赖 22 个里 19 个版本不同，Kun 的 CI 在自托管 runner 上、Qian 的在 GitHub 托管 runner 上，合仓要并轨。

### 待拍板

- D1 口径。推荐：采纳。对外是一个框架 Yi；Kun 改称「Yi 的内核包族」，不再写「面向任何 .NET 微服务的开发框架」；Qian 是平台层，也是面向第三方的 API 面；yue 是前端层。三层的层次不变，变的是 Kun 那一格的定位。与 S1-DEC-034 D2、S1-DEC-035 Q4 的前半句是同一件事，三处一并裁。
- D2 合仓。推荐：采纳。Kun 的源码与测试连同历史并入 `idadawn/qian`，放在独立的顶层目录；`Kun.*` 的包名、命名空间与 nuget.org 发布渠道都不变；Qian 包对 Kun 改为仓库内的项目引用，打包产物里仍然是对 `Kun.*` 包的依赖；`idadawn/kun` 归档为只读，README 指向新位置。ADR-001 D1.2「禁止把 Kun 源码复制进 Qian 仓库或以 ProjectReference 引用」随之改写；S1-DEC-035 Q4 里「不合仓」一句随之改写，Q4 的其余部分不受影响。
- D3 时点。推荐：放在下一批 Kun 改动之前，不插进「初步可用」里程碑（S1-DEC-033）的在途工作。11 月跨仓库改动为零，现在合仓收益兑现不了。接缝是 S1-KUN-015 或 S1-DEC-035 Q4 的归档瘦身发版，哪个先开工就在它之前做。
- D4 iClaw 的消费方式。推荐：作为合仓的前置。iClaw 改为引用 nuget.org 上的 `Kun.*` 包，与 ADR-001 D1.2 对 Qian 的要求一致。由谁做、何时做待产品负责人定；这一步不做就不合仓。
- D5 包族与版本线。推荐：不改名。维持两种版本号（`Kun.*` 日历版本、`Qian.*` 语义版本锁步），由同一条发版流水线一次发出。`Kun.*` 并入 `Qian.*` 或改成 `Yi.*` 不做；要统一成一个版本号，留到 1.0 之前再议。
- D6 分层。推荐：保留。「Kun 不带产品语义、不引用 Qian」的依赖方向由仓库内门禁守：`scripts/check_deps.py` 加一条「`Kun.*` 项目不得引用 `Qian.*`」，Kun 原有的分层检查与 AOT 审计并入 Qian 的工作流，按路径触发。
- D7 许可。推荐：分目录并存。Kun 目录维持 MIT，Qian 维持 Apache-2.0。仓库根目录补许可文件的事在 S1-DEC-035 Q28，不在本任务裁。

### D2 采纳后的工作

拍板后建档取号，下列各项合计粗估 5–8 人日，iClaw 切换另计 1–2 人日。估算未经拆解验证。

1. 保留历史导入 Kun 的源码与测试。
2. 构建基线并轨：中央包版本、分析器与 AOT 开关的作用域。
3. CI 并轨：Kun 的构建与测试、AOT 审计矩阵、分层检查，按路径触发。
4. 发版流水线一次发两族包；`KunVersion` 钉版机制定去留。
5. 文档站「Kun 框架」小节改为同仓来源，撤掉镜像同步与 tag 比对门禁。
6. 改写 ADR-001、ADR-021、`AGENTS.md` 与备忘录 §3.3 (d)。
7. `idadawn/kun` 归档为只读。
